## Decisions made during planning

### D-01 — Drop the `sourceSample` parameter entirely (21 params → 20)

The planning brief asked for a justified choice between (a) dropping the parameter, (b)
keeping it as a single-choice parameter, and (c) some other option. **Option (b) is not
merely risky — it is forbidden by JUCE**, which settles it. Two independent assertions in the
local JUCE 8.0.14 tree:

- `modules/juce_audio_processors_headless/utilities/juce_AudioParameterChoice.cpp:63` —
  `jassert (choices.size() > 1); // you must supply an actual set of items to choose from!`
- `modules/juce_core/maths/juce_NormalisableRange.h:254` — `checkInvariants()` asserts
  `end > start`, and `AudioParameterChoice` builds its range as
  `NormalisableRange<float> { 0.0f, (float) choices.size() - 1.0f }`
  (`juce_AudioParameterChoice.cpp:47`). One choice gives `{0.0f, 0.0f}`.

In a Release build (assertions compiled out) the degenerate range is worse, not better:
`convertTo0to1` computes `(v - start) / (end - start)` = `0/0` = NaN
(`juce_NormalisableRange.h:141`), and the guard `clampTo0To1` uses `jlimit`, which returns
its input unchanged for NaN (`NaN < 0` and `1 < NaN` are both false) — so the NaN
**propagates** rather than being clamped (`juce_NormalisableRange.h:259-268`). The very first
thing `AudioParameterChoice`'s constructor does is `defaultValue (convertTo0to1 ((float) def))`
(`:55`), so the parameter would be born holding NaN. This is exactly
`pattern_ci_pluginval10_catches_latent_nan` waiting to happen.

**Option (c) considered and rejected:** a two-choice `{ "piano", "(loaded)" }` selector would
satisfy JUCE's arity rule, but FUNC-02/03 explicitly specifies that the loaded-file state is
custom ValueTree state and **not** a choice entry (`.planning/parameter-spec.md:28`). It would
also create a real semantic hole — selecting "(loaded)" with nothing loaded has no defined
behaviour.

**Contract impact is nil.** The "frozen 21-param contract" has no downstream consumer: the
plugin has zero releases. Automation IDs for the surviving 20 parameters are stable in both
formats — JUCE derives VST3 `ParamID` and AUv2 `AudioUnitParameterID` from a hash of the
parameter's string ID, not from its index, so removing index 0 does not renumber the rest.
Old sessions carrying a `sourceSample` entry restore harmlessly: `replaceState` leaves an
orphan child with no matching parameter inert.

The `auval` assertion of "21 Global Scope Parameters" recorded in the Stage-4 SUMMARY
therefore moves to **20**, which Task 4 asserts explicitly.

### D-02 — No preset or session migration is required

Measured, not assumed:

- **All 7 factory presets were read** (`PluginProcessor.cpp:588-660`). *Raw One-Shot*,
  *Tuned Across the Keyboard*, *Looped Pad*, *Reversed Swell*, *Repitch vs Stretch A/B*,
  *SP-1200 Crunch*, *Filtered & Enveloped* — **not one of them sets `sourceSample`**. Every
  branch is deliberately source-agnostic; the only source-related step is the central
  post-reset root re-seed at `:579`, which reads `currentSourceIdentity` (custom state) and
  keeps working unchanged. No preset selects a withdrawn built-in.
- **This plugin has no JSON presets.** `find plugins/O-simpleSampler -name "*.json"` returns
  nothing and the plugin does not consume the `preset-manager` module. So
  `critical_apvts_denormalised_vs_preset_normalised` and
  `pattern_factory_preset_normalized_ignores_skew` have no surface here — there is no stored
  normalised value whose meaning shifts when the choice count changes, because the parameter
  is being removed rather than resized.
- **`pattern_preset_apply_needs_reset_to_defaults` is already satisfied** —
  `applyFactoryPreset` step 1 resets every parameter to its default before applying
  (`:556-557`).

### D-03 — No render-harness case exercises a withdrawn built-in

`tests/render-harness/main.cpp:373` pins the source to index 0 (piano) in the single
`setBaseline` helper, and `main.cpp:381` pins `rootKey` to 48 for deterministic pitch tests.
No other case touches the selector. The removal is a one-line deletion, and it is a
**compile-time** link: `PID::sourceSample` disappearing from the header makes the harness fail
to build if the line is missed. Per `pattern_render_harness_breaks_on_webview_editor` the
harness is still re-run in Task 4.

### D-04 — Version 1.1.0

A minor bump. Removing a parameter from a frozen contract would normally be major, but the
plugin has never been released, so there is no downstream contract to break and a 2.0.0 for an
unreleased plugin is noise. `1.1.0` signals a visible content change. Use the `VERSION`
keyword in `juce_add_plugin` — `PLUGIN_VERSION` is not a JUCE keyword and is silently ignored
(`critical_plugin_version_keyword_ignored_by_juce`).
