```markdown
# State Validation Skill

## Purpose
Detect inconsistencies in Plugin Freedom System state files. Runs on /continue, /focus, and /reconcile.

## Validation Protocol

### 1. Schema Validation
For each state file, validate against its schema:
- .planning/workflow/registry.json -> registry.schema.json
- .planning/workflow/active-plugin.json -> active-plugin.schema.json
- plugins/{name}/.planning/STATUS.md frontmatter -> status conventions

### 2. Cross-File Consistency Checks
Compare fields that must match across files:

| Source | Field | Must Match |
|--------|-------|------------|
| registry.json | plugins.{name}.stage | STATUS.md frontmatter stage |
| registry.json | plugins.{name}.phase | STATUS.md frontmatter phase |
| registry.json | plugins.{name}.status | STATUS.md frontmatter status |
| registry.json | focused | active-plugin.json plugin |

### 3. Existence Checks
- Every plugin in registry.json must have STATUS.md at `plugins/{name}/.planning/STATUS.md`
- Every plugin directory in `plugins/` should have registry entry (warning, not error)

## Result Format

[Include ReconciliationResult interface from RESEARCH.md]

status: 'healthy' | 'inconsistent' | 'corrupted'
- healthy: All checks pass
- inconsistent: Cross-file mismatches (recoverable)
- corrupted: Schema violations (needs repair)

## Check Execution Order

1. Registry file exists and is valid JSON
2. Registry matches registry.schema.json
3. Active plugin file exists and is valid JSON
4. For each plugin in registry:
   a. STATUS.md exists
   b. STATUS.md frontmatter is valid YAML
   c. Stage/phase/status match registry
5. Focused plugin matches active-plugin.json

## Output Format

When validation finds issues:

```
STATE VALIDATION REPORT
=======================
Status: [healthy|inconsistent|corrupted]
Timestamp: [ISO 8601]

Checks Run: N
Passed: M
Failed: K

[If failed checks:]
ISSUES FOUND:
-------------
1. [check_name]: [description]
   Location: [file:field]
   Expected: [value]
   Actual: [value]

2. ...

RECOMMENDED ACTION:
[Based on severity, link to recovery options]

```markdown
# State Recovery Skill

## Purpose
Repair corrupted or inconsistent Plugin Freedom System state. Always prompts user before making changes.

## Recovery Principle

**Never auto-repair silently.** Present options, explain tradeoffs, let user choose.

## Recovery Options

### Option 1: Manual Repair Instructions
**When to offer:** Any inconsistency
**What it does:** Provides exact commands/edits to fix the issue manually
**Risk level:** Lowest (user controls every change)

Format:
```
MANUAL REPAIR:
1. Open [file]
2. Change [field] from [current] to [expected]
3. Save file
4. Run /reconcile to verify
```

### Option 2: Reset to Last Checkpoint
**When to offer:** Valid checkpoint exists
**What it does:** Restores state files from checkpoint snapshot
**Risk level:** Medium (loses changes since checkpoint)

Prerequisites:
- Checkpoint file exists at `.planning/workflow/checkpoints/{plugin}/latest.json`
- Checkpoint is newer than 24 hours (configurable)

### Option 3: Rebuild from Filesystem
**When to offer:** Registry corruption, missing registry entries
**What it does:** Scans plugins/ directory and rebuilds registry
**Risk level:** Medium (may miss metadata not in filesystem)

Rebuild logic:
1. Scan `plugins/*/` directories
2. For each, read `.planning/STATUS.md` if exists
3. Extract stage, phase, status from frontmatter
4. Create registry entry
5. Set focused to first active plugin

## Source of Truth Rules

When files disagree, determine source of truth:

| Field | Source of Truth | Rationale |
|-------|-----------------|-----------|
| stage | STATUS.md | Updated during execution, closer to work |
| phase | STATUS.md | Updated during execution |
| status | STATUS.md | User may edit directly |
| path | Filesystem | Directory location is canonical |
| created | Registry | Original creation date |
| modules | Registry | Updated via /module commands |

## Recovery Execution

1. Present validation findings (from state-validation skill)
2. List applicable recovery options (1, 2, or 3)
3. Explain risk/benefit of each
4. Wait for user choice
5. Execute chosen recovery
6. Re-run validation to confirm
7. Report final state

## Prompts

### Inconsistency Found
```
STATE INCONSISTENCY DETECTED

[Issue description]

Recovery options:
1. Manual repair (safest) - I'll show you exactly what to edit
2. Rebuild from STATUS.md (recommended) - Update registry from plugin states
3. Skip - Continue with current state (not recommended)

Which option? [1/2/3]
```

### Corruption Found
```
STATE CORRUPTION DETECTED

[Issue description - schema violation or missing file]

Recovery options:
1. Manual repair - I'll guide you through fixing [file]
2. Reset to checkpoint - Restore from [timestamp] (loses recent changes)
3. Rebuild from filesystem - Reconstruct registry from plugins/

Which option? [1/2/3]
```
```

- User prompts with clear option explanations

```markdown
# /reconcile

Run state validation and offer recovery options if issues found.

## When to Use

- After manual file edits to STATUS.md or registry
- When session state seems wrong
- After git merge that touched .planning/ files
- Debugging "plugin not found" or stale state issues

## Process

1. **Load validation skill**
   @.claude/skills/state-validation/SKILL.md

2. **Run all validation checks**
   - Schema validation for registry.json, active-plugin.json
   - Cross-file consistency (registry <-> STATUS.md)
   - Existence checks (all registered plugins have STATUS.md)

3. **Report findings**
   Display STATE VALIDATION REPORT with pass/fail for each check

4. **If issues found:**
   Load recovery skill: @.claude/skills/state-recovery/SKILL.md
   Present recovery options based on issue type
   Execute user's chosen recovery
   Re-validate to confirm fix

5. **If healthy:**
   Report "State validated successfully. No issues found."

## Example Output

**Healthy state:**
```
STATE VALIDATION REPORT
=======================
Status: healthy
Timestamp: 2026-01-30T15:00:00Z

Checks Run: 8
Passed: 8
Failed: 0

State validated successfully. No issues found.
```

**Inconsistent state:**
```
STATE VALIDATION REPORT
=======================
Status: inconsistent
Timestamp: 2026-01-30T15:00:00Z

Checks Run: 8
Passed: 7
Failed: 1

ISSUES FOUND:
-------------
1. stage_consistency: Registry and STATUS.md disagree on stage
   Location: plugins.O-IntonationPad.stage
   Registry: 1-foundation
   STATUS.md: 2-dsp

RECOMMENDED ACTION:
Run recovery to synchronize. STATUS.md is typically more current.

[Recovery options presented...]
```

## Related Commands

- `/continue` - Runs validation automatically on session resume
- `/focus` - Runs validation automatically when switching plugins
```
