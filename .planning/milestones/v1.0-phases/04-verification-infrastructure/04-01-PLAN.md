  <action>
Create three JSON Schema files following draft 2020-12 (consistent with Phase 1-3 infrastructure):

**critic-report.schema.json** - Base schema that domain schemas extend:
- Required fields: critic, plugin, stage, attempt, maxAttempts, timestamp, scores, overallStatus, issues, nextAction
- `scores` as object with ScoreEntry definition (score 1-10, threshold 1-10, passed boolean, details string)
- `overallStatus`: enum ["PASSED", "NEEDS_FIXES", "ESCALATE"]
- `issues` array with Issue definition: id (pattern ^[A-Z]+-[0-9]+$), severity (error|warning), category, location, description, fixSuggestion (minLength 10)
- `previousIssueIds` array for no-progress detection
- `nextAction`: enum ["gate_pass", "fix_and_resubmit", "escalate_to_user"]
- `tokenMetrics` object with thisIteration, cumulative, budgetWarning fields
- additionalProperties: false for strict validation

**critic-dsp-report.schema.json** - DSP domain:
- $ref to critic-report.schema.json for base structure
- Override scores to require: realtime_safety (threshold 8), buffer_handling (threshold 7), parameter_integration (threshold 6)
- Optional: numerical_stability, architecture_alignment
- stage pattern: "^2-dsp$"
- critic: const "dsp-critic"

**critic-ui-report.schema.json** - UI domain:
- $ref to critic-report.schema.json for base structure
- Override scores to require: polish (threshold 5), consistency (threshold 6)
- Optional: accessibility, responsiveness
- stage pattern: "^3-gui$"
- critic: const "ui-critic"

Use the example from 04-RESEARCH.md as reference for structure. Ensure $id fields are set for proper schema resolution.

<task type="auto">
  <name>Task 2: Create critic orchestration script</name>
  <files>
    .planning/workflow/scripts/run-critic.sh

  <action>
Create bash script that orchestrates critic validation with iteration support:

**Arguments:**
- `<plugin>` - Plugin name (e.g., O-IntonationPad)
- `<stage>` - Stage identifier (e.g., 2-dsp, 3-gui)
- `--attempt N` - Current attempt number (default 1)
- `--deep` - Deep validation mode (vs smoke test)
- `--force` - Bypass with stderr warning (consistent with validate-handoff.sh pattern)
- `--help` - Usage info

**Stage-to-critic mapping:**
- 2-dsp -> dsp-critic
- 3-gui -> ui-critic
- Other stages -> "No critic applicable" (exit 0)

**Iteration behavior per CONTEXT.md:**
- Display "Attempt N/3" prominently for agent urgency awareness
- Check for previous iteration report in `.planning/verification/{plugin}/{stage}/`
- Load previousIssueIds if prior report exists
- Detect no-progress: if currentIssueIds == previousIssueIds, set nextAction to "escalate_to_user"

**Early-stop conditions:**
1. All scores >= thresholds -> PASSED (exit 0)
2. Same issues as previous iteration -> NO_PROGRESS (exit with escalation message)
3. Iteration count >= 3 -> MAX_ITERATIONS (exit with escalation message)

**Token budget tracking:**
- Accept --token-count N argument for cumulative tracking
- Warn (stderr) when cumulative > 50000 (soft limit from RESEARCH.md)
- Never block on token budget (warn-not-block per CONTEXT.md)

**Output:**
- Create report directory: `.planning/verification/{plugin}/{stage}/`
- On failure: write critic-failure-{timestamp}.json
- On pass: no file persisted (per CONTEXT.md decision)
- Exit codes: 0=PASSED, 1=NEEDS_FIXES, 2=ESCALATE, 3=usage error

**Integration point for Phase 5:**
- Output format compatible with stage-transition-gate.sh
- Can be invoked by gates or manually

Model on validate-handoff.sh style: colored output, clear section headers, consistent exit codes.
