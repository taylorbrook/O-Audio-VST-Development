# Coding Conventions

**Analysis Date:** 2026-01-29

## Naming Patterns

**Files:**
- Headers: `PascalCase.h` (e.g., `PluginProcessor.h`, `CrossoverFilter.h`)
- Implementation: `PascalCase.cpp` (e.g., `PluginProcessor.cpp`, `HarmonicGenerator.cpp`)
- UI files: `PluginEditor.h` / `PluginEditor.cpp` (standard JUCE convention)
- DSP components: Grouped in `Source/DSP/` subdirectory with descriptive names

**Classes:**
- `PascalCase` for all class names (e.g., `OBassAudioProcessor`, `CrossoverFilter`, `HarmonicGenerator`)
- Processor classes: `O{PluginName}AudioProcessor` (e.g., `OBassAudioProcessor`, `OAnalogSaturationAudioProcessor`)
- Editor classes: `O{PluginName}AudioProcessorEditor` (e.g., `OBassAudioProcessorEditor`)
- DSP utility classes: Descriptive `PascalCase` without prefix (e.g., `CrossoverFilter`, `Compressor`, `EnvelopeDetector`)

**Functions/Methods:**
- `camelCase` for public methods (e.g., `prepareToPlay()`, `processBlock()`, `setCutoffFrequency()`)
- JUCE overrides follow exact JUCE interface signatures (e.g., `processBlock()`, `releaseResources()`)
- Helper methods: `camelCase` (e.g., `updateLatencyReport()`, `recombineBands()`)

**Variables:**
- Member variables: `camelCase` with no prefix (e.g., `smoothedEnhance`, `limitIndicator`, `outputLevelDB`)
- Static constants: `UPPER_CASE` with `k` prefix (e.g., `kInputDrive`, `kH2Weight`, `kMaxFreq`)
- Local variables: `camelCase` (e.g., `targetGainReductionDB`, `envelopeLevel`)
- Atomic variables: `camelCase` with `std::atomic<>` wrapper (e.g., `limitIndicator { 0.0f }`)
- Parameters: `camelCase` (e.g., `sampleRate`, `samplesPerBlock`, `freqHz`)

**Types:**
- Enums: `enum class Mode { LowLatency, HighFidelity }` (scoped enums, `PascalCase` values)
- Type aliases: Not commonly used; prefer explicit types
- Template parameters: Not extensively used in this codebase

## Code Style

**Formatting:**
- No `.clangformat` file detected; code uses 4-space indentation consistently
- Brace style: Allman (opening brace on same line for functions, new line for class definitions)
- Line length: Generally 100-120 characters
- Spacing: Single space after control structures (`if (`, `for (`)

**Linting:**
- No linter configuration file (`.eslintrc`, `clang-tidy`) detected
- Compiler warnings enabled via CMake: `juce_recommended_warning_flags`
- No automated formatting enforcement

**Comments:**
- File headers: Standard JUCE license block with description
```cpp
/*
  ==============================================================================

    PluginName - Description
    Ouaricon Audio
    Developer: Taylor Brook

  ==============================================================================
*/
```
- Inline comments: Explain WHY, not WHAT (e.g., `// RT-safe mode flag`, `// avoid clicks`)
- Complex sections: Numbered phases (e.g., `// Phase 2.1: Setup oversampling`)
- Warnings: `// CRITICAL:` for build/runtime critical notes
- Known issues: `// Note:`, `// DISABLED:`, `// ("error message" explanation)` for problematic features

## Import Organization

**Order:**
1. C++ standard library: `#include <vector>`, `#include <atomic>`, `#include <cmath>`
2. JUCE modules: `#include <juce_audio_processors/juce_audio_processors.h>`, `#include <juce_dsp/juce_dsp.h>`
3. JUCE sub-modules: `#include <juce_audio_basics/juce_audio_basics.h>`
4. Local headers: `#include "PluginProcessor.h"`, `#include "DSP/CrossoverFilter.h"`
5. Generated headers: `#include "BinaryData.h"` (generated by CMake)

**Path Aliases:**
- No CMake `include_directories` aliases used; paths relative to `Source/` and `Source/DSP/`
- Includes use relative paths: `#include "DSP/CrossoverFilter.h"`
- Generated headers implicit in build

**Header Guards:**
- Pattern: `#pragma once` (modern C++, consistently used)
- Example: `CrossoverFilter.h` starts with `#pragma once`

## Error Handling

**Patterns:**
- No exceptions thrown; audio DSP code assumes success
- Return values used sparingly (mostly `bool` for success/failure in preset operations)
- Invalid parameters: Silently clamped or ignored (defensive programming)
- Thread safety: `std::atomic<T>` for shared state between audio and UI threads
- Assertions: `jassert()` macro available via JUCE (not observed extensively used)

**Null Checks:**
- Done implicitly via JUCE smart pointers (`std::unique_ptr<>`)
- Manual null checks rare; prefer lifetime management

**Audio Processing Safety:**
- No bounds checking in hot DSP loops (assumes correct buffer sizes from host)
- Defensive input validation in public methods (e.g., `if (numSamples == 0) return;`)
- Off-nominal state handling via smoothed value transitions

## Logging

**Framework:** No logging framework detected (console not used in audio plugins)

**Output Methods:**
- UI feedback: Atomic variables read by UI thread (e.g., `inputLevelDB.load()`)
- Debug output: Possible via IDE debugger; not baked into plugin code
- Status indicators: Atomic float meters (e.g., `gainReductionMeter`, `limitIndicator`)

**Patterns:**
- No log messages to files or console
- Meters updated via atomics: `gainReductionMeter.store(value, std::memory_order_relaxed)`
- UI polls meter values on timer: `getOutputLevelDB()`, `getLimitIndicator()`

## Comments

**When to Comment:**
- Complex DSP algorithms: Explain theory and implementation
- Non-obvious parameter choices: Document why a value was chosen
- Known limitations: Mark with `// Note:`, `// DISABLED:`
- Algorithm references: `// Linkwitz-Riley 24dB/oct`, `// Chebyshev waveshaper`
- TODO/FIXME/known issues: Clearly marked

**JSDoc/TSDoc:**
- Limited use; main API class `OuariconPresetManager` has detailed comments
- Method signatures documented with intent (e.g., `// Process stereo buffer with sidechain filtering`)
- Parameter descriptions in comments for complex functions

**Example Comment Style:**
```cpp
// FIR coefficient bank constants (Approach 3: Deferred Update)
static constexpr float kMinFreq = 40.0f;

// Smoothed frequency changes for IIR mode (avoid clicks)
juce::SmoothedValue<float, juce::ValueSmoothingTypes::Multiplicative> smoothedCutoff;
```

## Function Design

**Size:** Methods typically 10-80 lines; DSP process loops are sample-accurate and concise

**Parameters:**
- Prefer const references for large objects: `const juce::AudioBuffer<float>&`
- Pass-by-value for primitives: `float freqHz`, `int samplesPerBlock`
- Atomic references for thread-safe state: `std::atomic<float>& gainReductionMeter`
- Output parameters via reference: `juce::AudioBuffer<float>& output`

**Return Values:**
- `bool` for success/failure (preset operations)
- `float` for meter values and DSP output
- Void for audio processing (in-place modifications to buffer references)
- No null pointer returns; use `std::optional<T>` for optional values (limited use)

**Example Function:**
```cpp
void processStereo(juce::AudioBuffer<float>& buffer,
                  float thresholdDB,
                  float ratio,
                  bool isBypassed,
                  std::atomic<float>& gainReductionMeter)
{
    const int numSamples = buffer.getNumSamples();
    if (numSamples == 0 || isBypassed)
        return;

    // ... DSP processing ...
    gainReductionMeter.store(smoothedGainReductionDB, std::memory_order_relaxed);
}
```

## Module Design

**Exports:**
- Each DSP class defined in single header (`.h` file with implementation inline or in matching `.cpp`)
- Public interface: Configuration methods, lifecycle (`prepare()`, `reset()`), processing (`process()`)
- No external factory functions; direct instantiation via constructor

**Barrel Files:**
- None; includes are direct to needed classes

**Class Structure:**
- Public section: Configuration + lifecycle + processing
- Private section: Implementation details + helper methods + state
- Macro: `JUCE_DECLARE_NON_COPYABLE_WITH_LEAK_DETECTOR(ClassName)` on all non-copyable classes

**Example Module:**
```cpp
// CrossoverFilter.h
class CrossoverFilter {
public:
    void prepare(const juce::dsp::ProcessSpec& spec);
    void reset();
    void process(const juce::AudioBuffer<float>& input,
                 juce::AudioBuffer<float>& lowBand,
                 juce::AudioBuffer<float>& highBand);
private:
    juce::dsp::LinkwitzRileyFilter<float> iirLowpass;
    void updateIIRFilters();
    JUCE_DECLARE_NON_COPYABLE_WITH_LEAK_DETECTOR(CrossoverFilter)
};
```

## Thread Safety

**Patterns:**
- Audio thread (RT): Reads non-copyable, calls `process()`
- UI thread: Reads atomic meters, writes parameters via APVTS
- Parameter changes: Applied in `processBlock()` before DSP (no locks)
- Meter updates: Written atomically from audio thread, read from UI with memory ordering

**Atomics:**
- `std::atomic<float>` for meter values: `inputLevelDB`, `outputLevelDB`, `limitIndicator`
- Memory ordering: `std::memory_order_relaxed` for meter writes, `std::memory_order_acquire` for mode reads
- No `mutex` in audio path; smooth parameter transitions used instead

**Type Declarations:**
- Member variables ordering: Resource owners first, then parameters, then state
- Example from `PluginEditor.h`:
  ```cpp
  // 1. Relays FIRST (no dependencies)
  std::unique_ptr<juce::WebSliderRelay> frequencyRelay;
  // 2. WebView SECOND (depends on relays)
  std::unique_ptr<juce::WebBrowserComponent> webView;
  // 3. Attachments LAST (depend on both relays and parameters)
  std::unique_ptr<juce::WebSliderParameterAttachment> frequencyAttachment;
  ```
