Add a new `verify context-compliance <phase>` command to gsd-tools.js that deterministically cross-references CONTEXT.md user decisions with PLAN.md tasks.

**Command signature:**
```
node gsd-tools.js verify context-compliance <phase-number>
```

**Implementation outline:**

1. **Find phase directory** using existing `findPhaseDir(phaseArg)` helper.

2. **Read CONTEXT.md** — look for `{phase_dir}/*-CONTEXT.md`. If no CONTEXT.md exists, return early:
   ```json
   { "compliant": true, "skipped": true, "reason": "No CONTEXT.md found — no user decisions to check" }
   ```

3. **Parse CONTEXT.md sections** using markdown heading detection:
   - `## Decisions` or `### Decisions` — extract each bullet point as a locked decision
   - `## Claude's Discretion` or `### Claude's Discretion` — extract each bullet as discretion area
   - `## Deferred Ideas` or `### Deferred Ideas` — extract each bullet as deferred item

   For each item, extract the full text content (everything after the `- ` prefix up to the next bullet or section).

4. **Read all PLAN.md files** — glob `{phase_dir}/*-PLAN.md`. For each plan:
   - Extract task names from `<name>` elements
   - Extract task actions from `<action>` elements
   - Extract must_haves.truths from frontmatter (using existing frontmatter parsing)
   - Combine into a searchable text corpus per plan

5. **Tokenize for keyword matching:**
   - For each decision/deferred item, extract meaningful keywords:
     - Split on whitespace and punctuation
     - Remove common stop words (the, a, an, is, are, be, to, for, of, in, on, with, and, or, but, not, this, that, it, as, by, from, at, was, will, can, should, would, use, using)
     - Lowercase all tokens
     - Keep tokens with 3+ characters
   - For each plan's task corpus, do the same tokenization

6. **Cross-reference decisions against tasks:**
   For each locked decision:
   - Extract keyword tokens from decision text
   - Search each plan's task corpus for keyword overlap
   - A decision is "covered" if at least 40% of its non-stop-word tokens appear in at least one task's name, action, or must_haves text
   - Record which tasks cover each decision (task name + plan file)

7. **Check for deferred idea violations:**
   For each deferred item:
   - Extract keyword tokens from deferred text
   - Search each plan's task corpus for keyword overlap
   - A deferred item is "violated" if 50% or more of its tokens appear in a task — meaning the plan is implementing something the user explicitly deferred
   - Record which tasks violate (task name + plan file)

8. **Check discretion coverage (soft check):**
   For each discretion area:
   - Extract keyword tokens
   - Check if any task touches the area (30% token overlap)
   - If no coverage, add as "info" level issue (not blocker — planner has discretion)

9. **Return structured JSON:**
   ```json
   {
     "compliant": true/false,
     "skipped": false,
     "decisions": [
       {
         "text": "Use card layout for plugin browser",
         "covered": true,
         "covering_tasks": ["Task 2: Create card-based plugin browser", "16-02-PLAN.md"]
       }
     ],
     "deferred_violations": [
       {
         "idea": "Search functionality",
         "violating_tasks": ["Task 3: Add search bar", "16-01-PLAN.md"]
       }
     ],
     "discretion": [
       {
         "area": "Color palette",
         "covered": true,
         "coverage_tasks": ["Task 1: Design UI theme"]
       }
     ],
     "issues": [
       {
         "type": "uncovered_decision",
         "severity": "warning",
         "text": "Decision 'Use card layout' has no implementing task"
       }
     ],
     "stats": {
       "decisions_total": 3,
       "decisions_covered": 2,
       "deferred_total": 1,
       "deferred_violations": 0,
       "discretion_total": 2,
       "discretion_covered": 2
     }
   }
   ```

   `compliant` is `false` if any decision is uncovered OR any deferred item is violated.

**Implementation details:**

- Add the command handler in the verify command dispatch section of gsd-tools.js (near existing verify handlers around line ~2000+)
- Use existing `findPhaseDir()`, `readFrontmatter()`, and file reading helpers
- The tokenizer and keyword matching should be a local helper function within the command handler — no external dependencies
- Use `fs.readdirSync` + `path.join` for file discovery within the phase directory
- Parse XML task elements using regex (consistent with existing verify plan-structure approach)
- Handle edge cases: empty CONTEXT.md sections, plans with no tasks, single-word decisions

## Dimension 7: Context Compliance (if CONTEXT.md exists)

**Question:** Do plans honor user decisions from /gsd:discuss-phase?

**Only check if CONTEXT.md was provided in the verification context.**

**Step 7a: Deterministic pre-check (CLI)**

- For each uncovered decision: create a `context_compliance` issue with severity `blocker`
- For each deferred violation: create a `context_compliance` issue with severity `blocker`

Report CLI findings immediately — these are deterministic and high-confidence.

**Step 7b: Semantic analysis (agent judgment)**

The CLI uses keyword matching and may miss nuanced coverage. After CLI results, perform agent-level semantic analysis:

1. Review any decisions the CLI marked as "uncovered" — check if they are actually addressed implicitly by task actions (the CLI may miss synonyms or indirect implementation)
2. Review any deferred violations — check if the task is genuinely implementing the deferred idea or if it's a false positive from keyword overlap
3. Check for CONTRADICTIONS that keyword matching cannot detect — e.g., user said "cards layout" but plan implements "table layout" (both mention "layout" so CLI sees coverage, but the approach contradicts)

If agent analysis overrides a CLI finding:
- Demote CLI blocker to info with explanation: "CLI flagged as uncovered, but Task X implicitly addresses this via [explanation]"

If agent finds additional issues CLI missed:
- Add as new issues with `detected_by: "agent"` annotation
```
