## Core Components

### 1. Wavetable Engine (WavetableOscillator)

- **JUCE Class:** Custom implementation (no built-in JUCE wavetable oscillator)
- **Purpose:** Play bandlimited wavetable frames with position morphing between frames, phase accumulation, and anti-aliased output
- **Parameters Affected:** `oscATable`, `oscAPos`, `oscALevel`, `oscAPan`, `oscACoarse`, `oscAFine`, `oscAPhase`, `oscAUnison`, `oscADetune`, `oscAWidth` (and identical B-set)
- **Configuration:**
  - Wavetable size: 2048 samples per frame
  - Maximum frames per table: 256
  - Interpolation between samples within a frame: Linear (with bandlimited mipmap tables)
  - Interpolation between frames: Linear crossfade (morph via position parameter)
  - Anti-aliasing: Mipmap approach -- pre-generate bandlimited copies at multiple octave levels
  - Phase accumulator: 64-bit double precision, free-running or reset on note-on

**Mipmap Anti-Aliasing Strategy:**

The standard professional approach used by Serum, Vital, and other wavetable synthesizers:

1. At wavetable load time, for each frame:
   - Take FFT of 2048-sample frame
   - For each octave level (approximately 10 levels for MIDI range 0-127):
     - Zero out harmonics above Nyquist for that pitch
     - Take IFFT to generate bandlimited version
   - Store all mipmap levels (10 levels x 2048 samples per frame per table)
2. At playback time:
   - Select mipmap level based on current playback frequency
   - Interpolate between two adjacent mipmap levels for smooth transitions
   - Read samples from selected mipmap with linear interpolation

**Memory per table:** ~10 levels x 256 frames x 2048 samples x 8 bytes (double) = ~40 MB per table. This is significant -- will need lazy loading strategy (only load active tables, not all 100+).

**Optimization:** Store mipmap data as float (4 bytes), convert to double only during playback. Reduces memory to ~20 MB per table.

### 2. Sub Oscillator (SubOscillator)

- **JUCE Class:** Custom implementation (polyBLEP for anti-aliased classic waveforms)
- **Purpose:** Generate basic waveform shapes at sub-octave frequencies
- **Parameters Affected:** `subShape`, `subOctave`, `subLevel`
- **Configuration:**
  - Shapes: Sine (no aliasing), Triangle (polyBLEP), Saw (polyBLEP), Square (polyBLEP)
  - Octave: -2, -1, 0 relative to voice fundamental
  - Output bypasses filters, routes directly to voice output
  - Phase accumulator: 64-bit double, free-running

**polyBLEP anti-aliasing:**
- Polynomial Band-Limited step function applied at discontinuities
- Near-zero computational cost (only 2 sample correction at each discontinuity)
- Sufficient quality for sub oscillator (low frequencies have fewer aliasing issues)

### 3. Noise Generator (NoiseGenerator)

- **JUCE Class:** Custom implementation (simple RNG-based)
- **Purpose:** Generate various noise types for textural layering
- **Parameters Affected:** `noiseType`, `noiseLevel`
- **Configuration:**
  - White noise: Uniform random using `juce::Random`
  - Pink noise: Voss-McCartney algorithm (sum of octave-band white noise)
  - Brown noise: Integrated white noise with leaky integrator
  - Digital noise: Bit-reduced white noise (sample-and-hold at lower rate)
  - Vinyl noise: Filtered white noise with occasional crackle impulses
  - Wind noise: Heavily lowpass-filtered brown noise with slow modulation
  - Routable to filter chain or direct output (configurable per voice)

### 4. Dual State Variable Filters (SVFFilter)

- **JUCE Class:** `juce::dsp::StateVariableTPTFilter<double>` (from `juce_dsp` module)
- **Purpose:** Dual multi-mode filters with serial/parallel routing for timbral shaping
- **Parameters Affected:** `filtAType`, `filtACutoff`, `filtARes`, `filtADrive`, `filtAKeyTrack`, `filtBType`, `filtBCutoff`, `filtBRes`, `filtBDrive`, `filtBKeyTrack`, `filtRouting`
- **Configuration:**
  - Filter A and B each use `StateVariableTPTFilter<double>`
  - Types: LP12 (single SVF lowpass), LP24 (two cascaded SVF lowpass), HP12, HP24, BP12, BP24, Notch
  - Cutoff: 20 Hz to 20 kHz (exponential skew for frequency-domain control)
  - Resonance: 0.0 to 1.0 mapped to SVF Q factor (0.707 to self-oscillating ~20.0)
  - Drive: Pre-filter soft-clip saturation (`tanh(drive * input)`)
  - Key tracking: Cutoff offset = keyTrack * (midiNote - 60) * semitones-to-Hz
  - Routing: Serial (A->B), Parallel (A+B mixed)

**Implementation detail for 24dB slopes:**
- LP24/HP24/BP24: Two cascaded `StateVariableTPTFilter` instances per filter
- Each configured identically, processing in series
- Resonance applied to first stage only (prevents excessive resonance buildup)

**JUCE 8 gotcha (from juce8-critical-patterns.md):**
- `StateVariableTPTFilter` only supports LP/BP/HP types natively
- Notch: Compute as LP + HP (sum lowpass and highpass outputs from same SVF state)
- Drive: Apply `tanh()` waveshaping BEFORE filter input (pre-filter saturation)

### 5. ADSR Envelopes (ADSREnvelope)

- **JUCE Class:** `juce::ADSR` (from `juce_audio_basics` module)
- **Purpose:** Amplitude and filter cutoff modulation per voice
- **Parameters Affected:** `ampAttack`, `ampDecay`, `ampSustain`, `ampRelease`, `filtAttack`, `filtDecay`, `filtSustain`, `filtRelease`, `filtEnvDepth`
- **Configuration:**
  - Amplitude envelope: Applied to voice output after filters
  - Filter envelope: Modulates filter cutoff (depth from -1.0 to +1.0)
  - Attack: 0.001 to 10.0 seconds
  - Decay: 0.001 to 10.0 seconds
  - Sustain: 0.0 to 1.0
  - Release: 0.001 to 20.0 seconds
  - `juce::ADSR` handles sample-rate-independent timing

### 6. Unison Engine (UnisonEngine)

- **JUCE Class:** Custom implementation
- **Purpose:** Spread multiple detuned copies of each oscillator for thick, wide sound
- **Parameters Affected:** `oscAUnison`, `oscADetune`, `oscAWidth` (and B-set)
- **Configuration:**
  - Voice count: 1-8 per oscillator
  - Detune spread: Linear distribution around center frequency
    - For N voices: voice[i] detune = (i - (N-1)/2.0) / ((N-1)/2.0) * detuneAmount
    - Center voice (if odd count) at exact pitch
  - Stereo width: Pan positions spread across stereo field
    - voice[i] pan = (i - (N-1)/2.0) / ((N-1)/2.0) * widthAmount
  - Level normalization: Each voice amplitude = 1.0 / sqrt(N) to maintain consistent loudness
  - Random phase offset per unison voice (seeded per note for consistency)

### 7. Voice Manager (PrismVoice / PrismSynthesiser)

- **JUCE Class:** `juce::Synthesiser` + `juce::SynthesiserVoice` (from `juce_audio_basics`)
- **Purpose:** Manage polyphonic voice allocation, stealing, and rendering
- **Parameters Affected:** `polyphony`, `glideMode`, `glideTime`, `pitchBendRange`
- **Configuration:**
  - Maximum polyphony: 16 voices
  - Voice stealing: Oldest-note-first (JUCE `Synthesiser` default behavior)
  - Glide: Exponential frequency interpolation over glideTime
  - Pitch bend: Applied per-voice via TuningEngine pitch bend API
  - Each voice contains: 2x WavetableOscillator + SubOscillator + NoiseGenerator + 2x SVFFilter + 2x ADSR + UnisonEngine

**Per-voice architecture (PrismVoice extends juce::SynthesiserVoice):**
```
[Osc A (with unison)] --\
                          +--> [Osc Mix] --> [Filter A] --> [Filter B*] --> [Amp Env] --> Voice Out
[Osc B (with unison)] --/                                                                   |
[Noise] --(if routed to filter)--> [Filter input]                                           |
[Sub] -----------------------------------------------------------------> [Amp Env] --> Voice Out
                                                                          (direct path)
```
*Filter B is in serial path; in parallel mode, both filter outputs are summed.

**Why juce::Synthesiser instead of custom voice manager:**
- O-Lyrica (same catalog) uses `juce::Synthesiser` successfully with 16 voices
- Handles MIDI routing, voice allocation, pitch wheel, CC messages
- `renderNextBlock()` provides sample-accurate MIDI event timing
- Voice stealing is built-in (oldest note priority)
- Proven pattern in this codebase

### 8. Effects Chain (Global, post-voice)

#### 8a. Reverb
- **JUCE Class:** `juce::dsp::Reverb` (from `juce_dsp`)
- **Parameters:** `reverbSize`, `reverbDamp`, `reverbPredelay`, `reverbMix`
- **Implementation:** Use `juce::dsp::Reverb` with `juce::Reverb::Parameters`
- Pre-delay: Implemented with `juce::dsp::DelayLine<double>` before reverb input
- Dry/wet mix via `juce::dsp::DryWetMixer<double>`

#### 8b. Delay
- **JUCE Class:** `juce::dsp::DelayLine<double, juce::dsp::DelayLineInterpolationTypes::Lagrange3rd>` (from `juce_dsp`)
- **Parameters:** `delayTime`, `delayFeedback`, `delaySync`, `delayMode`, `delayMix`
- **Implementation:**
  - Free mode: Direct time in seconds
  - Sync mode: Quantized to BPM divisions (requires host tempo from `playHead`)
  - Ping-pong: Alternate feedback between L and R channels
  - LP filter on feedback path: `juce::dsp::StateVariableTPTFilter<double>` at ~8 kHz
  - Dry/wet via `juce::dsp::DryWetMixer<double>`

#### 8c. Chorus
- **JUCE Class:** `juce::dsp::Chorus<double>` (from `juce_dsp`)
- **Parameters:** `chorusRate`, `chorusDepth`, `chorusMix`
- **Implementation:** Direct use of JUCE Chorus widget
- Centre delay: 7ms (classic chorus)
- Feedback: 0 (clean chorus, no flanger)
- Dry/wet handled by JUCE Chorus internally

#### 8d. Distortion
- **JUCE Class:** Custom implementation (waveshaping functions)
- **Parameters:** `distType`, `distDrive`, `distMix`
- **Implementation:**
  - Soft clip: `tanh(drive * input)`
  - Hard clip: `max(-1, min(1, drive * input))`
  - Tube: Asymmetric waveshaping `(1 + k*x) / (1 + k*|x|)` where k = drive
  - Fold: `sin(drive * input * PI)` for wavefolder effect
  - Dry/wet via `juce::dsp::DryWetMixer<double>`
  - 2x oversampling for distortion only (prevents aliasing from nonlinear processing)

#### 8e. 3-Band EQ
- **JUCE Class:** `juce::dsp::IIR::Filter<double>` (from `juce_dsp`)
- **Parameters:** `eqLowGain`, `eqMidGain`, `eqMidFreq`, `eqHighGain`
- **Implementation:**
  - Low shelf: Fixed at 200 Hz, variable gain (-12 to +12 dB)
  - Mid peak: Variable frequency (200-8000 Hz), variable gain, Q=1.0
  - High shelf: Fixed at 8000 Hz, variable gain (-12 to +12 dB)
  - Coefficients via `juce::dsp::IIR::Coefficients<double>::makeLowShelf()`, `makePeakFilter()`, `makeHighShelf()`

### 9. Microtonal Engine (TuningEngine)

- **JUCE Class:** Custom (from `modules/tuning/scala-tuning-engine` v2.1.0)
- **Purpose:** Convert MIDI notes to frequencies using any tuning system
- **Parameters Affected:** `tuningPreset`, `tonic`, `masterTune`, `octaveStretch`, `pitchBendRange`, `glideMode`, `glideTime`
- **Configuration:**
  - Direct integration via `tuningEngine.getFrequency(midiNoteNumber)` in voice `startNote()`
  - Lock-free 128-note pre-computed frequency table (atomic reads from audio thread)
  - 24+ factory tunings via `EmbeddedTunings` class
  - Scala/KBM file import via native functions
  - Scale generators (EDO, harmonic series, rank-2 temperament)
  - Tonic selection with proper anchor-point shifting
  - Octave stretch for inharmonicity control
  - Per-note pitch bend via `tuningEngine.setPitchBend()`

**Integration pattern (proven in O-Lyrica/O-Bells):**
```cpp
// In PrismVoice::startNote()
double freq = tuningEngine->getFrequency(midiNoteNumber);
// Apply coarse/fine tuning
freq *= std::pow(2.0, (coarseSemitones + fineCents / 100.0) / 12.0);
// Set oscillator playback speed
double phaseIncrement = freq / sampleRate;
```

### 10. Wavetable Storage and Loading (WavetableManager)

- **JUCE Class:** Custom implementation using `juce::AudioFormatManager`, `juce::AudioFormatReader` (from `juce_audio_formats`)
- **Purpose:** Load, store, and manage wavetable data including factory tables and user imports
- **Parameters Affected:** `oscATable`, `oscBTable`
- **Configuration:**
  - Factory wavetables: Embedded as binary data or loaded from plugin bundle
  - User import: WAV/AIFF file import, auto-split into 2048-sample frames
  - Mipmap generation: On load, generate bandlimited versions for all octave levels
  - Thread safety: Loading on background thread, atomic pointer swap for audio thread access
  - Memory management: Only active tables + small cache loaded in memory

## Processing Chain

```
                              PER VOICE (x16 max)
    ============================================================

    MIDI Note On (+ velocity)
         |
         v
    [TuningEngine] --> frequency
         |
         v
    [Osc A (WavetableOsc)]    [Osc B (WavetableOsc)]
    [  + Unison Engine   ]    [  + Unison Engine   ]
    [  + Coarse/Fine     ]    [  + Coarse/Fine     ]
    [  + Phase control   ]    [  + Phase control   ]
    [  + Pan/Level       ]    [  + Pan/Level       ]
         |                         |
         +-------+  oscMix  +------+
                 |          |
                 v          v
              [Oscillator Mixer] <-- oscMix parameter
                      |
    [Noise] --------->| (if routed to filter)
                      v
              [Drive A: tanh()] <-- filtADrive
                      |
              [Filter A (SVF)] <-- filtACutoff, filtARes, filtAKeyTrack
                      |           + [Filter Envelope] <-- filtEnvDepth
                      |
              -----ROUTING-----
              |               |
         [SERIAL]        [PARALLEL]
              |               |
        [Drive B]      [Drive B applied
              |         to osc mix too]
        [Filter B]     [Filter B]
              |               |
              +-------+-------+
                      |
              [Amp Envelope] <-- ampA/D/S/R
                      |
    [Sub Osc] ------->| (direct to output, with amp env)
                      |
              [Voice Output] (stereo, from pan + unison width)

    ============================================================
                         GLOBAL
    ============================================================

    [Sum of all voices]
         |
         v
    [Distortion] <-- distType, distDrive, distMix (with 2x oversampling)
         |
    [Chorus] <-- chorusRate, chorusDepth, chorusMix
         |
    [Delay] <-- delayTime, delayFeedback, delaySync, delayMode, delayMix
         |
    [Reverb] <-- reverbSize, reverbDamp, reverbPredelay, reverbMix
         |
    [3-Band EQ] <-- eqLowGain, eqMidGain, eqMidFreq, eqHighGain
         |
    [Master Volume] <-- masterVol
         |
         v
    [Stereo Output]
```

**Routing notes:**
- Osc A and B are mixed according to `oscMix` parameter (0.0 = A only, 1.0 = B only, 0.5 = equal)
- Sub oscillator bypasses filters entirely and is summed at voice output
- Noise generator can be routed either to filter input or direct to output (design choice: route to filter for v1.0)
- Filter routing is per-voice (serial: A->B, parallel: A+B summed)
- Effects chain is global (post voice-sum), fixed order for v1.0
- Effects are always active but mix=0.0 effectively bypasses (dry signal passthrough via DryWetMixer)

## System Architecture

### File I/O System

**File types supported:** .wav, .aiff (wavetable import), .scl (Scala scale), .kbm (keyboard mapping)

**Loading strategy:**
- Factory wavetables: Pre-generated and embedded in BinaryData, loaded at initialization
- User wavetable import: Background thread loading via `juce::Thread::launch()`
- Scala/KBM files: Message thread loading via file dialog (small files, instant)

**JUCE classes:**
- `juce::AudioFormatManager` -- Format detection for WAV/AIFF
- `juce::AudioFormatReader` -- Read audio file into memory buffer
- `juce::File` -- File path management for Scala/KBM
- `juce::BinaryData` -- Embedded factory wavetable data

**Thread safety:**
- Wavetable loading on background thread
- Audio thread accesses loaded wavetable via atomic pointer swap
- Scala/KBM loading is near-instant (text files), done on message thread
- TuningEngine handles thread safety internally (atomic frequency table)

**Error handling:**
- Invalid audio file: Show error in UI, keep current wavetable
- Non-2048-multiple sample count: Resample to nearest multiple of 2048
- Missing Scala file on restore: Revert to 12-TET, show warning
- Invalid Scala syntax: Show parse error, keep current tuning

### MIDI Routing

**Input handling:** Single MIDI input, responds to all channels (omni mode)

**Note mapping:**
- MIDI note number -> `TuningEngine::getFrequency(note)` -> oscillator frequency
- Velocity -> amplitude scaling (0-127 mapped to 0.0-1.0 via velocity curve)
- Pitch wheel -> `TuningEngine::setPitchBend()` with configurable range (1-48 semitones)
- CC1 (Mod wheel) -> reserved for v2.0 modulation matrix
- CC64 (Sustain pedal) -> handled by `juce::Synthesiser` automatically

**JUCE classes:**
- `juce::MidiBuffer` -- MIDI event iteration in processBlock
- `juce::MidiMessage` -- Note on/off, pitch wheel, CC parsing
- `juce::Synthesiser` -- Handles MIDI -> voice routing automatically

**Processing:**
- JUCE Synthesiser handles MIDI event dispatch internally
- `startNote()` receives MIDI note, velocity, pitch wheel position
- `pitchWheelMoved()` updates TuningEngine pitch bend in real-time
- Voice stealing handled by Synthesiser (oldest note priority)

### State Persistence

**What state is saved:**
- APVTS parameters: All 60+ parameters (automatic via APVTS)
- Custom state:
  - Current wavetable selection per oscillator (table index or file path)
  - Active tuning state (intervals, mode, preset, Scala file content)
  - Tonic selection
  - Master tune
  - Octave stretch

**Serialization format:**
- APVTS parameters: Automatic via `AudioProcessorValueTreeState`
- Custom state: ValueTree with structure:
  ```xml
  <PrismState>
    <Oscillators>
      <OscA tableIndex="0" tablePath=""/>
      <OscB tableIndex="0" tablePath=""/>
    </Oscillators>
    <Tuning mode="0" preset="0" intervals="0,100,200,..."
            scaleName="12-TET" tonic="0"/>
  </PrismState>
  ```

**JUCE classes:**
- `juce::AudioProcessorValueTreeState` -- Parameter persistence (automatic)
- `juce::ValueTree` -- Custom state tree for non-parameter data
- `juce::MemoryBlock` -- Binary serialization

**Restore behavior:**
- Missing wavetable file: Revert to factory default, show warning
- Invalid tuning data: Revert to 12-TET
- Version migration: Check version attribute, apply defaults for new parameters

## Algorithm Details

### Wavetable Mipmap Generation

**Algorithm:** FFT-based harmonic removal for bandlimited table generation

**Implementation notes:**
1. For each frame in the wavetable:
   - Compute FFT of 2048 samples using `juce::dsp::FFT` (size 2048)
   - For each mipmap level L (0 = full bandwidth, 9 = lowest bandwidth):
     - Max harmonic = floor(sampleRate / (2 * fundamentalFrequency_at_level))
     - Zero all FFT bins above max harmonic
     - Compute IFFT to generate bandlimited frame
     - Store in mipmap[level][frame][sample]
2. Mipmap levels spaced at octave intervals:
   - Level 0: Full harmonics (for lowest octave MIDI 0-12)
   - Level 1: Harmonics up to Nyquist/2 (MIDI 12-24)
   - ...
   - Level 9: Fundamental only (MIDI 108-127)

**JUCE class:** `juce::dsp::FFT` from `juce_dsp` module

**Edge cases:**
- Empty wavetable: Generate silence (all zeros)
- Single-frame wavetable: No frame interpolation needed
- Very high notes (above level 9): Use level 9 (essentially sine wave)

### Wavetable Playback

**Algorithm:** Phase-accumulator based playback with mipmap level selection and frame interpolation

**Implementation notes:**
```
For each sample:
  1. phaseAccumulator += phaseIncrement  (phaseIncrement = frequency / sampleRate)
  2. if phaseAccumulator >= 1.0: phaseAccumulator -= 1.0
  3. sampleIndex = phaseAccumulator * 2048.0
  4. mipmapLevel = calculateMipmapLevel(frequency, sampleRate)
  5. frame0 = floor(position * (numFrames - 1))
  6. frame1 = frame0 + 1
  7. frameFrac = position * (numFrames - 1) - frame0
  8. sample0 = linearInterpolate(mipmap[mipmapLevel][frame0], sampleIndex)
  9. sample1 = linearInterpolate(mipmap[mipmapLevel][frame1], sampleIndex)
  10. output = sample0 + frameFrac * (sample1 - sample0)  // frame crossfade
```

**Mipmap level selection:**
```
mipmapLevel = max(0, min(9, floor(log2(frequency / baseFrequency))))
```
Where baseFrequency is the frequency at which the table has full harmonics (~8 Hz for level 0).

For smooth transitions between mipmap levels, interpolate between two adjacent levels:
```
levelFrac = log2(frequency / baseFrequency) - floor(log2(frequency / baseFrequency))
output = mipmap[level] * (1 - levelFrac) + mipmap[level+1] * levelFrac
```

### polyBLEP Sub Oscillator

**Algorithm:** Polynomial Band-Limited step function for alias-free classic waveforms

**Implementation notes:**
- polyBLEP correction applied at waveform discontinuities
- Correction function:
  ```
  polyBLEP(t, dt):
    if t < dt:
      t /= dt
      return t + t - t * t - 1.0
    elif t > 1.0 - dt:
      t = (t - 1.0) / dt
      return t * t + t + t + 1.0
    return 0.0
  ```
- Where t = phase (0-1), dt = phaseIncrement
- Applied differently per shape:
  - Saw: Apply to falling edge at phase=0
  - Square: Apply to rising edge at phase=0 and falling edge at phase=pulseWidth
  - Triangle: Integrate polyBLEP square wave (leaky integrator)
  - Sine: No correction needed (naturally bandlimited)

### SVF Filter with Drive and Key Tracking

**Algorithm:** Vadim Zavalishin TPT State Variable Filter with pre-filter saturation

**Implementation notes:**
- Use `juce::dsp::StateVariableTPTFilter<double>` for core filtering
- For 24dB slopes: Cascade two identical SVF instances
- Cutoff modulation from filter envelope:
  ```
  modulatedCutoff = baseCutoff * pow(2.0, filterEnvValue * envDepth * 4.0)
  // envDepth range -1.0 to 1.0, scaled to +-4 octaves
  ```
- Key tracking:
  ```
  keyTrackOffset = keyTrackAmount * (midiNote - 60) // semitones from middle C
  modulatedCutoff *= pow(2.0, keyTrackOffset / 12.0)
  ```
- Drive (pre-filter saturation):
  ```
  drivenInput = tanh(input * (1.0 + drive * 9.0))
  ```
- Resonance mapping:
  ```
  // JUCE SVF resonance: lower values = higher Q
  svfResonance = 1.0 / (1.0 + resonanceParam * 19.0)
  // At resonanceParam=0: Q=0.707 (flat), at 1.0: Q=20 (self-oscillating)
  ```
- Notch implementation:
  ```
  notchOutput = lowpassOutput + highpassOutput
  // Where LP and HP are from the same SVF state (no additional computation)
  ```

### Unison Detune Spread

**Algorithm:** Linear frequency spread with stereo panning

**Implementation notes:**
```
For N unison voices (1-8):
  centerIndex = (N - 1) / 2.0
  for i in 0..N-1:
    // Detune: Linear spread, symmetric around center
    normalizedPos = (i - centerIndex) / max(1, centerIndex)  // -1.0 to +1.0
    detuneRatio = pow(2.0, normalizedPos * detuneAmount * maxDetuneCents / 1200.0)
    voiceFreq = baseFreq * detuneRatio

    // Pan: Spread across stereo field
    voicePan = normalizedPos * widthAmount  // -1.0 to +1.0

    // Amplitude: Normalize for consistent loudness
    voiceGain = 1.0 / sqrt(N)

    // Phase: Random offset per voice (seeded)
    voicePhaseOffset = random(0.0, 1.0)  // set once at note-on
```

**maxDetuneCents:** 50 cents at detuneAmount=1.0 (Serum-like range)

### Glide/Portamento

**Algorithm:** Exponential frequency interpolation

**Implementation notes:**
```
// On note-on:
if glideMode == Always OR (glideMode == Legato AND previousNoteActive):
  targetFreq = newFrequency
  glideCoeff = exp(-1.0 / (glideTime * sampleRate))
else:
  currentFreq = newFrequency  // instant

// Per sample:
currentFreq = currentFreq * glideCoeff + targetFreq * (1.0 - glideCoeff)
```

### Noise Generation

**White noise:** `juce::Random::nextDouble() * 2.0 - 1.0`

**Pink noise (Voss-McCartney):**
```
// 8 octave bands, each updated at different rates
for each sample:
  counter++
  for band = 0 to 7:
    if (counter % (1 << band)) == 0:
      pinkBand[band] = random() * 2.0 - 1.0
  output = sum(pinkBand) / 8.0
```

**Brown noise:**
```
brownState += whiteNoise * 0.02
brownState *= 0.998  // leaky integrator to prevent DC drift
output = brownState
```

## Integration Points

### Feature Dependencies

- **TuningEngine -> WavetableOscillator:** Frequency from TuningEngine drives oscillator phase increment
- **ADSR (filter) -> SVFFilter:** Filter envelope modulates cutoff frequency each sample
- **ADSR (amp) -> Voice output:** Amplitude envelope shapes final voice output
- **UnisonEngine -> WavetableOscillator:** Unison creates multiple oscillator instances per voice with different frequencies/phases
- **SVFFilter routing -> SVFFilter A/B:** Serial vs parallel routing changes signal flow topology
- **WavetableManager -> WavetableOscillator:** Loaded wavetable data referenced during playback
- **Effects chain -> Voice sum:** Effects process the summed output of all voices (global, not per-voice)

### Parameter Interactions

- **oscMix + oscALevel + oscBLevel:** Three parameters controlling oscillator balance; oscMix is crossfade, levels are individual gains
- **filtACutoff + filtEnvDepth + filtAKeyTrack:** Three sources modulating final cutoff -- base value + envelope + key tracking
- **oscAUnison + polyphony:** CPU impact is multiplicative: 16 voices x 8 unison x 2 oscillators = 256 oscillator instances worst case
- **reverbSize + reverbDamp:** Longer size with high damping creates short, dense reverb; long size with low damping creates infinite-feeling tails
- **delaySync + delayTime:** When sync is on, delayTime should snap to BPM divisions (the UI handles this, DSP receives final time value)
- **filtRouting + filtAType + filtBType:** Serial routing means filter B processes filter A's output (compound filtering); parallel means independent filtering summed

### Processing Order Requirements

**Per-voice processing order (REQUIRED):**

1. **Frequency calculation:** TuningEngine frequency + coarse + fine tuning + pitch bend + glide
2. **Oscillator rendering:** Osc A and Osc B generate samples at calculated frequencies (with unison)
3. **Oscillator mixing:** Apply oscMix crossfade between A and B, apply levels and panning
4. **Noise mixing:** Add noise to oscillator mix (if routed to filter)
5. **Filter processing:** Apply drive, then filter A, then filter B (or parallel)
   - Filter cutoff = base + envelope + key tracking (calculated per sample)
6. **Amplitude envelope:** Apply amp ADSR to filtered signal
7. **Sub oscillator:** Generate and add sub oscillator (with amp envelope) directly to output
8. **Voice output:** Stereo signal ready for voice summing

**Global processing order (REQUIRED):**

1. **Voice summing:** Sum all active voice outputs
2. **Distortion:** Apply distortion with 2x oversampling (first in chain to shape harmonics)
3. **Chorus:** Apply chorus (after distortion for richer modulation)
4. **Delay:** Apply delay (after chorus to include modulated signal)
5. **Reverb:** Apply reverb (last time-based effect, creates space)
6. **EQ:** Apply 3-band EQ (final tonal shaping)
7. **Master volume:** Apply master gain

**Why this order:**
- Distortion first: Creates harmonics that are then modulated/spaced by subsequent effects
- Reverb after delay: Prevents reverb tail from being further delayed (unnatural)
- EQ last: Final tonal correction after all processing

### Thread Boundaries

**Audio thread:**
- All DSP processing in `processBlock()` (via `juce::Synthesiser::renderNextBlock()`)
- Parameter reads via `APVTS::getRawParameterValue()->load()` (atomic)
- Wavetable data reads from pre-loaded buffers (no allocations)
- TuningEngine frequency reads via atomic frequency table

**Message thread:**
- UI parameter changes via APVTS (atomic writes)
- Wavetable selection changes (triggers background load)
- Tuning system changes via native WebView functions
- Scala/KBM file loading (via file dialog)
- Preset save/load

**Background thread:**
- Wavetable loading from disk (WAV/AIFF parsing)
- Mipmap generation (FFT processing)
- Completed wavetable delivered to audio thread via atomic pointer swap

**Communication:**
- APVTS parameters: Atomic reads (audio thread) / atomic writes (message thread)
- Wavetable data: `std::atomic<WavetableData*>` pointer swap after background load
- TuningEngine: Internal atomic frequency table (audio reads, message thread writes)
- No mutexes on audio thread (lock-free requirement)

## Implementation Risks

### Wavetable Mipmap Engine

**Complexity:** HIGH

**Risk Level:** HIGH

**Risk factors:**
1. FFT-based mipmap generation is computationally expensive at load time
2. Memory management for multiple mipmap levels per table (potentially 20MB+ per table)
3. Correct mipmap level selection during playback (artifacts if wrong level chosen)
4. Frame interpolation combined with mipmap interpolation adds complexity
5. No existing JUCE wavetable class (fully custom implementation required)

**Alternative approaches:**
1. **Runtime oversampling instead of mipmaps:**
   - Simpler implementation (just use `juce::dsp::Oversampling`)
   - Higher CPU cost per voice (2x or 4x processing)
   - No memory overhead for pre-computed tables
   - Quality: Comparable, but higher CPU

2. **Reduced mipmap levels (5 instead of 10):**
   - Less memory per table
   - Slightly more aliasing at intermediate frequencies
   - Acceptable tradeoff for v1.0

**Fallback architecture:**
- **Primary:** FFT-based mipmap with 10 octave levels
- **Fallback 1:** Reduced to 5 mipmap levels (less memory, slight quality reduction)
- **Fallback 2:** Runtime 2x oversampling (higher CPU, simpler implementation, no mipmap memory)
- **Fallback 3:** No anti-aliasing (unacceptable for release, but validates other systems)

**Mitigation strategy:**
1. Implement basic wavetable playback first (no anti-aliasing)
2. Add mipmap generation as second step
3. Profile memory usage early
4. Consider float storage for mipmaps (halves memory)
5. Reference: Surge synthesizer open-source implementation on GitHub

### Dual SVF Filter with Routing

**Complexity:** MEDIUM

**Risk Level:** LOW

**Risk factors:**
1. JUCE `StateVariableTPTFilter` only supports LP/BP/HP (need notch workaround)
2. Cascading two SVFs for 24dB requires careful resonance handling
3. Serial vs parallel routing requires conditional signal flow

**Alternative approaches:**
1. **Custom SVF implementation (Zavalishin):**
   - Full control over all outputs (LP/HP/BP/notch from single computation)
   - More code but architecturally cleaner
   - Slightly higher risk (custom DSP vs tested JUCE class)

**Fallback architecture:**
- Use JUCE `StateVariableTPTFilter` for all filter types except notch
- Notch: Sum LP and HP outputs (mathematically equivalent)
- If cascading causes resonance issues: Reduce max resonance for 24dB modes

**Mitigation strategy:**
1. Start with JUCE SVF for LP/HP/BP
2. Add notch as LP+HP sum
3. Add 24dB cascading
4. Test self-oscillation stability at high resonance

### Voice Management and CPU Budget

**Complexity:** HIGH

**Risk Level:** MEDIUM

**Risk factors:**
1. Worst case: 16 voices x 8 unison x 2 oscillators = 256 oscillator instances
2. Each voice also has 2 filters, 2 ADSRs, noise generator, sub oscillator
3. CPU budget: <25% at 16 voices (per NFR-02)
4. 64-bit double precision doubles memory bandwidth vs float

**Alternative approaches:**
1. **Voice limiting:** Cap at 8 voices when unison > 4
2. **Progressive quality:** Reduce mipmap interpolation quality at high voice counts
3. **Float processing for oscillators:** Use float internally, convert to double for filters

**Fallback architecture:**
- Reduce max polyphony dynamically based on unison count
- Implement "eco mode" that uses float precision for oscillators
- Allow user to choose polyphony limit

**Mitigation strategy:**
1. Benchmark single voice CPU early
2. Implement voice count limiting based on unison
3. Profile with worst-case settings (16 voices, 8 unison, both osc active)
4. Consider SIMD optimization for wavetable interpolation if needed

### Microtonal Integration

**Complexity:** LOW

**Risk Level:** LOW

**Risk factors:**
1. TuningEngine is proven code (used in O-Lyrica and O-Bells)
2. Integration pattern well-documented in scala-tuning-engine module v2.1.0
3. Only risk: Wavetable playback speed must be derived from TuningEngine frequency (not standard MIDI pitch)

**Alternative approaches:** None needed -- this is proven, reliable code.

**Mitigation strategy:**

## Architecture Decisions

### Decision 1: Mipmap Anti-Aliasing vs Runtime Oversampling

**Decision:** Use mipmap-based bandlimited wavetables (pre-compute at load time)

**Rationale:**
- Industry standard for professional wavetable synths (Serum, Vital, Surge)
- Zero additional CPU cost during playback (just table lookups)
- Scales linearly with voice count (no per-voice oversampling overhead)
- Critical for meeting <25% CPU budget at 16 voices with unison

**Alternatives considered:**
1. **Runtime 2x oversampling via `juce::dsp::Oversampling`:**
   - Why rejected: Doubles CPU per oscillator; with 256 potential oscillator instances, this is prohibitive
   - When to reconsider: If mipmap memory proves too large (>200MB total)

2. **No anti-aliasing:**
   - Why rejected: Unacceptable audio quality; aliasing artifacts audible on all but lowest notes
   - When to reconsider: Never (dealbreaker for professional synth)

**Tradeoffs accepted:**
- **Higher memory usage:** ~20MB per loaded table (float mipmaps) vs ~4MB without mipmaps
  - Acceptable: Only 2-3 tables loaded simultaneously; modern systems have 8+ GB RAM
- **Longer load time:** FFT processing at table load time (~100ms per table)
  - Acceptable: Loading happens on background thread; user perceives instant switch for factory tables (pre-computed)

### Decision 2: JUCE Synthesiser vs Custom Voice Allocator

**Decision:** Use `juce::Synthesiser` and `juce::SynthesiserVoice` base classes

**Rationale:**
- Proven pattern in O-Lyrica (16-voice polyphonic physical modeling synth)
- Handles MIDI routing, voice stealing, pitch wheel, sustain pedal automatically
- `renderNextBlock()` provides sample-accurate MIDI event timing
- Reduces implementation risk for voice management (JUCE handles edge cases)

**Alternatives considered:**
1. **Fully custom voice allocator:**
   - Why rejected: Voice management is complex (stealing, pedals, legato); no benefit over JUCE base class
   - When to reconsider: If `juce::Synthesiser` voice stealing behavior needs customization

**Tradeoffs accepted:**
- **Less control over voice stealing algorithm:** JUCE uses oldest-note priority
  - Acceptable: This is the most common behavior; matches Serum/Vital

### Decision 3: JUCE StateVariableTPTFilter vs Custom SVF

**Decision:** Use `juce::dsp::StateVariableTPTFilter<double>` from JUCE 8

**Rationale:**
- Zavalishin TPT design (same algorithm as custom implementation would use)
- Built into JUCE 8, well-tested, handles denormals
- `processSample()` method enables per-sample cutoff modulation (required for filter envelope)
- Notch achievable by summing LP + HP outputs

**Alternatives considered:**
1. **Custom Zavalishin SVF:**
   - Why rejected: Identical algorithm; extra implementation risk for no benefit
   - When to reconsider: If JUCE SVF lacks needed features (unlikely)

2. **Moog Ladder filter:**
   - Why rejected: Only provides lowpass; we need LP/HP/BP/Notch from single structure
   - When to reconsider: As additional filter type in v2.0

**Tradeoffs accepted:**
- **Limited to 12dB per SVF stage:** Need to cascade two for 24dB
  - Acceptable: Standard approach; cascading two SVFs is well-documented

### Decision 4: Double Precision Processing

**Decision:** Use 64-bit double precision for all internal processing

**Rationale:**
- Brief specifies 64-bit double precision (NFR-01)
- Prevents floating-point noise in filter feedback paths
- Important for accurate phase accumulation in wavetable playback
- JUCE `StateVariableTPTFilter<double>` supports double natively

**Tradeoffs accepted:**
- **2x memory bandwidth for audio buffers:** Double vs float
  - Acceptable: O-Prism is a studio instrument, not a mobile app; CPU has adequate bandwidth
- **Potential SIMD penalty:** SSE/AVX handles 2 doubles vs 4 floats per instruction
  - Mitigated: Wavetable data stored as float, converted to double during playback; main loop is memory-bound not compute-bound

### Decision 5: Effects Chain Order (Fixed for v1.0)

**Decision:** Fixed effects order: Distortion -> Chorus -> Delay -> Reverb -> EQ

**Rationale:**
- Distortion first creates harmonics processed by subsequent effects
- Time-based effects (chorus, delay, reverb) in increasing "size" order
- EQ last for final tonal correction
- v1.0 keeps it simple; v2.0 adds rearrangeable chain

**Alternatives considered:**
1. **Rearrangeable chain (like Serum):**
   - Why rejected: Significant UI/DSP complexity for v1.0
   - When to reconsider: v2.0 roadmap

## Special Considerations

### Thread Safety
- All parameter reads use atomic `getRawParameterValue()->load()` in audio thread
- Filter coefficient updates happen per-sample in audio thread (no allocations)
- Wavetable data accessed via atomic pointer (swapped after background load)
- TuningEngine uses atomic frequency table (128 atomic doubles)
- Voice allocation handled by `juce::Synthesiser` (thread-safe by design)
- No mutexes or locks on audio thread

### Performance
- **Wavetable oscillator:** ~2% CPU per voice per oscillator (table lookup + interpolation)
- **Unison (8 voices):** ~16% CPU per oscillator at max unison
- **SVF filter (per voice):** ~0.5% CPU per filter
- **Effects (global):** ~5% total (reverb dominant)
- **Worst case estimate:** 16 voices x (2 osc + unison overhead + 2 filters + 2 ADSRs) + effects = ~50% single core at 48kHz
- **Typical case:** 8 voices x (1 osc + 2 unison + 1 filter) + effects = ~15% single core
- **Optimization path:** SIMD for wavetable interpolation, float storage for mipmap data

### Denormal Protection
- Use `juce::ScopedNoDenormals` at top of `processBlock()`
- JUCE DSP components (SVF, Reverb, Delay, Chorus) handle denormals internally
- Custom oscillators use phase wrapping (0.0-1.0) avoiding denormals
- Brown noise uses leaky integrator (decays to zero, no denormals)

### Sample Rate Handling
- All DSP components reinitialized in `prepareToPlay()` with new sample rate
- Wavetable mipmap levels calculated relative to sample rate
- Filter cutoff prewarping handled by JUCE SVF internally
- ADSR timing recalculated on sample rate change
- Delay line buffer sized for maximum delay at maximum sample rate
- Phase increment: `frequency / sampleRate` (sample-rate-dependent)

### Latency
- Zero latency (no lookahead processing)
- Distortion 2x oversampling: Internal latency compensated within effect (DryWetMixer handles this)
- `setLatencySamples(0)` in `prepareToPlay()`
- Note: `getLatencySamples()` is NOT virtual in JUCE 8 (use `setLatencySamples()`)

## Research References

### Professional Plugins

1. **Xfer Serum**
   - Industry standard wavetable synth
   - 2048 samples per frame, 256 frames per table
   - Mipmap-based anti-aliasing with 2x oversampling
   - Dual multi-mode filters with routing options
   - Observation: Uses float precision internally for oscillators

2. **Vital (Matt Tytel)**
   - Open-source wavetable synth, modern architecture
   - Extremely low noise floor (sharp Nyquist cutoff)
   - SSE/SIMD optimizations for oscillator rendering
   - 3 oscillators with spectral warping
   - Observation: Bandlimited tables pre-calculated per octave

3. **Surge Synthesizer (open source)**
   - Wavetable + other synthesis modes
   - Well-documented open-source codebase on GitHub
   - Mipmap wavetable implementation with multiple interpolation modes
   - Reference for wavetable data structures and memory management

4. **Arturia Pigments**
   - Wavetable + VA + granular synthesis
   - Polished WebView-like UI at 1200+ pixel width
   - Dual filter with serial/parallel routing
   - Observation: Clean UI organization for 100+ parameters

5. **Kilohearts Phase Plant**
   - Modular routing architecture
   - Clean wavetable engine with minimal aliasing
   - Observation: Demonstrates effective routing visualization

### JUCE Documentation

- **`juce::dsp::StateVariableTPTFilter`:** TPT SVF with LP/BP/HP, per-sample processing, resonance control. Module: `juce_dsp`. Verified in JUCE 8.0.4 source.
- **`juce::Synthesiser` / `juce::SynthesiserVoice`:** Polyphonic voice management with MIDI routing, voice stealing, pitch wheel. Module: `juce_audio_basics`.
- **`juce::dsp::FFT`:** Fast Fourier Transform for mipmap generation. Module: `juce_dsp`.
- **`juce::dsp::Oversampling<double>`:** 2x/4x/8x/16x oversampling with FIR or IIR filters. Module: `juce_dsp`.
- **`juce::dsp::DelayLine<double>`:** Variable delay with Linear/Lagrange3rd/Thiran interpolation. Module: `juce_dsp`.
- **`juce::dsp::Reverb`:** Built-in reverb (Freeverb-based). Module: `juce_dsp`.
- **`juce::dsp::Chorus<double>`:** Chorus effect with rate/depth/mix. Module: `juce_dsp`.
- **`juce::dsp::DryWetMixer<double>`:** Latency-compensated dry/wet mixing. Module: `juce_dsp`.
- **`juce::dsp::IIR::Filter<double>`:** Biquad filter with coefficient helpers. Module: `juce_dsp`.
- **`juce::ADSR`:** Sample-rate-independent ADSR envelope. Module: `juce_audio_basics`.

- **Will Pirkle, "Designing Audio Effect Plugins in C++"** - Filter design patterns, effect implementations
- **KVR Audio DSP Forum** - Community discussion of interpolation methods and CPU optimization
- **Surge Synthesizer (GitHub)** - Open-source reference for wavetable engine implementation

## Notes

- The tuning engine is proven code from the shared `scala-tuning-engine` module v2.1.0; integration follows the documented checklist at `modules/tuning/scala-tuning-engine/snippets/INTEGRATION-CHECKLIST.md`
- O-Lyrica's `HarpSynthVoice` pattern (APVTS pointer passed to voice, tuning engine pointer shared) should be replicated for PrismVoice
- Factory wavetables should be generated/sourced before Stage 2 DSP implementation; placeholder single-cycle waveforms (saw, square, etc.) sufficient for initial development
- The 68 parameter count is the highest in the Ouaricon catalog; Stage 1 foundation needs careful APVTS layout organization
- WebView relay management for 68 parameters will need the shared `webview-relay-manager` module from `modules/core/`
- v1.0 scope explicitly excludes: modulation matrix, wavetable editor, preset browser, rearrangeable effects chain -- these are v2.0 features
- For distortion oversampling, use `juce::dsp::Oversampling<double>` with 2x and IIR half-band filter (lower latency than FIR)
