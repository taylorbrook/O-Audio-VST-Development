## Core Components

### 1. Gain Stage

- **JUCE Class:** `juce::dsp::Gain<float>` (from `juce_dsp` module)
- **Purpose:** Apply combined gain_offset + trim as a single linear gain multiplication with built-in smoothing
- **Parameters Affected:** `gain_offset`, `trim`
- **Configuration:**
  - Combined gain: `totalGain_dB = gain_offset + trim`
  - Linear gain: `juce::Decibels::decibelsToGain(totalGain_dB)`
  - Ramp duration: 20ms for click-free gain changes
  - `setGainDecibels()` called per-block from APVTS parameter values
  - Uses internal `SmoothedValue` for zipper-noise-free transitions

### 2. K-Weighting Pre-Filter (BS.1770 Stage 1)

- **JUCE Class:** `juce::dsp::IIR::Filter<double>` with custom coefficients (from `juce_dsp` module)
- **Purpose:** Model head-related transfer function -- high-shelf boost of ~+4 dB above 2 kHz
- **Parameters Affected:** None (fixed filter, recalculated only on sample rate change)
- **Configuration:**
  - Filter type: 2nd-order high-shelf (biquad)
  - ITU-R BS.1770-5 published coefficients at 48 kHz:
    - b0 = 1.53512485958697, b1 = -2.69169618940638, b2 = 1.19839281085285
    - a1 = -1.69065929318241, a2 = 0.73248077421585
  - For other sample rates: use bilinear transform to recalculate from analog prototype
  - Apply using `juce::dsp::IIR::Coefficients<double>` constructor with raw b/a coefficients
  - Process using `processSample()` per-sample within measurement accumulator
  - **Double precision** for measurement accuracy

### 3. K-Weighting RLB Filter (BS.1770 Stage 2)

- **JUCE Class:** `juce::dsp::IIR::Filter<double>` with custom coefficients (from `juce_dsp` module)
- **Purpose:** Revised Low-frequency B-weighting -- high-pass rolloff below ~100 Hz
- **Parameters Affected:** None (fixed filter, recalculated only on sample rate change)
- **Configuration:**
  - Filter type: 2nd-order high-pass (biquad)
  - ITU-R BS.1770-5 published coefficients at 48 kHz:
    - b0 = 1.0, b1 = -2.0, b2 = 1.0
    - a1 = -1.99004745483398, a2 = 0.99007225036621
  - For other sample rates: recalculate via bilinear transform
  - Cascaded after pre-filter (pre-filter -> RLB -> squared accumulation)
  - **Double precision** for measurement accuracy

### 4. LUFS Gating Block Accumulator

- **JUCE Class:** Custom implementation (no JUCE class for this)
- **Purpose:** Accumulate K-weighted power in 400ms overlapping blocks with 75% overlap (new block every 100ms) per EBU Tech 3341
- **Parameters Affected:** `measurement_mode` (only active when mode == LUFS)
- **Configuration:**
  - Block size: 400ms (sampleRate * 0.4 samples)
  - Hop size: 100ms (sampleRate * 0.1 samples) -- 75% overlap
  - Per-block loudness: `-0.691 + 10 * log10(sum_of_mean_squared_per_channel)`
  - Store all block loudness values in a `std::vector<double>` for gating calculation
  - Momentary LUFS: last 400ms block
  - Short-term LUFS: last 3s (sliding window over blocks)
  - Integrated LUFS: all blocks since Learn start, with dual-gate applied

### 5. EBU R128 Dual-Gate System

- **JUCE Class:** Custom implementation (no JUCE class for this)
- **Purpose:** Remove silence and unrepresentative quiet passages from integrated loudness calculation
- **Parameters Affected:** None (internal to measurement)
- **Configuration:**
  - **Absolute gate:** -70 LUFS threshold
    - Step 1: Calculate mean power across ALL blocks
    - Step 2: Discard blocks below -70 LUFS
  - **Relative gate:** -10 LU below absolute-gated mean
    - Step 3: Calculate mean of blocks surviving absolute gate
    - Step 4: Set relative threshold = absolute-gated mean - 10 LU
    - Step 5: Discard blocks below relative threshold
    - Step 6: Final integrated loudness = mean of surviving blocks
  - Only applied to integrated LUFS (NOT momentary or short-term)

### 6. True Peak Detector

- **JUCE Class:** `juce::dsp::Oversampling<float>` (from `juce_dsp` module) for 4x upsampling
- **Purpose:** Detect inter-sample peaks per ITU-R BS.1770-5 for ceiling safety check
- **Parameters Affected:** None (internal to measurement, used during Learn calculation)
- **Configuration:**
  - 4x oversampling factor (factor=2 in Oversampling constructor = 2^2 = 4x)
  - FIR equiripple filter type (`filterHalfBandFIREquiripple`) for accuracy
  - Process: upsample block -> find absolute max of upsampled signal -> convert to dBTP
  - Track running maximum true peak across entire Learn session
  - Used in gain calculation: `max_safe_gain = ceiling_dBTP - measured_true_peak_dBTP`
  - **Alternative approach:** Custom 4x FIR polyphase interpolation using BS.1770 published 48-tap coefficients (12 taps per phase). This avoids the overhead of full Oversampling class. Recommended as primary approach due to lower CPU and no latency.

### 7. RMS Meter

- **JUCE Class:** Custom implementation using `std::sqrt` and sample accumulation
- **Purpose:** Calculate flat (non-weighted) RMS level for display and optional RMS-based learn mode
- **Parameters Affected:** `measurement_mode` (active when mode == RMS), `meter_mode` (active when mode == RMS)
- **Configuration:**
  - Window: sliding window of configurable length (default 300ms for VU-compatible display, or full Learn duration for learn mode)
  - Formula: `RMS_dB = 20 * log10(sqrt(sum_of_squares / N))`
  - Per-channel calculation, then average for stereo
  - For learn mode (RMS): use full-session RMS (no gating)

### 8. VU Meter Ballistics

- **JUCE Class:** `juce::dsp::BallisticsFilter<float>` (from `juce_dsp` module)
- **Purpose:** Apply authentic VU meter response (300ms rise to 99%, 1-1.5% overshoot per ANSI C16.5)
- **Parameters Affected:** `meter_mode` (active when mode == VU)
- **Configuration:**
  - Attack time: ~300ms (adjustable to match ANSI spec)
  - Release time: ~300ms (VU meters have symmetric attack/release)
  - Level calculation type: `BallisticsFilterLevelCalculationType::RMS` (VU meters measure average)
  - Alternative implementation: 2nd-order IIR lowpass at 2.224 Hz, Q=0.6053 for exact ANSI ballistics with 1% overshoot
  - Input: rectified (absolute value) signal
  - Output: VU level in linear scale, convert to dB for display
  - Calibration: 0 VU = -18 dBFS (configurable via target_level mapping)

### 9. Peak Meter

- **JUCE Class:** Custom implementation (simple max-abs tracking with decay)
- **Purpose:** Display instantaneous peak levels with hold and decay
- **Parameters Affected:** `meter_mode` (active when mode == Peak)
- **Configuration:**
  - Peak detection: `std::abs(sample)` per channel, track max per block
  - Peak hold: 2 seconds (configurable)
  - Decay rate: -20 dB/s (smooth falloff after hold expires)
  - Convert to dBFS: `20 * log10(peakLevel)`
  - Track separately for input and output metering

### 10. Channel Utilities

- **JUCE Class:** Custom implementation (trivial sample-level operations)
- **Purpose:** Phase inversion, channel swap, mono sum, M/S encode/decode
- **Parameters Affected:** `phase_invert_l`, `phase_invert_r`, `channel_swap`, `mono_sum`, `ms_mode`
- **Configuration:**
  - **Phase invert:** `sample *= -1.0f` per channel when enabled
  - **Channel swap:** swap L/R buffer pointers (zero-copy when possible, or swap samples)
  - **Mono sum:** `mono = (L + R) * 0.5f; L = mono; R = mono`
  - **M/S encode:** `M = (L + R) * 0.5f; S = (L - R) * 0.5f; L = M; R = S`
  - **M/S decode:** `L = (M + S); R = (M - S)` (where M = left input, S = right input)
  - All operations are sample-level, zero latency, negligible CPU
  - Mutual exclusivity: mono_sum and ms_mode are mutually exclusive (ms_mode takes priority if both enabled)

## Processing Chain

```
Input (Stereo L/R)
  |
  v
[Phase Invert L/R] ---- phase_invert_l, phase_invert_r parameters
  |
  v
[Channel Swap] --------- channel_swap parameter
  |
  v
[M/S Encode] ----------- ms_mode parameter (if encode selected)
  |
  v
[Mono Sum] ------------- mono_sum parameter
  |
  v
[Input Metering] ------- Peak/RMS/VU/LUFS display (pre-gain)
  |
  v
[Learn Measurement] ---- K-weight filters -> gating block accumulator
  |                      (ONLY active during Learn mode)
  |                      Also tracks true peak (4x FIR polyphase)
  |
  v
[Apply Gain] ----------- gain_offset + trim -> juce::dsp::Gain
  |
  v
[Output Metering] ------ Peak/RMS/VU/LUFS display (post-gain)
  |
  v
Output (Stereo L/R)
```

**Routing notes:**
- Channel utilities (phase, swap, M/S, mono) are applied BEFORE measurement and gain
- Learn measurement reads the pre-gain signal so it measures true incoming level
- Input metering shows the signal after channel utilities but before gain
- Output metering shows the signal after gain application
- No feedback loops, no parallel processing paths, no sidechain
- Processing is strictly sequential and zero-latency

## Algorithm Details

### Gain Application

**Algorithm:** Linear gain multiplication with smoothing

**Implementation notes:**
- `totalGain_dB = gain_offset + trim`
- `linearGain = juce::Decibels::decibelsToGain(totalGain_dB)`
- Use `juce::dsp::Gain<float>::setGainDecibels(totalGain_dB)` per block
- Built-in SmoothedValue handles click-free transitions (20ms ramp)
- Process via `juce::dsp::Gain::process(ProcessContextReplacing)` on AudioBlock
- Total gain range: -46 dB to +46 dB (gain_offset + trim extremes)

### ITU-R BS.1770-5 K-Weighted LUFS Measurement

**Algorithm:** Two-stage IIR filtering (K-weighting) followed by gated power accumulation

**Implementation notes:**

**Stage 1 -- Pre-filter (head model high-shelf):**
- 2nd-order biquad IIR filter
- Coefficients at 48 kHz (from ITU-R BS.1770-5 Annex):
  ```
  b0 = 1.53512485958697
  b1 = -2.69169618940638
  b2 = 1.19839281085285
  a0 = 1.0
  a1 = -1.69065929318241
  a2 = 0.73248077421585
  ```
- For other sample rates: apply bilinear transform with frequency warping
- Reference analog prototype: high-shelf at ~1504 Hz with ~+3.999 dB gain

**Stage 2 -- RLB high-pass filter:**
- 2nd-order biquad IIR filter
- Coefficients at 48 kHz:
  ```
  b0 = 1.0
  b1 = -2.0
  b2 = 1.0
  a0 = 1.0
  a1 = -1.99004745483398
  a2 = 0.99007225036621
  ```
- For other sample rates: recalculate (high-pass at ~38 Hz)

**Power accumulation:**
- After K-weighting, square each sample and accumulate
- Block size: 400ms worth of samples
- Hop: every 100ms (75% overlap)
- Per-block loudness: `L_block = -0.691 + 10 * log10(1/N * sum(x_k^2))` summed across channels
- Channel weighting: 1.0 for L, R (stereo only -- no surround for this plugin)

**Gating (integrated measurement only):**
- Step 1: Compute loudness of each 400ms block
- Step 2: Absolute gate at -70 LUFS -- discard blocks below
- Step 3: Compute mean of remaining blocks
- Step 4: Relative gate at mean - 10 LU -- discard blocks below
- Step 5: Integrated LUFS = -0.691 + 10 * log10(mean_power_of_surviving_blocks)

**Momentary LUFS:** Loudness of the most recent 400ms block (no gating)
**Short-term LUFS:** Mean power of blocks within last 3 seconds (no gating)

### True Peak Detection

**Algorithm:** 4x polyphase FIR interpolation per ITU-R BS.1770-5

**Implementation notes:**
- Use the 48-tap FIR coefficients from BS.1770-5 (12 taps per phase, 4 phases)
- For each input sample, compute 4 interpolated sub-samples using the 4 phases
- Track absolute maximum across all sub-samples during Learn session
- Convert to dBTP: `truePeak_dBTP = 20 * log10(maxAbsValue)`
- Used in gain safety check: `max_safe_gain = ceiling_dBTP - measured_true_peak_dBTP`
- Default ceiling: -1.0 dBTP

**Alternative (fallback):** Use `juce::dsp::Oversampling<float>` with factor=2 (4x) and FIR equiripple. Simpler to implement but adds latency and higher CPU. Since we only need peak detection (not full processing), the polyphase FIR approach is more efficient.

### RMS Measurement

**Algorithm:** Root mean square of signal amplitude

**Implementation notes:**
- Accumulate `sum += sample * sample` across all samples
- `RMS = sqrt(sum / N)` where N = total sample count
- `RMS_dB = 20 * log10(RMS)`
- For stereo: average power across channels before sqrt
- For learn mode: accumulate over entire learn duration (no windowing)
- For display metering: use sliding window (300ms for VU-compatible, or configurable)

### VU Meter Ballistics

**Algorithm:** ANSI C16.5 standard volume indicator with 300ms rise time

**Implementation notes:**
- Use `juce::dsp::BallisticsFilter<float>` with:
  - Attack time: 300ms
  - Release time: 300ms (symmetric)
  - Level calculation: RMS mode
- Input signal: absolute value (rectified)
- Output: smoothed envelope level
- Calibration: 0 VU maps to -18 dBFS by default (adjustable via target_level)
- Display range: -20 VU to +3 VU (typical VU meter range)
- Overshoot: the BallisticsFilter may not produce exactly 1-1.5% overshoot per ANSI spec; acceptable for visual display purposes

### Channel Utilities

**Algorithm:** Direct sample manipulation

**Phase inversion:**
```
if (phase_invert_l) L_sample *= -1.0f;
if (phase_invert_r) R_sample *= -1.0f;
```

**Channel swap:**
```
if (channel_swap) std::swap(L_sample, R_sample);
```

**Mono sum:**
```
if (mono_sum) {
    float mono = (L_sample + R_sample) * 0.5f;
    L_sample = mono;
    R_sample = mono;
}
```

**M/S encode:**
```
if (ms_mode == Encode) {
    float mid = (L_sample + R_sample) * 0.5f;
    float side = (L_sample - R_sample) * 0.5f;
    L_sample = mid;   // L output = Mid
    R_sample = side;  // R output = Side
}
```

**M/S decode:**
```
if (ms_mode == Decode) {
    float left = L_sample + R_sample;   // L = Mid + Side
    float right = L_sample - R_sample;  // R = Mid - Side
    L_sample = left;
    R_sample = right;
}
```

### Learn Mode State Machine

**Algorithm:** UI-driven state machine controlling measurement lifecycle

**States:**
1. **Idle** -- No measurement active. Gain applied from stored gain_offset parameter.
2. **Learning** -- Accumulating K-weighted blocks. Metering display shows momentary/short-term/integrated LUFS, elapsed time, block count, confidence.
3. **Complete** -- Measurement finished, gain_offset calculated and applied.

**Transitions:**
- Idle -> Learning: User presses Learn button (UI sends atomic flag)
- Learning -> Idle: User presses Learn button again (stop and calculate)
- Learning -> Complete -> Idle: Automatic (calculate gain on stop, write to APVTS, return to Idle)

**Gain calculation on Learn stop:**
```
measured = integrated_LUFS;  // or RMS_dB if measurement_mode == RMS
gain_dB = target_level - measured;
gain_dB = clamp(gain_dB, -40.0, +40.0);  // clamp to parameter range

// True peak safety
max_safe_gain = -1.0 - true_peak_dBTP;  // ceiling at -1 dBTP
gain_dB = min(gain_dB, max_safe_gain);

// Write to APVTS parameter
apvts.getParameter("gain_offset")->setValueNotifyingHost(normalizedValue);
```

**Confidence indicator:**
- Low: < 5 seconds of audio, or < 50 gated blocks
- Medium: 5-15 seconds, 50-150 gated blocks
- High: > 15 seconds, > 150 gated blocks, AND integrated LUFS has stabilized (< 0.5 LU change in last 2 seconds)

**Thread safety:**
- `std::atomic<bool> learnActive` -- set by UI thread, read by audio thread
- Measurement accumulation happens on audio thread (lock-free)
- Results read by UI thread only after learn stops (single-producer/single-consumer)
- Meter values communicated via `std::atomic<float>` for display

## Integration Points

### Feature Dependencies

- K-weighting filters -> LUFS accumulator: Pre-filter and RLB must be applied before power accumulation
- LUFS accumulator -> Dual-gate system: Gates applied to accumulated block data on Learn stop
- True peak detector -> Gain calculation: True peak maximum used for safety clamp
- Channel utilities -> Learn measurement: Utilities applied before measurement so measurement reflects the processed signal
- Learn state machine -> APVTS gain_offset: Learn completion writes calculated gain to parameter
- Gain stage -> Output metering: Metering reads post-gain signal
- All metering -> UI display: Atomic float values polled by UI at display refresh rate

### Parameter Interactions

- `gain_offset` and `trim` are additive: total gain = gain_offset + trim. No interaction beyond summation.
- `measurement_mode` determines which algorithm the Learn mode uses (LUFS or RMS). Does NOT affect meter display mode.
- `meter_mode` only affects the display -- it does NOT affect Learn measurement algorithm.
- `mono_sum` and `ms_mode` are mutually exclusive in practice:
  - If both enabled, `ms_mode` takes priority (encode/decode operates on stereo pairs)
  - Mono sum after M/S encode would collapse mid and side to mono (rarely useful)
  - UI should discourage simultaneous activation but not strictly prevent it
- `phase_invert_l/r` affects measurement: inverting phase before measurement does not change LUFS/RMS values (power-based metrics are phase-independent)
- `channel_swap` before measurement: swaps which channel provides L vs R data, but for stereo LUFS with equal channel weighting, this has no effect on the result

### Processing Order Requirements

**Sequential processing order (REQUIRED):**

1. **Phase inversion:** Apply polarity flip to L and/or R channels
   - Must happen first (affects all downstream processing)

2. **Channel swap:** Swap L and R channel data
   - After phase invert (swap should swap the already-inverted channels)

3. **M/S encode/decode:** Convert between L/R and M/S domains
   - After channel swap (operates on final L/R assignment)

4. **Mono sum:** Sum to mono
   - After M/S (if both somehow active, mono sum operates on the M/S-encoded data)

5. **Input metering:** Read signal levels for input meter display
   - After all channel utilities (shows the signal as it enters the gain stage)

6. **Learn measurement:** K-weight filtering and power accumulation
   - After channel utilities, before gain (measures true incoming level)
   - Also runs true peak detection on the pre-gain signal

7. **Apply gain:** Multiply by gain_offset + trim
   - After measurement capture (measurement must see un-gained signal)

8. **Output metering:** Read signal levels for output meter display
   - After gain (shows the signal as it leaves the plugin)

**Why order matters:**
- Measurement before gain: prevents feedback loop where the plugin measures its own gain adjustment
- Channel utilities before measurement: measurement reflects the signal as the user has configured it
- Input/output metering flanking the gain stage: provides before/after comparison

### Thread Boundaries

**Audio thread:**
- All DSP processing (channel utilities, K-weight filtering, power accumulation, gain application)
- Parameter reads via `APVTS::getRawParameterValue()->load()` (atomic)
- Learn flag read via `std::atomic<bool>::load()` (lock-free)
- Meter level writes via `std::atomic<float>::store()` (lock-free)
- Sample-by-sample or block-level processing in processBlock()

**Message thread (UI):**
- Parameter updates from UI via APVTS (atomic writes)
- Learn button toggle: `learnActive.store(true/false)` (atomic write)
- Meter value reads: `meterLevel.load()` (atomic read, polled at ~30-60 Hz)
- Gain calculation on Learn stop: reads accumulated data, calculates result, writes to APVTS
  - Note: The gain calculation itself happens on the message thread AFTER the audio thread has stopped accumulating (learnActive set to false, then UI reads final accumulated values)
- Confidence indicator update
- Elapsed time display

**No background thread needed:**
- No file I/O
- No long-running operations
- All processing is real-time compatible
- Gain calculation on Learn stop is trivial (microseconds)

**Communication:**
- APVTS parameters: atomic reads (audio thread) / atomic writes (message thread)
- Learn active flag: `std::atomic<bool>` (UI writes, audio reads)
- Meter values: `std::atomic<float>` per meter per channel (audio writes, UI reads)
- Learn results: accumulated data protected by learn-active flag transition (audio stops writing when learn goes inactive, UI reads after transition)

## Implementation Risks

### K-Weighted LUFS Measurement

**Complexity:** MEDIUM

**Risk Level:** MEDIUM

**Risk factors:**
- BS.1770 filter coefficients are published only for 48 kHz; other sample rates require bilinear transform recalculation
- Dual-gate system involves iterating over all accumulated blocks twice (absolute gate, then relative gate)
- Overlapping 400ms blocks with 100ms hop require circular buffer management
- Double-precision arithmetic needed for accurate loudness values

**Alternative approaches:**
1. **libebur128 (C library, MIT license):** Pre-built EBU R128 implementation. Could be integrated as a dependency. Tradeoff: adds external dependency, but guarantees standards compliance.
2. **Simplified non-overlapping blocks:** Use 400ms non-overlapping blocks instead of 75% overlap. Tradeoff: less smooth momentary LUFS readings, but simpler implementation.

**Fallback architecture:**
- If custom K-weighting implementation proves inaccurate: integrate libebur128 as a fallback
- If bilinear transform coefficient calculation fails for edge sample rates: provide pre-calculated coefficients for common rates (44100, 48000, 88200, 96000)

**Mitigation strategy:**
- Validate against libebur128 output or known test signals (EBU test signals available)
- Start with 48 kHz coefficients, add sample-rate adaptation later
- Use double-precision throughout measurement path

### True Peak Detection

**Complexity:** MEDIUM

**Risk Level:** LOW

**Risk factors:**
- Polyphase FIR implementation requires understanding of multi-rate signal processing
- BS.1770 published FIR coefficients are specific to the standard's accuracy requirements
- Potential for off-by-one errors in polyphase indexing

**Alternative approaches:**
1. **juce::dsp::Oversampling:** Use JUCE's built-in oversampling class. Simpler but adds latency and higher CPU since it processes the entire signal, not just peak detection.
2. **Simple digital peak (no oversampling):** Just use `std::abs(sample)` max. Misses inter-sample peaks but is trivially simple. Acceptable as MVP.

**Fallback architecture:**
- Primary: Custom 4x polyphase FIR (most efficient, zero latency)
- Fallback 1: `juce::dsp::Oversampling` (more CPU, adds latency -- would need to only run during Learn)
- Fallback 2: Digital peak without oversampling (misses inter-sample peaks, note in UI)

**Mitigation strategy:**
- The polyphase FIR is well-documented with published coefficients
- Can validate by comparing against known true peak test signals
- Start with simple digital peak for MVP, add polyphase FIR in refinement

### VU Meter Ballistics

**Complexity:** LOW

**Risk Level:** LOW

**Risk factors:**
- `juce::dsp::BallisticsFilter` may not exactly match ANSI C16.5 overshoot specification (1-1.5%)
- VU meter calibration (0 VU = -18 dBFS) is a display mapping concern, not DSP

**Alternative approaches:**
1. **Custom 2nd-order IIR (2.224 Hz, Q=0.6053):** More accurate ANSI ballistics with correct overshoot. Slightly more implementation effort.
2. **Simple exponential smoothing:** One-pole filter with ~300ms time constant. Easiest but no overshoot (not truly ANSI-compliant).

**Fallback architecture:**
- Primary: `juce::dsp::BallisticsFilter` (simplest, close enough for visual display)
- Fallback: Custom 2nd-order IIR if visual accuracy is insufficient

**Mitigation strategy:**
- BallisticsFilter is battle-tested in JUCE -- low risk of bugs
- Visual accuracy is sufficient for a gain staging utility (not a dedicated VU meter plugin)

### Channel Utilities

**Complexity:** LOW

**Risk Level:** LOW

**Risk factors:**
- M/S encode/decode requires correct matrix math (risk of level errors if scaling factors wrong)
- Mutual exclusivity of mono_sum and ms_mode needs clear precedence rules

**Alternative approaches:** None needed -- these are trivially simple operations.

**Fallback architecture:** N/A -- no fallback needed for sample-level arithmetic.

**Mitigation strategy:**
- Test with known signals (pure L, pure R, mono, stereo pink noise)
- Verify M/S round-trip: encode then decode should yield original signal

### Learn Mode State Machine

**Complexity:** MEDIUM

**Risk Level:** LOW

**Risk factors:**
- Thread safety between UI toggle and audio accumulation
- Edge case: user starts Learn, switches measurement_mode mid-learn (should restart or ignore?)
- Edge case: very short Learn session (< 1 second) produces unreliable measurement

**Alternative approaches:** N/A -- state machine design is standard.

**Fallback architecture:** N/A.

**Mitigation strategy:**
- Use atomic flag for learn active state (proven pattern)
- If measurement_mode changes during Learn: ignore change, use mode that was active at Learn start
- Minimum Learn duration: display "Low confidence" warning for < 5 seconds

### Overall Project Risk

**Overall complexity:** MEDIUM
- K-weighted LUFS measurement is the most complex component but is well-documented with published coefficients
- All other components are LOW complexity
- No feedback loops, no FFT, no real-time pitch/frequency processing

**Highest risk component:** K-Weighted LUFS Measurement
- Represents ~50% of project implementation effort
- Most algorithmically complex (dual IIR filters + gating block system + dual-gate)
- Requires sample-rate-dependent coefficient calculation
- Validation requires test signals or reference implementation comparison

**Recommended approach:**
1. Start with channel utilities and gain stage (LOW risk, validates architecture)
2. Implement K-weighted measurement with hardcoded 48 kHz coefficients
3. Add sample-rate-adaptive coefficients
4. Implement metering display modes
5. Polish Learn mode UX (confidence, elapsed time)

## Architecture Decisions

### Decision 1: Custom LUFS Implementation vs. libebur128

**Decision:** Custom implementation using JUCE IIR filters with published BS.1770 coefficients

**Rationale:**
- No external dependency (keeps build simple)
- Full control over threading and memory allocation
- BS.1770 algorithm is well-documented with published coefficients
- Custom implementation integrates naturally with JUCE's audio processing model
- Learn mode only needs integrated LUFS (not full real-time LUFS display initially)

**Alternatives considered:**
1. **libebur128 (C library):** Pre-built, validated, MIT license. Rejected because: adds external dependency, requires CMake integration, may have threading assumptions incompatible with JUCE audio thread.
2. **JUCE built-in loudness meter:** JUCE does not have a built-in LUFS meter class. Not available.

**Tradeoffs accepted:**
- Must validate correctness manually against test signals
- Must handle sample-rate-dependent coefficient calculation ourselves
- Acceptable because: BS.1770 is a well-specified standard with published coefficients and test vectors

### Decision 2: True Peak via Custom Polyphase FIR vs. juce::dsp::Oversampling

**Decision:** Start with simple digital peak for MVP, implement polyphase FIR for v1.0

**Rationale:**
- Simple digital peak works for MVP (catches most peaks, misses inter-sample by ~0.5-1 dB)
- Custom polyphase FIR is more efficient than full Oversampling class (we only need peak detection, not full processing at 4x rate)
- Oversampling class adds unwanted latency to the entire signal path

**Alternatives considered:**
1. **juce::dsp::Oversampling<float>:** Easy to implement but processes entire signal at 4x rate (wasteful when we only need peak values). Also adds latency to the plugin, violating zero-latency requirement.

**Tradeoffs accepted:**
- MVP will slightly underestimate true peaks (by up to ~1 dB)
- Acceptable because: true peak is a safety check, not a precision measurement; -1 dBTP ceiling with ~1 dB error still provides adequate headroom

### Decision 3: Effect Plugin (Not Instrument)

**Decision:** Configure as audio effect (stereo input + stereo output)

**Rationale:**
- O-Gain is a utility that processes existing audio
- No MIDI input needed
- No sound generation

**Implications:**
- `IS_SYNTH FALSE` (or omitted) in CMakeLists.txt
- BusesProperties: `.withInput("Input", stereo, true).withOutput("Output", stereo, true)`
- Appears in effects category in DAW

### Decision 4: Learn Measurement on Pre-Gain Signal

**Decision:** Measure incoming signal BEFORE gain application

**Rationale:**
- Prevents feedback loop where the plugin measures its own gain adjustment
- Gives accurate reading of the true incoming level
- Standard practice in auto-gain plugins (HoRNet TheNormalizer, VU Meter MK4)

**Alternatives considered:**
1. **Post-gain measurement:** Would create a feedback loop -- measured level changes after gain is applied, leading to iterative re-measurement. Rejected.

**Tradeoffs accepted:**
- None -- this is unambiguously the correct approach

### Decision 5: Double Precision for Measurement, Single Precision for Processing

**Decision:** Use `double` for LUFS measurement path, `float` for gain/channel utilities

**Rationale:**
- LUFS calculation involves summing many small squared values (numerical precision matters)
- Power accumulation over 10-30 seconds can lose precision in float32
- Gain application and channel utilities are simple multiplications where float32 is adequate
- JUCE's IIR::Filter supports double template parameter

**Tradeoffs accepted:**
- Slightly higher CPU for measurement path (double vs float operations)
- Acceptable because: measurement only runs during Learn mode (not continuous)

## Special Considerations

### Thread Safety
- All parameter reads use atomic `getRawParameterValue()->load()`
- Learn active flag: `std::atomic<bool>` (lock-free)
- Meter values: `std::atomic<float>` per meter per channel (lock-free)
- Learn accumulator data: protected by learn-active flag transition (single-producer/single-consumer pattern)
- No mutexes on audio thread, no allocations on audio thread

### Performance
- **Channel utilities:** ~1% CPU (trivial sample-level ops)
- **Gain application:** ~1% CPU (single multiply per sample with smoothing)
- **K-weight measurement (during Learn):** ~5% CPU (two biquad filters per channel + accumulation)
- **True peak detection (during Learn):** ~3% CPU (polyphase FIR per sample)
- **Metering (continuous):** ~2% CPU (peak tracking + optional ballistics)
- **Total estimated:** ~5% single core idle, ~12% during Learn mode at 48 kHz
- **Designed for 40+ instances:** Plugin must be extremely lightweight when Learn is not active. Target: < 1% CPU per instance in normal operation.

### Denormal Protection
- Use `juce::ScopedNoDenormals` at top of `processBlock()`
- K-weight IIR filters can generate denormals during silence -- ScopedNoDenormals handles this
- BallisticsFilter has internal denormal snapping via `JUCE_DSP_ENABLE_SNAP_TO_ZERO`

### Sample Rate Handling
- K-weight filter coefficients must be recalculated in `prepareToPlay()` for each sample rate
- Published coefficients are for 48 kHz -- bilinear transform needed for other rates
- BallisticsFilter automatically adapts to sample rate via `prepare(ProcessSpec)`
- Gain ramp duration is time-based (20ms) and adapts via `prepare(ProcessSpec)`
- Gating block sizes (400ms, 100ms) are calculated in samples from sample rate in `prepareToPlay()`
- True peak FIR coefficients are sample-rate-independent (they interpolate between existing samples)

### Latency
- **Zero latency** -- no FFT, no lookahead, no oversampling in signal path
- True peak detection does NOT add latency (it's a measurement side-chain, not in the signal path)
- Report `setLatencySamples(0)` in `prepareToPlay()`
- This is a critical requirement: gain staging plugin must not add latency

## Notes

- K-weight filter coefficient recalculation for non-48kHz rates is the primary implementation challenge. Pre-calculate coefficients for common rates (44100, 48000, 88200, 96000, 176400, 192000) and store as lookup table for reliability.
- The 0.5f scaling factor in M/S encode (M = (L+R)*0.5, S = (L-R)*0.5) preserves unity gain through encode/decode round-trip. Some implementations omit the 0.5 scaling on encode and apply it on decode -- either convention works as long as it's consistent.
- `gain_offset` parameter should use a skew factor that provides finer resolution near 0 dB and coarser resolution at extremes. Consider `NormalisableRange` with center at 0 dB.
- For the MVP, consider implementing only LUFS measurement mode and adding RMS as a secondary option. The brief lists LUFS as "primary" and RMS as "secondary option."
- UI meter refresh rate should be throttled to 30-60 Hz to prevent UI thread starvation, especially when 40+ instances are running. Use a timer callback, not processBlock-driven updates.
- The plugin should work correctly in mono-in/stereo-out configurations that some DAWs use. Handle channel count in `isBusesLayoutSupported()`.
