# DSP Architecture: O-Bassoon

**CRITICAL CONTRACT:** This specification is immutable during Stages 1-4 implementation. Stage 1 Foundation builds the project shell against this spec. Stage 2 (DSP) implements this exact architecture.

**Generated by:** Stage 0 Research (research-planning-agent)
**Generated on:** 2026-04-27
**Referenced by:** Stage 1 (Foundation), Stage 2 (DSP), Stage 3 (GUI), Stage 4 (Validation)
**Purpose:** DSP specification for a modal-synthesis bassoon optimized for sustained microtonal long tones. Per-voice bank of damped resonators, no reed self-oscillation, no waveguide, no O-Reed dependency.

---

## Core Components

### 1. Voice Class

- **JUCE Class:** `juce::SynthesiserVoice` (custom subclass `BassoonVoice`)
- **Purpose:** Per-note voice owning a modal mode bank, excitation generator, ADSR envelope, vibrato LFO, and a `pendingTuningSource` pointer for VST3 Note Expression delta application
- **Parameters Affected:** All per-voice parameters (vibrato_*, breath, tone, attack_character, attack_time, release_time)
- **Configuration:**
  - One `BassoonVoice` instance per polyphony slot, all pre-allocated in `prepareToPlay()`
  - Holds raw pointer (non-owning) to APVTS, `Ouaricon::NoteExpression::PendingTuningTable`, and `TuningEngine`
  - Same ownership pattern as O-Lyrica `HarpSynthVoice` and O-Wind `FluteSynthVoice`
  - `canPlaySound()` returns true for the single `BassoonSound`

**Key methods:**
- `startNote(midiNote, velocity, sound, currentPitchWheelPosition)` — compute base frequency via TuningEngine, apply pending NE delta via `applyPendingTuning`, retune mode bank, reset envelopes, configure attack from velocity
- `stopNote(velocity, allowTailOff)` — start release envelope; voice clears when envelope reaches silence
- `renderNextBlock(outputBuffer, startSample, numSamples)` — main audio inner loop
- `pitchWheelMoved(value)` — update voice-local pitch-bend semitones (MPE), retune mode bank without resetting envelope
- `controllerMoved(controllerNumber, value)` — handle CC2 (Breath), CC1 (optional vibrato depth), CC11 (expression)

### 2. Mode Bank (Damped Resonators)

- **JUCE Class:** Custom `ModeBank` struct using **direct-form biquad arrays** (NOT `juce::dsp::IIR::Filter` per-mode — too much overhead for 16-mode * 8-voice = 128 instances). Pattern matches O-Formant's "custom biquad structs (32 bytes each)" precedent.
- **Purpose:** Sum of damped sinusoids producing the bassoon timbre. Each mode is a 2nd-order resonant filter with controllable frequency, decay (T60), and amplitude.
- **Parameters Affected:** tone (per-mode damping scaling), breath (overall amplitude), attack_character (excitation, indirectly)
- **Configuration:**
  - **Mode count:** 16 modes per voice (covers fundamental + ~16 harmonics, sufficient for bassoon character without runaway CPU at 8-voice polyphony)
  - **Mode storage:** `std::array<Biquad, 16>` per voice (per-channel state held inside biquad struct, mono per voice — voice output later panned/mono-summed)
  - **Pole-radius coefficient form:** Resonator biquad with two-pole + zero-zero structure
    ```
    theta_k = 2π * f_k / fs
    R_k     = exp(-1/(tau_k * fs))      // pole radius
    a1_k    = -2*R_k*cos(theta_k)
    a2_k    =  R_k * R_k
    G_k     = (1 - R_k) * amplitude_k    // unity peak gain normalisation
    ```
    (Direct from `research/modal-synthesis-bells-academic-research.md` §7.1 — same formula family; bell-vs-bassoon difference lives in the partial table, not the biquad math.)
  - **Bassoon partial table (per-mode ratios + amplitudes):** Inharmonic-but-near-integer ratios with first-formant emphasis at ~450-500 Hz. See **§ Algorithm Details / Bassoon Partial Table** below for concrete numbers.
  - Coefficients recomputed when fundamental changes (note-on, MPE pitch-bend, NE delta) AND when `tone` parameter changes
  - All allocations in `prepareToPlay()` — `processBlock()` only updates coefficients in place

### 3. Excitation Generator

- **JUCE Class:** Custom `Exciter` (impulse + filtered noise + attack-character morph). No JUCE dsp class is a drop-in; we compose `juce::Random` + a single `juce::dsp::IIR::Filter<float>` for the noise lowpass.
- **Purpose:** Inject energy into the mode bank to start (and continuously sustain at low level for long-tone air noise) the resonators. Models the bassoon's air column excitation without modeling reed self-oscillation.
- **Parameters Affected:** attack_character, breath, attack_time
- **Configuration:**
  - **Onset impulse component:** Short shaped pulse at note-on. Shape morphs with `attack_character`:
    - `attack_character = 0` (Soft pad): 30-50 ms half-sine impulse, low amplitude, low-passed at ~600 Hz — pad-like, gentle
    - `attack_character = 1` (Tongued): 5-10 ms exponentially decaying noise burst, full bandwidth, higher peak — articulated
    - Crossfade between the two via `attack_character`
  - **Sustain noise component:** Low-level filtered white noise during sustain — models the air-column hiss that real wind instruments retain. Lowpass cutoff ~2 kHz, level scales with `breath` parameter.
  - **Velocity scaling:** Initial dynamic + initial attack character bias (high velocity → biases attack_character toward "tongued"; low velocity → biases toward "soft")
  - Pre-allocated impulse buffer + `juce::dsp::IIR::Filter` for noise LP. No allocations in `processBlock`.

---

### 4. ADSR Amplitude Envelope

- **JUCE Class:** `juce::ADSR` (per-voice) — built-in JUCE class, well-validated for envelope shaping
- **Purpose:** Per-note onset/sustain/release amplitude shaping. AS = constant (always 1.0) since long-tone use is sustain-dominated; D = 0 (no decay phase). Effectively AR shape for long-tone instrument.
- **Parameters Affected:** attack_time, release_time, breath
- **Configuration:**
  - `juce::ADSR::Parameters` populated as `{attack_time/1000, 0.0f, 1.0f, release_time/1000}` (D=0 ensures we go straight from attack peak to sustain)
  - `setSampleRate()` in `prepareToPlay()`
  - `noteOn()` in `startNote`, `noteOff()` in `stopNote`
  - Final per-sample amplitude = `adsr.getNextSample() * breath_smoothed`

**Why JUCE ADSR (not custom):** Long-tone use case is exactly what JUCE's ADSR is built for. Adds attack/release smoothing without click. Already validated across 8+ Ouaricon plugins.

---

### 5. Vibrato LFO + Onset Delay

- **JUCE Class:** Custom small LFO struct (sine LUT or `std::sin` on a phase accumulator) + onset-delay smoothed amplitude ramp (`juce::SmoothedValue<float>`)
- **Purpose:** Slow pitch modulation that fades in after a configurable delay — matches real bassoonist phrasing (player adds vibrato after the note has stabilised).
- **Parameters Affected:** vibrato_rate, vibrato_depth, vibrato_onset
- **Configuration:**
  - LFO output range: ±1.0 sine wave at `vibrato_rate` Hz
  - Effective depth: `vibrato_depth_cents * vibrato_onset_envelope * lfo_value`
  - Onset envelope: 0.0 from note-on, ramps to 1.0 over `vibrato_onset` ms (linear ramp via `SmoothedValue<float>::reset(sr, vibrato_onset/1000)` followed by `setTargetValue(1.0)` after note-on)
  - Vibrato pitch delta is in **cents**, applied multiplicatively to fundamental:
    `f_modulated = f_base * pow(2, vibrato_cents / 1200)`
  - Mode bank coefficients recompute on every block (or every N samples — see Optimisation note in Special Considerations)
  - **NOT MIDI-CC linked by default** — vibrato is parameter-driven, not aftertouch-driven, for v1.0. (Brief notes "aftertouch → optional vibrato depth modulation (TBD in Stage 0)"; **Decision below: defer to v1.1** — see Architecture Decision 4.)

---

### 6. Tone / Brightness Control

- **JUCE Class:** Coefficient logic inside `ModeBank` (no separate class). Operates by scaling per-mode `T60` decay times.
- **Purpose:** Continuous dark-to-bright control without changing mode count or partial structure. `tone = 0` heavily damps upper modes (woody, dark). `tone = 1` light damps upper modes (bright, present).
- **Parameters Affected:** tone
- **Configuration:**
  - Per-mode damping scale: `T60_k_scaled = T60_k * mix(0.3, 1.5, tone)` for upper modes (k > 4)
  - Lower modes (k <= 4, including the formant region) are largely untouched — fundamental and first-formant region remain stable across tone sweeps
  - Recompute biquad pole radius `R_k` whenever `tone` parameter changes
  - Smoothed via `SmoothedValue` (50ms ramp) to avoid zipper noise on rapid parameter changes

---

### 7. Voice Manager (Polyphony)

- **JUCE Class:** `juce::Synthesiser` (NOT `juce::MPESynthesiser`)
- **Purpose:** Allocate up to 16 `BassoonVoice` instances, route MIDI note-on/note-off events to voices, implement oldest-note stealing.
- **Parameters Affected:** voice_count
- **Configuration:**
  - Voice count is **dynamic** — `voice_count` parameter changes take effect on next `noteOn` (not mid-note, to avoid clipping a held voice)
  - One `juce::SynthesiserSound` (subclassed as `BassoonSound`) registered globally
  - 16 voices pre-allocated in `prepareToPlay()`; if `voice_count < 16`, the lowest-index voices are eligible and the rest are inert (return false from `canPlaySound` while above the cap, OR the synth's stealing logic naturally limits active count — see Algorithm Details)
  - **Stealing policy:** Oldest-note (default `juce::Synthesiser` behaviour with `setNoteStealingEnabled(true)`)

**Why `juce::Synthesiser` (not `MPESynthesiser`):**
1. O-Lyrica + O-Wind both use plain `juce::Synthesiser` and successfully integrate Note Expression + MPE pitch-bend without MPE-specific machinery
2. `MPESynthesiserVoice` has 6 pure-virtual methods (`noteStarted`, `noteStopped`, `notePressureChanged`, etc.) — heavier integration cost, not needed for our parameter set
3. Dorico's NE pattern (the spike) is host-side — works identically with either base class
4. MPE channel pitch-bend is handled by JUCE's internal pitch-bend → `pitchWheelMoved(value)` per voice (channel-aware when MPE is enabled in the host) — already supports MPE in practice without `MPESynthesiser`

### 8. Microtonal Tuning (Shared `note-expression` Module)

- **JUCE Class:** Shared module at `modules/tuning/note-expression/`
  - `Ouaricon::NoteExpression::Controller` (NEC for `kTuningTypeID`)
  - `Ouaricon::NoteExpression::VST3Extensions` (owns NEC + raw-event queue + 128-slot `PendingTuningTable`)
  - `Ouaricon::NoteExpression::updatePendingFromEvents()` — drain helper called at top of `processBlock()`
  - `Ouaricon::NoteExpression::applyPendingTuning()` — voice-side helper called inside `startNote()` before DSP retune
- **Purpose:** Per-note tuning offsets driven by Dorico's `kTuningTypeID` Note Expression events, applied on top of any base tuning (12-TET or Scala/TUN).
- **Parameters Affected:** None — this is a host-driven sub-system, not user-facing
- **Configuration:**
  - Plugin must declare `target_link_libraries(O-Bassoon PRIVATE Ouaricon::note_expression)` in CMakeLists.txt (or equivalent — the module ships an `OuariconModules.cmake` helper)
  - Plugin must implement `getVST3ClientExtensions()` to return a long-lived `Ouaricon::NoteExpression::VST3Extensions` instance
  - Plugin must drain the queue at the top of `processBlock()` BEFORE `synthesiser.renderNextBlock()`
  - Voice must call `applyPendingTuning(pendingTuningSource, midiNoteNumber, currentFrequency)` inside `startNote()` BEFORE retuning the mode bank
  - Requires the local JUCE-NE-PATCH (already applied to `/Users/taylorbrook/JUCE/`) — CMake-time marker check is built into the module

**Why shared module (not local copy):** v1.1.0 of `note-expression` is production-validated by O-Lyrica 2.3.0 and includes a stripped-of-spike-diagnostics public surface. Reusing avoids the spike's `/tmp/olyrica-ne-trace.log` audio-thread-file-I/O landmine.

### 9. Tuning Engine (Optional Shared Module)

- **JUCE Class:** Shared module at `modules/tuning/scala-tuning-engine/` (`Ouaricon::TuningEngine` or equivalent)
- **Purpose:** Provides MIDI-note → frequency lookup, supports 12-TET (default) and Scala/TUN files. Used by every voice to compute base frequency before NE delta application.
- **Parameters Affected:** None at v1.0 (defer Scala UI to v1.1; v1.0 ships 12-TET default with reference A4 = 440 Hz)
- **Configuration:**
  - One shared `TuningEngine` instance owned by the processor, raw pointer passed to each voice
  - Default state: 12-TET, A4 = 440 Hz — equivalent to standard MIDI conversion
  - `tuningEngine.getFrequency(midiNote)` returns frequency in Hz
  - Voice-side flow: `f_base = tuningEngine.getFrequency(midiNote); f_with_NE = applyPendingTuning(f_base, ...); f_final = f_with_NE * pitchBendMultiplier;`

**v1.0 scope decision:** Wire the engine in (so v1.1 can add Scala UI without architectural change) but expose **no UI / no APVTS parameters** for tuning at v1.0. Default 12-TET behavior is identical to a plugin without any tuning engine.

## Processing Chain

```
MIDI/MPE/NE Input
     |
     v
[NE Drain] (top of processBlock — Ouaricon::NoteExpression::updatePendingFromEvents)
     |   writes per-pitch semitone deltas into PendingTuningTable
     v
[juce::Synthesiser::renderNextBlock] — routes MIDI to voices
     |
     v
PER VOICE (BassoonVoice::renderNextBlock):
     |
[Vibrato LFO] (sine, vibrato_rate Hz)
     |   * VibratoOnsetEnvelope (ramp 0→1 over vibrato_onset ms)
     |   * vibrato_depth (cents)
     |
     v
[Frequency Computation]
     |   f_base   = tuningEngine.getFrequency(midiNote)  -- already applied at startNote
     |   f_NE     = applyPendingTuning(f_base, ...)     -- already applied at startNote
     |   f_pb    = pitchBendMultiplier (per-voice, MPE channel pitch-bend)
     |   f_vib   = pow(2, vibratoCents/1200)
     |   f_final = f_NE_pb * f_vib
     |
     v
[Mode Bank Coefficient Update] (recompute biquad coeffs from f_final, T60_k * tone_scale)
     |   Throttled: only recompute if f_final or tone changed > epsilon
     |
     v
[Excitation Generator]
     |   onset_impulse  -- shaped pulse at note-on (depends on attack_character)
     |   sustain_noise  -- low-level filtered noise (depends on breath)
     |   summed: excitation = onset_impulse + sustain_noise * breath
     |
     v
[Mode Bank] (16 parallel biquad resonators)
     |   For each mode k: y_k[n] = G_k*x[n] - a1_k*y_k[n-1] - a2_k*y_k[n-2]
     |   voice_out = sum_k(y_k)
     |
     v
[ADSR Envelope] (juce::ADSR — attack_time, sustain=1.0, release_time)
     |   voice_out *= adsr.getNextSample()
     |
     v
[Per-voice scaling: breath]
     |   voice_out *= breath_smoothed (parameter smoother)
     |
     v
Per-Voice Mono Output --> Sum into stereo buffer (centered pan, equal L/R)

AFTER VOICE SUMMATION:
     |
     v
[Output Gain] (output_gain dB, juce::dsp::Gain<float> or simple SmoothedValue gain)
     |
     v
Output (L, R)
```

**Routing notes:**
- **No feedback loops.** All processing is feed-forward through the mode bank. (Distinct from O-Bowed/O-Contrabass/O-Wind, which all have waveguide feedback loops.)
- **No FFT, no oversampling.** Modal synthesis is inherently band-limited (no waveshaping, no harmonic generation). Plain sample-rate processing is sufficient.
- **No multi-output routing.** Single stereo output bus.
- **Vibrato is per-voice** — each voice has its own LFO instance with its own onset envelope (so retriggered notes get a fresh vibrato fade-in).
- **NE drain is processor-level**, not per-voice. Drain runs once per processBlock at the top, then `renderNextBlock` calls per-voice processing.

## System Architecture

### MIDI Routing

**Input handling:** Standard MIDI + optional MPE channel pitch-bend (via the host enabling MPE — JUCE's pitch-bend infrastructure already routes per-channel bends to per-voice `pitchWheelMoved` when MPE is on).

**Note mapping:**
- MIDI note number → `tuningEngine.getFrequency(noteNumber)` → mode bank fundamental
- Velocity → initial dynamic (scales attack peak amplitude) + biases `attack_character` toward "tongued" at high velocity
- Channel handling: omni mode by default (responds to all 16 channels). MPE-aware via pitch-bend per-voice.
- Note range: C1 (MIDI 24) – C6 (MIDI 84). Below C1 or above C6: still play (no hard cutoff) but mode bank may sound thin/sparse.

**MPE Dimensions (when host enables MPE):**

| MPE Dimension | Target Parameter | Range |
|---------------|-----------------|-------|
| Velocity | Initial dynamic + attack character bias | 1-127 → low/soft–high/tongued |
| Pitch bend (X) | Per-voice frequency multiplier | configurable semitone range, default ±2 semis |
| Aftertouch (Z) | Reserved for v1.1 (vibrato depth modulation) | -- |
| Slide (Y / CC74) | Not used at v1.0 | -- |

**Legacy CC mapping:**

| CC | Target | Description |
|----|--------|-------------|
| CC2 | breath | Primary loudness (continuous swells) |
| CC1 | vibrato_depth (optional) | Mod wheel — wired but parameter-summed (not mutually exclusive with parameter) |
| CC11 | output_gain | Standard expression CC |

**JUCE classes:**
- `juce::Synthesiser` + `juce::SynthesiserVoice` — voice allocation with MIDI routing
- `juce::MidiBuffer` — MIDI iteration
- `juce::MidiMessage` — message parsing
- `Ouaricon::NoteExpression::VST3Extensions` — VST3 NE event capture (shared module)

**Processing:**
- Note-on (MIDI / VST3 NoteOn-with-noteId): `juce::Synthesiser` allocates a voice, calls `BassoonVoice::startNote(...)`. Voice computes base frequency, applies pending NE delta, retunes mode bank, resets envelopes, configures attack from velocity.
- Note-off: `BassoonVoice::stopNote(velocity, true)` starts ADSR release. Voice clears when ADSR reaches silence.
- CC2/Aftertouch/CC11/CC1: handled in `BassoonVoice::controllerMoved` — update SmoothedValue targets per voice.
- Pitch bend: `pitchWheelMoved(value)` updates per-voice pitch-bend multiplier and triggers mode bank coefficient update.

## Algorithm Details

### Bassoon Partial Table (Mode Bank Tuning)

**Bassoon spectral observations** (from "Bassoon Operator: Formants in a bassoon spectrum" + Kopp Reeds harmonic analysis):

1. The fundamental is **not the strongest partial** in low/mid register
2. **First formant at ~450-500 Hz** dominates the spectrum — whichever harmonic falls closest to this region is the loudest
3. Partials are **near-integer harmonics** (more harmonic than a bell, less than a perfect string)
4. Spectrum envelope rises from fundamental to formant peak, then descends slowly with strong skew
5. Low notes have many partials (10+); high notes have few (4-5)

**Implementation: Static partial ratio table, dynamic amplitude shaping based on fundamental frequency**

```cpp
// Per-mode partial ratio (relative to fundamental). Near-integer with slight inharmonicity.
static constexpr std::array<float, 16> PARTIAL_RATIOS = {
    1.000f, 2.005f, 3.010f, 4.018f, 5.024f, 6.032f,  7.041f,  8.052f,
    9.064f, 10.078f, 11.092f, 12.108f, 13.125f, 14.144f, 15.164f, 16.186f
};

// Per-mode base T60 (seconds, will be modulated by `tone` for upper modes)
static constexpr std::array<float, 16> BASE_T60 = {
    2.5f, 2.2f, 2.0f, 1.8f, 1.6f, 1.4f, 1.2f, 1.0f,
    0.8f, 0.7f, 0.6f, 0.5f, 0.4f, 0.35f, 0.30f, 0.25f
};

// Dynamic amplitude: peaks at the harmonic closest to FORMANT_F1 = 475 Hz
constexpr float FORMANT_F1 = 475.0f;
constexpr float FORMANT_BW = 200.0f;  // Hz, formant bandwidth

float computeModeAmplitude(int k, float f0) {
    float f_k = f0 * PARTIAL_RATIOS[k];
    // Bell-shaped weighting around the first formant
    float dist = (f_k - FORMANT_F1) / FORMANT_BW;
    float formantWeight = std::exp(-0.5f * dist * dist);
    // Spectral roll-off: harmonics above formant decay as 1/k
    float rollOff = 1.0f / (1.0f + 0.5f * k);
    return formantWeight * rollOff;
}
```

**Acceptance test for FUNC-01 ("recognizable bassoon-like timbre"):** Hold a C3 (130 Hz). Inspect spectrum (e.g., in iZotope Insight): expect peak energy in the 400-600 Hz range (3rd-4th harmonic). Compare to a recorded bassoon C3 — peak harmonic regions should match qualitatively.

### Modal Resonator Biquad

**Algorithm:** Pole-only biquad with normalized peak gain (one-zero output for DC blocking optional).

**Per-mode coefficients:**
```cpp
// Given mode k: f_k (Hz), tau_k = T60_k / 6.91 (decay time constant), fs (sample rate), amp_k
float theta = juce::MathConstants<float>::twoPi * f_k / fs;
float R     = std::exp(-1.0f / (tau_k * fs));
float a1    = -2.0f * R * std::cos(theta);
float a2    = R * R;
float G     = (1.0f - R) * amp_k;  // unity peak gain normalization

// Difference equation (per sample):
// y[n] = G * x[n] - a1 * y[n-1] - a2 * y[n-2]
```

**Stability guarantees:**
- `R < 1` for all valid `tau > 0` → poles inside the unit circle
- Even at extremely long decay (T60 = 30s), R ≈ 0.99995 → still stable
- **Denormal protection:** `juce::ScopedNoDenormals` in `processBlock`. The G normalisation already prevents the biquad from accumulating sub-LSB energy, but ScopedNoDenormals is the belt-and-braces rule for any IIR filter.

**Coefficient update strategy:**
- Note-on: full recompute of all 16 mode coefficients
- Pitch-bend / NE: full recompute (cost = 16 modes × ~10 flops = 160 flops, negligible)
- Tone parameter change: recompute the upper-half (k > 4) modes only
- Vibrato modulation: **block-rate update (not per-sample)** — recompute on every block boundary using the LFO's average-over-block value. Per-sample coefficient update would dominate CPU; block-rate is sufficient for 5 Hz vibrato at 256-sample buffers (one update per 5.3ms = 188 Hz ≫ 5 Hz vibrato).

### Excitation Generator: Attack-Character Morph

**Algorithm:** Crossfade between two pre-computed onset shapes plus a continuous low-level noise component.

```cpp
// In startNote: configure onset
float softShape[NUM_ONSET_SAMPLES];   // 30-50ms half-sine, lowpassed
float tonguedShape[NUM_ONSET_SAMPLES]; // 5-10ms exp-decay noise burst
// Both pre-computed once in prepareToPlay (no allocations in startNote/processBlock)

// In renderNextBlock per sample, while in onset window:
float shapeMix = attack_character;  // 0=soft, 1=tongued
float onset_env = mix(softShape[onsetIdx], tonguedShape[onsetIdx], shapeMix);

// Sustain noise (always running):
float noise = noiseLP.processSample(random.nextFloat() * 2 - 1);
float sustain = noise * 0.05f * breath;  // 5% nominal noise floor scaled by breath

float excitation = onset_env + sustain;
```

**Velocity → attack_character bias:**
```cpp
// In startNote, modify per-voice attack_character:
float vel_bias = (velocity - 0.5f) * 0.3f;  // ±0.3 around UI value
voice_attack_character = clamp(global_attack_character + vel_bias, 0.0f, 1.0f);
```

This satisfies: low velocity → softer attack regardless of UI setting; high velocity → more tongued. Matches real bassoonist behavior (gentle vs. articulated tonguing).

### Vibrato Onset Envelope

**Algorithm:** Linear ramp 0→1 starting at note-on, completing in `vibrato_onset` ms.

```cpp
// In startNote (per voice):
vibratoOnsetSmoother.reset(sampleRate, vibrato_onset / 1000.0);
vibratoOnsetSmoother.setCurrentAndTargetValue(0.0f);
vibratoOnsetSmoother.setTargetValue(1.0f);

// In renderNextBlock:
float onsetGain = vibratoOnsetSmoother.getNextValue();  // ramps 0→1 over vibrato_onset ms
float lfoOut    = std::sin(lfoPhase);  // -1..1
float vibratoCents = vibrato_depth * onsetGain * lfoOut;
lfoPhase += juce::MathConstants<float>::twoPi * vibrato_rate / sampleRate;
if (lfoPhase >= juce::MathConstants<float>::twoPi)
    lfoPhase -= juce::MathConstants<float>::twoPi;  // phase wrap (denormal-safe)
```

**Why linear (not exponential) ramp:** Real bassoonists' vibrato fade-in is approximately linear in perceived depth. Exponential ramps feel "delayed then sudden" — wrong character.

### Voice Stealing

**Algorithm:** `juce::Synthesiser` default behavior with `setNoteStealingEnabled(true)`. JUCE selects the voice with the longest-running envelope (oldest active voice) for steal.

**Voice count enforcement:**
- `voice_count` parameter ∈ {1..16}
- All 16 voices are pre-allocated in `prepareToPlay`
- On note-on: count active voices; if `>= voice_count`, force a steal via JUCE's mechanism. We do this by querying `juce::Synthesiser::findVoiceToSteal` directly OR by overriding `findFreeVoice` to return the oldest voice when active count >= cap.

**Implementation note:** Simplest path is to override `findFreeVoice(soundToPlay, midiChannel, midiNoteNumber, stealIfNoneAvailable)` in a custom `juce::Synthesiser` subclass, returning a stolen voice if `getActiveVoiceCount() >= voice_count`.

## Integration Points

### Feature Dependencies

- **Mode Bank ← Tuning Engine + Note Expression:** Mode bank fundamental frequency depends on `tuningEngine.getFrequency() * NE_multiplier * pitchBendMultiplier * vibratoMultiplier`. NE delta MUST be applied before mode bank coefficient computation in `startNote`.
- **Excitation Generator ← ADSR + breath:** Sustain noise level scales with `breath`. Onset shape time is independent of `attack_time` (envelope vs. excitation pulse are distinct timescales).
- **ADSR ← Voice Manager:** ADSR `noteOff()` is triggered by `juce::Synthesiser` via `BassoonVoice::stopNote`. Voice clears when ADSR reaches silence (`adsr.isActive() == false`).
- **Voice Stealing ← Voice Count:** Voice cap is enforced at note-on via custom `findFreeVoice` override.
- **Vibrato Onset ← Note-on:** Vibrato onset envelope resets to 0 on every note-on (per-voice), so retriggers always start fresh.

### Parameter Interactions

- **breath × output_gain:** Both scale loudness. `breath` is musical (per-note expression), `output_gain` is mix-level (master output). They multiply.
- **tone × attack_character:** Independent — tone shapes sustain spectrum, attack_character shapes onset spectrum. No cross-coupling at the parameter level, but both contribute to perceived "darkness" if you tune both to the dark extreme (deep design space).
- **vibrato_depth × vibrato_onset:** vibrato_depth is the asymptotic depth; vibrato_onset is how long until you reach it. At vibrato_onset = 0, depth is full immediately at note-on (sounds artificial — this is the "no fade-in" path).
- **attack_time × attack_character:** attack_time shapes the amplitude envelope (slow-rising vs. fast-rising). attack_character shapes the spectral content of the onset (gentle vs. percussive). They are orthogonal: short attack_time + soft attack_character = "fast pad" (unusual but valid). Long attack_time + tongued attack_character = "slow articulated swell" (also valid).

### Processing Order Requirements

**Per-block processing order (REQUIRED):**

1. **NE Drain** — drain the raw-event queue and write per-pitch tuning deltas into `PendingTuningTable` (processor-level)
2. **Synthesiser::renderNextBlock** — JUCE iterates MIDI events and dispatches noteOn/noteOff/pitchBend/CC to voices. **CRITICAL:** Drain (step 1) must happen BEFORE this step so per-voice `startNote` sees the pending NE delta when its note-on fires.
3. **Per-voice render loop** (called by Synthesiser):
   a. Sample vibrato LFO + onset envelope (per block start, to produce vibratoCents for this block)
   b. If frequency or tone changed since last block → recompute mode bank coefficients
   c. Per-sample inner loop:
      - Sample ADSR
      - Sample excitation (onset shape if in onset window + sustain noise)
      - Run mode bank biquads (16 second-order sections)
      - Apply ADSR × breath gain
      - Write to voice mono buffer
4. **Voice summation** — JUCE sums per-voice buffers into the output (centered, equal L/R)
5. **Output Gain** — post-summation `output_gain` applied (block-level smoothed)

**Why order matters:**
- NE drain BEFORE renderNextBlock: per the spike pattern, voices read pending tuning in `startNote` via `exchange`. Drain must populate the table first.
- Mode bank coefficient update BEFORE per-sample inner loop: avoids the first sample of each block being computed with stale coefficients (audible as zipper noise during pitch sweeps).
- ADSR multiplied AFTER mode bank: applying ADSR before the mode bank (i.e., scaling the excitation) would change resonator excitation energy, not just amplitude. The mode bank is supposed to ring; we want ADSR to control the ring's amplitude envelope, not the excitation's energy directly.

### Thread Boundaries

**Audio thread:**
- All DSP processing (mode bank, excitation, ADSR, vibrato, output gain)
- NE queue drain (queue is lock-free; PendingTuningTable is `std::array<std::atomic<double>, 128>`)
- Per-voice `startNote` / `stopNote` / `pitchWheelMoved` / `controllerMoved` / `renderNextBlock`
- Parameter reads via `APVTS::getRawParameterValue()->load()` (atomic) — pulled at block start, smoothed inside block

**Message thread:**
- UI parameter changes via APVTS (atomic writes)
- Preset load/save
- UI repaints

**No background thread needed at v1.0:**
- No file I/O
- Tuning engine ships with embedded 12-TET (no .scl loading at v1.0 — defer to v1.1)
- All state is APVTS-managed

**Communication mechanisms:**
- APVTS atomic parameter values (already managed by JUCE)
- `PendingTuningTable` — `std::array<std::atomic<double>, 128>` from the `note-expression` module (lock-free)
- VST3 raw event queue — managed inside `note-expression` module (lock-free SPSC)

## Implementation Risks

### 1. Modal Synthesis Voice (Mode Bank)

**Complexity:** MEDIUM
- Standard biquad implementation, well-documented in `research/modal-synthesis-bells-academic-research.md`
- 16 modes × 8 voices = 128 biquads at audio rate — within budget on modern CPUs but worth profiling
- Coefficient update math is simple but must be allocation-free

**Risk Level:** LOW

**Risk factors:**
1. Bassoon partial ratios may not produce a recognizable bassoon timbre on first attempt — the formant emphasis at 475 Hz is a hypothesis that needs A/B comparison vs. real bassoon recording
2. CPU cost at 16-voice polyphony × 16 modes = 256 biquads — could push 25% CPU on M1 (target per PERF-02)
3. Inharmonic ratios may sound "bell-like" rather than "bassoon-like" if pushed too far

**Alternative approaches:**
1. **8 modes per voice (instead of 16):** halves CPU cost. Trade-off: thinner timbre, less faithful spectrum. Acceptable if 16-mode CPU exceeds 25%.
2. **Frequency-dependent mode count:** Use 16 modes for low notes, 8 for high notes (matches real bassoon — high notes have fewer audible partials per the Kopp/Bassoon Operator research).
3. **Modal data from real recording (analysis-resynthesis):** Capture spectra from a real bassoon recording, extract per-partial frequencies/decays via sinusoidal modeling tools. Higher fidelity, deferred to v1.1+.

**Fallback architecture:**
- **Primary:** 16 modes per voice with synthesised partial table
- **Fallback 1 (if CPU exceeds budget):** 8 modes per voice, retain formant emphasis
- **Fallback 2 (if timbre unrecognisable):** Adjust formant frequency / amplitudes after A/B vs. recording

**Mitigation strategy:**
1. Implement with simple constants in initial pass; swap in tuned partial table after first listen
2. CPU profile at 8-voice polyphony at 48kHz/256 buffer EARLY in DSP stage
3. Have spectrum analyser ready in DAW for A/B comparison vs. real bassoon recording

## Architecture Decisions

### Decision 1: Modal Synthesis (NOT Waveguide, NOT Reed Self-Oscillation, NOT Additive)

**Decision:** Use parallel-biquad modal synthesis with bassoon-shaped partial table for the voice algorithm.

**Rationale:**
- Brief explicitly mandates "modal synthesis" and excludes O-Reed dependency
- Modal synthesis is excellent for sustained, stable long tones (the explicit use case)
- Low CPU vs. waveguide (no recursive feedback loop, no iterative solver)
- Inherently stable (poles strictly inside unit circle by design — no runaway feedback risk)
- Well-documented in CCRMA / Nathan Ho / Carillon DAFx 2017 research, with concrete formulas in `research/modal-synthesis-bells-academic-research.md`
- No oversampling needed (no nonlinearities in the resonator path)

**Alternatives considered:**
1. **Waveguide (cylindrical bore, like O-Wind/O-Reed):** Rejected. Brief explicitly excludes O-Reed code reuse. Waveguides require feedback-loop stability work, oversampling for nonlinearities, and reed-junction modeling — complexity O-Bassoon doesn't need for a long-tone-focused instrument.
2. **Pure additive synthesis (sum of sines with envelopes):** Rejected. Equivalent CPU to modal banks but **less expressive** — modal banks naturally respond to per-mode damping changes (the `tone` parameter), additive needs separate per-partial envelope state. Modal also handles transient excitation naturally; additive needs explicit envelope shaping per partial.
3. **Sample playback (with looping):** Rejected. Real bassoon samples can't do per-note microtonal pitch without artifacts (resampling mucks up the formant). Modal synth retunes cleanly via coefficient update.
4. **Hybrid (modal core + sampled attack layer):** Rejected for v1.0 (brief explicitly excludes "key-click sample layer"). Reasonable v1.1+ exploration.

**Tradeoffs accepted:**
- **Lower realism than waveguide:** Acceptable because the use case (long-tone microtonal drones, ambient pads) doesn't require the full articulation expressiveness of a waveguide model. Reviewers comparing to SWAM Bassoon will hear differences; that's OK — O-Bassoon is a stylized "modal bassoon" tool, not a SWAM competitor.
- **No reed self-oscillation:** Locked in by brief. Means no embouchure-driven multiphonics, no overblowing tricks. Acceptable.
- **Static partial structure:** Spectrum doesn't morph with playing dynamics the way a real bassoon does. Mitigated partially by `attack_character` (onset spectrum) and `tone` (sustain spectrum). Full dynamic spectrum morphing deferred to v1.1+.

---

### Decision 2: 16 Modes Per Voice

**Decision:** 16 modes per voice. Fixed across all notes; per-mode amplitude weighted by formant proximity.

**Rationale:**
- Bell research notes "8-16 modes for simple modal synth, 30-60 for realistic"
- Bassoon's spectrum has ~10-12 audible partials in low/mid register (per Kopp/Bassoon Operator), so 16 covers it with headroom
- 16 × 8 voices = 128 biquads at audio rate — well within CPU budget on M1 (estimated <10% CPU at 48kHz/256)
- 16 is a power of 2, friendly for SIMD experimentation if perf becomes an issue

**Alternatives considered:**
1. **8 modes:** Rejected as primary. Would lose the upper-formant region detail. Acceptable as fallback if CPU budget breached.
2. **24-32 modes:** Rejected. Diminishing returns past 16 — bassoon doesn't have meaningful partial energy past the ~16th harmonic (which is ~8 kHz at C3, near the spectral noise floor).
3. **Frequency-adaptive count:** Considered for v1.1. Stage 0 v1.0 keeps it simple at fixed 16.

**Tradeoffs accepted:**
- Slight over-budgeting at high notes (where bassoon naturally has fewer audible partials). Cost: ~10% wasted CPU on inaudible upper modes for high notes. Acceptable for v1.0 simplicity.

---

### Decision 3: `juce::Synthesiser` (Not `MPESynthesiser`)

**Decision:** Use `juce::Synthesiser` + `juce::SynthesiserVoice` base classes. MPE pitch-bend handled via the standard `pitchWheelMoved` per-voice callback (which JUCE makes channel-aware when MPE is enabled in the host).

**Rationale:**
- O-Lyrica + O-Wind both use `juce::Synthesiser` and successfully integrate Note Expression + MPE in production
- `MPESynthesiserVoice` has 6 pure-virtual methods → larger integration cost without proportional benefit for our parameter set (we don't need per-note pressure / timbre slide)
- Note Expression flow is independent of voice base class — works identically with either
- Brief lists Aftertouch as "TBD" / "deferred to v1.1"; we don't need MPE pressure/timbre at v1.0

**Alternatives considered:**
1. **`MPESynthesiser`:** Rejected for v1.0. Would revisit if v1.1 adds MPE pressure (vibrato depth modulation) or timbre (tone control).
2. **Custom voice manager:** Rejected. Reinventing JUCE's voice manager has no benefit and known pitfalls (stuck notes, allocation bugs).

### Decision 4: Aftertouch → Vibrato Deferred to v1.1

**Decision:** Wire CC1 (mod wheel) and the `vibrato_depth` UI parameter additively at v1.0. Aftertouch (channel pressure) is **not connected** at v1.0.

**Rationale:**

**Alternatives considered:**

2. **Poly aftertouch → vibrato_depth:** Requires per-voice aftertouch state. Rejected for v1.0 scope.

**v1.1 reconsideration:** Add when also adding MPESynthesiser support (if user demand exists).

## Special Considerations

### Thread Safety

- Parameter reads use `APVTS::getRawParameterValue()->load()` once per block, smoothed across the block via `juce::SmoothedValue`
- Mode bank coefficient updates happen on the audio thread (no allocations — coefficient arrays are pre-sized in `prepareToPlay`)
- LFO phase state is per-voice (no shared state)
- `PendingTuningTable` is `std::array<std::atomic<double>, 128>` — lock-free reads / writes between processor (drain) and voice (`exchange` consume)
- ADSR state is per-voice (juce::ADSR is thread-confined)
- No mutexes anywhere in the audio path

### Performance

**Per-voice CPU breakdown (estimated, M1 / 48kHz / 256 buffer):**
- 16 biquad modes: ~1.5% CPU per voice
- Excitation generator (noise + onset shape): ~0.2% CPU per voice
- ADSR + vibrato + envelope smoothing: ~0.1% CPU per voice
- Coefficient updates (block-rate vibrato modulation): ~0.05% CPU per voice
- **Total per-voice:** ~2% CPU
- **8 voices:** ~16% CPU (well under PERF-02's 25% target)
- **16 voices (max):** ~32% CPU (exceeds PERF-02's target which only specifies 8-voice; documented as a known limit)

**Optimization opportunities (if needed):**
- SIMD biquad evaluation (4-wide at minimum, could process 4 modes in parallel)
- Per-voice dropping of inaudible upper modes when ADSR amplitude is below -60 dBFS
- Block-rate (not per-sample) coefficient update is already in place

### Denormal Protection

- `juce::ScopedNoDenormals` at the top of `processBlock`
- All biquad state has G-normalized peak gain → naturally avoids accumulating sub-LSB energy
- ADSR release: when ADSR reaches silence, voice clears (zeros mode bank state on `clearCurrentNote`) — prevents long-lived residual state from accumulating denormals

### Sample Rate Handling

- All coefficient computations are sample-rate-aware (`fs` is a parameter to every coefficient formula)
- `prepareToPlay` is called for every sample-rate change → all biquad coefficients recomputed
- LFO phase increment recomputed in `prepareToPlay`
- ADSR `setSampleRate` called in `prepareToPlay`
- Vibrato onset SmoothedValue `reset(sampleRate, ...)` called in `prepareToPlay`

### Latency

- **Zero processing latency.** Mode bank is feed-forward (one biquad cycle = 1 sample of internal delay, dwarfed by host buffer size).
- `getLatencySamples()` returns 0.
- No host compensation needed.
