## Core Components

### 1. Bow Model (Exciter)

- **JUCE Class:** Custom implementation -- no JUCE class for bow excitation
- **Purpose:** Generate bow velocity signal from MIDI/MPE input and envelope, route to friction junction
- **Parameters Affected:** BOW_SPEED, BOW_PRESSURE, BOW_POSITION
- **Configuration:**
  - MIDI note-on velocity maps to initial bow speed
  - Aftertouch / CC2 (Breath) maps to BOW_PRESSURE in real-time
  - CC74 (MPE Y / Slide) maps to BOW_POSITION (beta)
  - CC11 (Expression) maps to BOW_SPEED
  - Pitch bend maps to frequency (portamento via delay line interpolation)
  - Bow envelope: attack ramp 5-50ms depending on velocity, sustain at target, release ramp on note-off
  - Bow direction tracking (up/down bow) for noise bursts on direction change

### 2. Nonlinear Friction Junction (Scattering Junction)

- **JUCE Class:** Custom implementation -- core nonlinear DSP
- **Purpose:** Compute stick-slip interaction between bow and string at the bow contact point
- **Parameters Affected:** BOW_SPEED, BOW_PRESSURE, ROSIN, REVERSED_FRICTION
- **Configuration:**
  - **Core tier (always active):** Enhanced hyperbolic bow table
    - `mu(v_rel) = mu_d + (mu_s - mu_d) * v_0 / (v_0 + |v_rel|)`
    - mu_s = 0.8 (static friction), mu_d = 0.3 (dynamic friction)
    - v_0 = 0.01-0.1 maps from ROSIN parameter (low ROSIN = smooth, high = aggressive)
    - Memoryless table lookup: O(1) per sample, no iteration
    - Reflection coefficient: `rho = r / (1 + r)` where `r = 0.25 * mu / R_s`
  - **Enhanced tier (optional):** + Elasto-plastic bristle state
    - State variable z (bristle displacement) tracks stick-slip transitions
    - Three regimes: pre-sliding (elastic), elasto-plastic (transition), purely plastic (slip)
    - Passivity guaranteed via velocity-dependent damping: `sigma_1_eff = sigma_1 * (1 + v_rel^2)`
    - Newton-Raphson solver: 4 iterations typical, O(4) function evaluations per sample
  - **Quality tier (optional):** + Thermal rosin temperature
    - Temperature state variable T_contact tracks contact point temperature
    - Rosin glass transition at ~49C creates natural hysteresis loops
    - Heat generation: `Q = F_friction * |v_rel|`
    - Cooling: Newton's law `Q_loss = k * (T - T_ambient)`
  - REVERSED_FRICTION parameter (0-100%): Blends between normal and inverted friction curve
  - Friction tier selectable at runtime (user quality preference)

### 3. Digital Waveguide String

- **JUCE Class:** `juce::dsp::DelayLine<float, juce::dsp::DelayLineInterpolationTypes::Thiran>` (allpass interpolation for fractional delay)
- **Module:** `juce_dsp`
- **Purpose:** Model wave propagation in the bowed string via bidirectional delay lines
- **Parameters Affected:** STRING_TUNING_1-4, BOW_POSITION, INFINITE_SUSTAIN
- **Configuration:**
  - Two delay lines per string: bridgeDelay (bow-to-bridge) and neckDelay (bow-to-nut)
  - `bridgeDelaySamples = (internalSampleRate / f0) * beta`
  - `neckDelaySamples = (internalSampleRate / f0) * (1.0 - beta)`
  - Thiran allpass interpolation for fractional delay (critical for tuning accuracy and smooth portamento)
  - Maximum delay size: `internalSampleRate / 20.0` (lowest note ~20Hz = C0)
  - Nut termination: near-total reflection with sign inversion (hard boundary)
  - Bridge termination: lowpass filter modeling losses and body coupling
  - Bridge loss filter: one-pole `H(z) = g * (1-p) / (1 - p*z^-1)` where g < 1, p controls brightness
  - INFINITE_SUSTAIN (0-100%): Reduces bridge loss filter gain toward 1.0 (reduces damping toward zero)
  - Vibrato: LFO modulates neckDelay length (+/- cents around target pitch)
  - Portamento: smooth interpolation of total delay length when pitch changes

### 4. Bridge Filter

- **JUCE Class:** `juce::dsp::IIR::Filter<float>` with `juce::dsp::IIR::Coefficients<float>`
- **Module:** `juce_dsp`
- **Purpose:** Frequency-dependent loss at bridge termination + spectral shaping
- **Parameters Affected:** BRIGHTNESS
- **Configuration:**
  - 2-pole lowpass at BRIGHTNESS frequency (20-20000 Hz)
  - Additional bridge hill resonance at ~2.5 kHz (violin), ~1.5 kHz (cello), varies by body preset
  - Coefficients recalculated on parameter change (not per-sample)
  - Part of the waveguide loop -- processes output of bridgeDelay before body resonator

### 5. Body Resonator (Morphable Biquad Bank)

- **JUCE Class:** Array of `juce::dsp::IIR::Filter<float>` in parallel configuration
- **Module:** `juce_dsp`
- **Purpose:** Model instrument body resonance via parallel biquad bank with morphable coefficients
- **Parameters Affected:** BODY_MATERIAL, BODY_SIZE
- **Configuration:**
  - 8 parallel biquad sections (peaking EQ filters)
  - BODY_MATERIAL (0-100%) morphs between 4 preset coefficient banks:
    - 0% = Membrane (erhu-like): odd-harmonic resonances 1:3:5:7, formant-like
    - 33% = Wood (violin/cello-like): A0 air, B1-, B1+, bridge hill
    - 66% = Metal: dense inharmonic modes, bright, long sustain
    - 100% = Glass/Synthetic: sparse tuned resonances, otherworldly
  - BODY_SIZE (0-100%) scales all resonant frequencies:
    - 0% = Small (violin range, high freq modes)
    - 50% = Medium (viola/erhu)
    - 100% = Large (cello/bass, low freq modes)
  - Coefficient interpolation: linear interpolation between nearest two preset banks
    - `coeffs = lerp(presetA, presetB, fractionalPosition)`
  - Coefficients updated on parameter change (NOT per-sample -- thread-safe atomic swap)
  - Parallel topology: each biquad processes same input, outputs summed
  - Gain normalization to prevent level jumps during morph

| Metal | 440, 1123, 1872, 3100, 680, 1560, 2400, 5200 | 25, 20, 15, 12, 18, 14, 10, 8 | +8, +6, +5, +4, +7, +5, +3, +2 |

### 6. Sympathetic String Coupling

- **JUCE Class:** Array of `juce::dsp::DelayLine<float, juce::dsp::DelayLineInterpolationTypes::Thiran>` (passive waveguides)
- **Module:** `juce_dsp`
- **Purpose:** Model passive sympathetic string resonance excited by bridge output
- **Parameters Affected:** SYMPATHETIC_AMOUNT, SYMPATHETIC_COUNT
- **Configuration:**
  - 0-12 passive Karplus-Strong style waveguide strings (no bow interaction)
  - Each sympathetic string = single delay line + one-pole loss filter (simple, low CPU)
  - Coupling coefficient: SYMPATHETIC_AMOUNT * 0.01 (range 0.001 to 0.01 of bridge amplitude)
  - Each string tuned to a fixed pitch (chromatic by default, configurable per preset)
  - Excitation: attenuated bridge output fed into each sympathetic string's delay input
  - Optimization: gate strings that are far from current harmonic content (skip if amplitude < threshold)
  - CPU per sympathetic string: ~0.1-0.3% single core at 44.1 kHz
  - Total CPU for 12 strings: ~1.2-3.6% additional

### 7. Bow Noise Generator

- **JUCE Class:** Custom implementation using `juce::Random` for noise source + `juce::dsp::IIR::Filter<float>` for shaping
- **Module:** `juce_dsp`
- **Purpose:** Add rosin scratch/texture that pure waveguide models lack
- **Parameters Affected:** ROSIN, BOW_SPEED, BOW_PRESSURE
- **Configuration:**
  - White noise source filtered to match bow noise spectrum
  - Bandpass filter centered around 2-6 kHz (rosin scratch range)
  - Amplitude modulated by: BOW_PRESSURE * BOW_SPEED (harder/faster bowing = more noise)
  - Direction change noise burst: short (~5ms) broadband burst on bow reversal
  - Mixed into signal path after body resonator (additive, not in waveguide loop)
  - Level: typically 1-5% of main signal

### 8. 2x Internal Oversampling

- **JUCE Class:** `juce::dsp::Oversampling<float>`
- **Module:** `juce_dsp`
- **Purpose:** Reduce aliasing from nonlinear friction junction
- **Parameters Affected:** None (always active)
- **Configuration:**
  - 2x oversampling with polyphase halfband filter
  - Process friction junction + waveguide loop at 2x internal rate
  - Downsample output with `juce::dsp::Oversampling` built-in anti-aliasing
  - Latency: reported via `setLatencySamples()` in `prepareToPlay()`
  - NOTE: Oversampling introduces latency. Brief says "0 samples latency" but this refers to algorithmic latency from the waveguide (causal). Oversampling latency is acceptable and reported to host.
  - Alternative: process entire waveguide at 2x or only the friction junction at 2x (latter is more efficient)

### 9. Stereo Width Processor

- **JUCE Class:** Custom implementation (mid-side encoding)
- **Purpose:** Generate stereo spread from mono waveguide output
- **Parameters Affected:** WIDTH
- **Configuration:**
  - Mono waveguide output duplicated to L/R
  - For multi-string: strings panned across stereo field
  - WIDTH parameter (0-200%):
    - 0% = mono
    - 100% = natural stereo (slight decorrelation per string)
    - 200% = wide (exaggerated stereo, side boosted)
  - Implementation: mid-side matrix with WIDTH controlling side gain
  - M = (L + R) / 2, S = (L - R) / 2
  - L_out = M + S * widthFactor, R_out = M - S * widthFactor

### 10. Sub-Harmonics Generator

- **JUCE Class:** Custom implementation (nonlinear waveguide feedback)
- **Purpose:** Generate sub-octave content for "impossible physics" sound design
- **Parameters Affected:** SUB_HARMONICS
- **Configuration:**
  - Nonlinear feedback injection into waveguide at half-frequency
  - Achieved by frequency-halving circuit: asymmetric clipping in feedback path
  - SUB_HARMONICS (0-100%) controls injection level
  - At 0%: completely bypassed
  - At 100%: prominent sub-octave
  - Applied within waveguide loop (pre-body resonator)

### 11. Microtonal Tuning System

- **JUCE Class:** Shared module at `modules/tuning/scala-tuning-engine`
- **Module:** Custom (pre-existing shared module)
- **Purpose:** Support Scala/TUN import, MTS-ESP, and standard 12TET tuning
- **Parameters Affected:** REFERENCE_PITCH, TUNING_SYSTEM
- **Configuration:**
  - TUNING_SYSTEM choice: 0 = Scala/TUN file, 1 = MTS-ESP, 2 = 12TET (default)
  - REFERENCE_PITCH: 220-880 Hz (default 440 Hz)
  - TuningEngine pointer passed to each voice (same pattern as O-Prism / O-Lyrica)
  - Scala file loading on message thread, tuning table passed to audio thread atomically
  - Per-string tuning offsets (STRING_TUNING_1-4) applied on top of tuning system

## Processing Chain

```
MIDI/MPE Input
     |
     v
[Bow Model] ------> (v_bow, F_bow, beta)
     |
     |   +------ [2x Oversampling Upsample] ------+
     |   |                                          |
     v   v                                          |
[Nonlinear Friction Junction] <--> [String Waveguide(s)]
     |      rho_hat * v_delta                       |
     |      injected into both                      |
     |      delay lines                             |
     |                                              |
     |   +------ [2x Oversampling Downsample] -----+
     |
     v
[Bridge Filter] <-- BRIGHTNESS parameter
     |
     v
[Body Resonator] <-- BODY_MATERIAL, BODY_SIZE parameters
     |                (parallel biquad bank, morphable)
     |
     v
[Sympathetic Coupling] <-- SYMPATHETIC_AMOUNT, SYMPATHETIC_COUNT
     |                      (0-12 passive waveguide strings)
     |
     +--- [Bow Noise Generator] (additive mix)
     |          ^
     |          |-- BOW_PRESSURE, BOW_SPEED, ROSIN
     |
     v
[Output Level] <-- OUTPUT_LEVEL parameter
     |
     v
[Stereo Width] <-- WIDTH parameter
     |
     v
Output (L, R)
```

**Routing notes:**
- Friction junction and waveguide operate at 2x internal sample rate
- Bridge filter and body resonator operate at native sample rate (post-downsample)
- Sympathetic strings operate at native sample rate (passive, no nonlinearity)
- Bow noise is additive (not in waveguide loop) -- mixed after body resonator
- Multi-string: each active string has its own waveguide + friction junction, shares body resonator
- STRING_COUNT determines how many string waveguides are active (1-4)
- Sub-harmonics injection happens inside the waveguide loop (before bridge filter)
- Infinite sustain modifies bridge loss filter gain (inside waveguide loop)
- Reversed friction modifies friction curve shape (inside friction junction)

## System Architecture

### MIDI Routing

**Input handling:** MPE-aware (per-note expression) with legacy MIDI CC fallback

**Note mapping:**
- MIDI note number determines string pitch (f0 = tuningEngine.getFrequency(noteNumber))
- Velocity maps to bow attack intensity (initial bow speed ramp)
- Channel handling: MPE mode (per-note channel) or legacy omni mode

**MPE Dimensions:**

| MPE Dimension | Target Parameter | Range |
|---------------|-----------------|-------|
| Note velocity | Bow speed attack | 0-127 -> 0.02-2.0 m/s |
| Aftertouch (Z) | Bow pressure | 0-127 -> 0.01-5.0 N |
| Slide (Y / CC74) | Bow position (beta) | 0-127 -> 0.02-0.30 |
| Pitch bend (X) | Pitch / portamento | +/- 48 semitones |

**Legacy CC Mapping:**

| CC | Target | Description |
|----|--------|-------------|
| CC1 | Vibrato depth | Mod wheel |
| CC2 | Bow pressure | Breath controller |
| CC11 | Bow speed | Expression |
| CC74 | Bow position | Brightness / MPE Y |

**JUCE classes:**
- `juce::MidiBuffer` -- MIDI event iteration in processBlock
- `juce::MidiMessage` -- individual message parsing
- `juce::MPEInstrument` -- MPE zone management (if full MPE support)
- `juce::SynthesiserVoice` -- voice allocation with MIDI routing

**Processing:**
- MIDI messages processed in `processBlock()` on audio thread
- Note-on: allocate voice, configure bow model, start bow envelope
- Note-off: start bow release envelope (fade bow speed to 0)
- CC messages: update bow parameters in real-time via atomic reads
- Pitch bend: smooth portamento via delay line interpolation

### State Persistence

**What state is saved:**
- APVTS parameters: All 22 automatable parameters (automatic via APVTS)
- Custom state:
  - Friction tier selection (core/enhanced/quality)
  - Scala/TUN file path (if tuning system = Scala)
  - Preset body coefficient overrides (if user has custom body)
  - Per-string tuning offsets

**Serialization format:**
- APVTS parameters: Automatic via `AudioProcessorValueTreeState`
- Custom state: `juce::ValueTree` with XML serialization

**JUCE classes:**
- `juce::AudioProcessorValueTreeState` -- parameter persistence (automatic)
- `juce::ValueTree` -- custom state tree
- `juce::File` -- Scala/TUN file path storage

**Save/restore methods:**
- `getStateInformation(MemoryBlock& destData)` -- serialize APVTS + custom ValueTree
- `setStateInformation(const void* data, int sizeInBytes)` -- deserialize and restore

**Restore behavior:**
- Missing Scala file: fall back to 12TET, show warning in UI
- Invalid state data: use defaults (all parameters at default values)
- Version migration: future-proofed via ValueTree versioning

## Algorithm Details

### Enhanced Hyperbolic Bow Table (Core Friction)

**Algorithm:** Physics-derived hyperbolic friction curve replacing STK's empirical 4th-power formula

**Implementation notes:**
- `mu(v_rel) = mu_d + (mu_s - mu_d) * v_0 / (v_0 + |v_rel|)`
- Convert friction coefficient to waveguide reflection coefficient: `r = 0.25 * mu / R_s; rho = r / (1 + r)`
- ROSIN parameter maps to v_0: `v_0 = 0.1 * exp(-4.6 * rosin)` (range 0.1 to 0.01)
- R_s = string wave impedance = `sqrt(tension * linearMass)`
- Computation: O(1) per sample, no iteration, memoryless
- Input: incoming differential velocity `v_delta+ = v_bow - (v_sr+ + v_sl+)`
- Output: `newVelocity = v_delta+ * rho(v_delta+)` injected into both delay lines

### Elasto-Plastic Bristle Model (Enhanced Friction)

**Algorithm:** State-based friction with bristle displacement tracking

**Implementation notes:**
- State variable: z (bristle displacement), updated per-sample
- `dz/dt = alpha(z, v_rel) * v_rel`
- Alpha transition: sinusoidal smooth transition between stick (alpha=0) and slip (alpha=1)
- z_ba (breakaway) = mu_s * F_n / sigma_0
- z_ss (steady-state) = mu_d * F_n / sigma_0
- Friction force: `F = sigma_0 * z + sigma_1_eff * dz/dt + sigma_2 * v_rel`
- Passivity fix: `sigma_1_eff = sigma_1 * (1 + v_rel^2)` (prevents energy injection)
- Newton-Raphson solver required: 4 iterations typical per sample
- Clamp z to +/- 1.5 * z_ss to prevent runaway

### Thermal Rosin Model (Quality Friction)

**Algorithm:** Temperature-dependent friction coefficient

**Implementation notes:**
- State variable: T_contact (contact temperature in Celsius)
- `mu(T) = mu_max * exp(-alpha_T * max(0, T - T_glass))`
- T_glass = 49C (rosin glass transition)
- Heat generation: `Q_gen = |F_friction * v_rel|`
- Cooling: `Q_loss = k * (T - T_ambient)` (Newton's law)
- Temperature update: `T += (Q_gen - Q_loss) / thermalMass * dt`
- Clamp T to [T_ambient, 200C]
- Thermal time constant is slow relative to audio rate -- adds subtle evolution to sustained tones

### Waveguide Scattering Junction

**Algorithm:** Nonlinear two-port scattering at bow contact point

**Implementation notes:**
- Read incoming waves: `v_sr+ = bridgeDelay.readFromEnd()`, `v_sl+ = neckDelay.readFromEnd()`
- Compute incoming differential velocity: `v_delta+ = v_bow - (v_sr+ + v_sl+)`
- Compute reflection: `newVelocity = v_delta+ * rho(v_delta+)` (using chosen friction model)
- Write outgoing waves: `bridgeDelay.write(v_sr+ + newVelocity)`, `neckDelay.write(v_sl+ + newVelocity)`
- Nut reflection: sign inversion `output = -input` (hard boundary)
- Bridge reflection: loss filter then body coupling

### Body Resonator Coefficient Morphing

**Algorithm:** Linear interpolation between preset biquad coefficient banks

**Implementation notes:**
- BODY_MATERIAL determines which two presets to interpolate between:
  - 0.0-0.33: membrane <-> wood
  - 0.33-0.66: wood <-> metal
  - 0.66-1.0: metal <-> glass
- For each of 8 biquad sections: `b0, b1, b2, a0, a1, a2 = lerp(bankA[i], bankB[i], t)`
- BODY_SIZE scales center frequencies: `f_scaled = f_base * pow(2.0, (0.5 - bodySize) * 3.0)` (3 octaves range)
- Recalculate peaking EQ coefficients with scaled frequencies using `juce::dsp::IIR::Coefficients<float>::makePeakFilter(sampleRate, freq, Q, gain)`
- Update coefficients atomically (swap pointers, not per-sample recalculation)
- Apply makeup gain normalization after morph to prevent level jumps

### Sympathetic String Resonance

**Algorithm:** Simplified Karplus-Strong waveguides excited by bridge output

**Implementation notes:**
- Each sympathetic string: one delay line + one-pole loss filter
- Delay length: `internalSampleRate / f_sympathetic`
- Loss filter: `y[n] = (1 - damping) * x[n] + damping * y[n-1]` (damping ~0.999)
- Excitation: `input = bridgeOutput * couplingCoefficient`
- Coupling coefficient: SYMPATHETIC_AMOUNT * 0.01
- Gating optimization: skip computation if string's stored energy < threshold
- All sympathetic strings summed and mixed with main signal

### Fractional Delay (Allpass Interpolation)

**Algorithm:** First-order allpass filter for sub-sample delay accuracy

**Implementation notes:**
- `y[n] = a * x[n] + x[n-1] - a * y[n-1]` where `a = (1-d)/(1+d)`, d = fractional part
- Critical for: accurate tuning, smooth portamento, vibrato
- JUCE's `DelayLine` with `Thiran` interpolation provides this built-in
- For portamento: smoothly ramp total delay length over 10-100ms
- For vibrato: sinusoidal modulation of neckDelay length

## Integration Points

### Feature Dependencies

- **Bow Model -> Friction Junction:** Bow velocity and force are inputs to friction computation
- **Friction Junction <-> Waveguide:** Bidirectional coupling -- friction depends on string velocity, string depends on friction force
- **Waveguide -> Bridge Filter:** String output (from bridge end of delay line) feeds bridge filter
- **Bridge Filter -> Body Resonator:** Filtered string output feeds parallel biquad bank
- **Body Resonator -> Sympathetic Coupling:** Body output excites sympathetic strings
- **Oversampling wraps Friction + Waveguide:** Only the nonlinear section runs at 2x
- **Tuning System -> Waveguide:** Tuning engine provides frequency for delay length calculation
- **Per-String Tuning -> Waveguide:** Cent offsets added to base frequency before delay calculation
- **Bow Noise -> Output Mix:** Additive (post-body), not in waveguide feedback loop

### Parameter Interactions

- **BOW_SPEED + BOW_PRESSURE:** Together determine Schelleng playability region. High pressure with low speed = raucous. Low pressure with high speed = surface sound. The "sweet spot" varies with BOW_POSITION.
- **BOW_POSITION (beta) + BOW_PRESSURE:** Schelleng wedge narrows as beta decreases (closer to bridge). Maximum force inversely proportional to beta.
- **ROSIN + BOW_PRESSURE:** Both affect friction curve shape. High ROSIN + High pressure = very aggressive stick-slip (harsh sound). Low ROSIN + moderate pressure = smooth, pure tone.
- **BODY_MATERIAL + BODY_SIZE:** Interact to create instrument identity. Material=Wood + Size=Small = violin. Material=Membrane + Size=Medium = erhu. Both affect coefficient bank simultaneously.
- **INFINITE_SUSTAIN + bridge loss filter:** INFINITE_SUSTAIN reduces bridge filter gain toward 1.0, effectively removing per-cycle energy loss. At 100%, string sustains indefinitely (drone).
- **REVERSED_FRICTION + normal friction:** Crossfade between normal and inverted curves. At 50%, friction curve is flattened (neither sticking nor slipping normally), producing unusual timbres.
- **STRING_COUNT + CPU:** Each additional string adds ~2-5% CPU. 4 strings + 12 sympathetic = significant load.

### Processing Order Requirements

**Sequential processing order (REQUIRED):**

1. **Read MIDI/MPE input:** Parse note events, CC changes, pitch bend, aftertouch
2. **Update bow model:** Calculate v_bow, F_bow, beta from MIDI state + envelopes
3. **Upsample to 2x:** Prepare for oversampled processing
4. **For each oversample (2 iterations per output sample):**
   a. Read incoming waves from both delay lines
   b. Compute differential velocity v_delta+
   c. Evaluate friction model (core, or core+enhanced, or core+enhanced+thermal)
   d. Compute reflected velocity (newVelocity)
   e. Write outgoing waves into both delay lines
   f. Apply nut reflection (sign inversion) at neckDelay end
   g. Apply bridge loss filter at bridgeDelay end
   h. If SUB_HARMONICS > 0: inject sub-harmonic feedback
5. **Downsample from 2x:** Anti-aliased decimation
6. **Apply bridge filter:** Frequency-dependent spectral shaping
7. **Process through body resonator:** Parallel biquad bank (8 sections)
8. **Sum sympathetic strings:** Add passive string resonance
9. **Add bow noise:** Shaped noise mixed at low level
10. **Apply output level:** dB to linear gain
11. **Apply stereo width:** Mid-side processing

**Why order matters:**
- Friction junction MUST be inside oversampled section (nonlinear aliasing)
- Bridge filter processes post-waveguide output (not in 2x loop to save CPU)
- Body resonator MUST be after bridge filter (signal flow integrity)
- Sympathetic strings excited by body output (not raw string output)
- Bow noise is additive post-body (not in feedback loop -- would cause instability)
- Stereo width MUST be last before output (operates on final stereo signal)

### Thread Boundaries

**Audio thread:**
- All DSP processing (friction, waveguide, body, sympathetic, noise, width)
- Parameter reads via `APVTS::getRawParameterValue()->load()` (atomic)
- MIDI message processing in `processBlock()`
- Voice allocation via `juce::Synthesiser`
- Sample-by-sample processing within each voice

**Message thread:**
- Parameter updates from UI via APVTS (atomic writes)
- Preset loading/saving
- UI repaints
- Scala/TUN file loading (parse file, build tuning table)
- Body resonator coefficient recalculation on material/size change
- Trigger coefficient swap to audio thread via atomic pointer

**Communication:**
- APVTS parameters: atomic reads (audio thread) / atomic writes (message thread)
- Body coefficients: double-buffer with atomic pointer swap
- Tuning table: atomic pointer swap (message thread builds table, audio thread reads)
- Friction tier selection: atomic int (0=core, 1=enhanced, 2=quality)
- No mutexes on audio thread -- all communication lock-free

## Implementation Risks

### Nonlinear Friction Junction

**Complexity:** HIGH

**Risk Level:** HIGH

**Risk factors:**
1. Implicit nonlinear equation at every sample (circular dependency bow<->string)
2. Newton-Raphson convergence not guaranteed for all parameter combinations
3. Elasto-plastic bristle state can inject energy if passivity not maintained
4. Three friction tiers adds implementation and testing complexity
5. Friedlander ambiguity (3 intersection points) requires hysteresis tracking

**Alternative approaches:**
1. **Memoryless table only (STK approach):** Avoids implicit equation entirely. Lower quality but guaranteed stable and O(1).
2. **Precomputed 2D lookup table:** Offline-solve (v_delta, F_bow) grid, bilinear interpolate at runtime. O(1) with NR-quality results.
3. **Single-tier only:** Skip enhanced/quality tiers. Ship with core tier only for v1.0, add tiers in v1.x.

**Fallback architecture:**
- **Primary:** Enhanced hyperbolic (core) + optional NR-solved elasto-plastic (enhanced) + optional thermal (quality)
- **Fallback 1:** If NR diverges -> clamp and use previous sample's solution
- **Fallback 2:** If elasto-plastic causes instability -> disable, use core-only
- **Fallback 3:** If all advanced friction fails -> STK bow table (proven stable for 30+ years)

**Mitigation strategy:**
1. Implement core tier first, validate sound quality before adding tiers
2. STK source code provides working reference implementation
3. Clamp all state variables (z, T) to prevent runaway
4. Limit NR iterations to 6, bail out with last valid solution
5. Add passivity fix from recent research (velocity-dependent damping)

### Morphable Body Resonator

**Complexity:** MEDIUM

**Risk Level:** MEDIUM

**Risk factors:**
1. Coefficient interpolation between banks can produce invalid filter states
2. Filter stability not guaranteed for all interpolated coefficient sets
3. Level normalization during morph requires careful gain compensation
4. 8 parallel biquads is moderate CPU (but manageable)

**Alternative approaches:**
1. **Preset-only (no morphing):** Discrete body presets with crossfade between them. Simpler but loses continuous morph.
2. **Convolution-based body:** Short IR convolution (~50ms) instead of biquad bank. More realistic but not morphable.
3. **Fewer biquads:** 4-6 instead of 8 sections. Lower accuracy but reduces coefficient management complexity.

**Fallback architecture:**
- **Primary:** 8 parallel biquads with lerp coefficient morphing
- **Fallback:** 6 biquads with discrete preset banks (crossfade audio output between presets rather than interpolating coefficients)

**Mitigation strategy:**
1. Validate filter stability after every coefficient interpolation (check pole locations)
2. Use JUCE's `makePeakFilter` to recalculate from interpolated freq/Q/gain (safer than raw coefficient lerp)
3. Test morphing across full range with sine sweeps to catch resonance/instability issues

### Multi-String Management (1-4 Active + 0-12 Sympathetic)

**Complexity:** HIGH

**Risk Level:** MEDIUM

**Risk factors:**
1. Up to 16 waveguide strings running simultaneously (4 active + 12 sympathetic)
2. Voice allocation with multiple strings per note is non-standard
3. CPU budget: 4 active strings at quality tier + 12 sympathetic could exceed 20% CPU
4. String-to-string coupling (active strings affect each other through bridge)

**Alternative approaches:**
1. **Fixed string count:** Always 1 string (monophonic). Simplest, lowest CPU.
2. **Capped sympathetic:** Maximum 4 sympathetic strings instead of 12. Reduces CPU ceiling.
3. **Simplified sympathetic:** Comb filter approximation instead of full waveguide per sympathetic string.

**Fallback architecture:**
- **Primary:** 1-4 active waveguide strings + 0-12 passive sympathetic strings
- **Fallback 1:** Cap at 2 active + 6 sympathetic if CPU target exceeded
- **Fallback 2:** Replace sympathetic strings with resonant comb filter bank (single filter, not per-string)

**Mitigation strategy:**
1. Profile CPU per string early in development
2. Implement gating (skip sympathetic strings below energy threshold)
3. Start with 1 active string, add multi-string in Phase 3.3

### Microtonal Tuning Integration

**Complexity:** LOW

**Risk Level:** LOW

**Risk factors:**
1. Shared module at `modules/tuning/scala-tuning-engine` -- dependency on external code
2. MTS-ESP requires dynamic library loading at runtime

**Alternative approaches:**
1. **12TET only for v1.0:** Skip Scala/MTS-ESP, add in v1.x
2. **Scala only (no MTS-ESP):** File-based tuning without runtime library dependency

**Fallback architecture:**
- If tuning engine fails to load Scala file: fall back to 12TET
- If MTS-ESP library unavailable: disable option in UI, use 12TET

**Mitigation strategy:**
1. Tuning engine is proven (used in O-Prism and O-Lyrica)
2. Test with known Scala files (pythagorean, meantone, just intonation)

### 2x Oversampling Latency

**Complexity:** LOW

**Risk Level:** LOW

**Risk factors:**
1. `juce::dsp::Oversampling` adds latency that must be reported to host
2. Brief states "0 samples latency" but oversampling latency is unavoidable

**Mitigation strategy:**
1. Report latency via `setLatencySamples(oversampling.getLatencyInSamples())` in prepareToPlay
2. Document that "0 algorithmic latency" refers to waveguide causality, not oversampling filter

## Architecture Decisions

### Decision 1: Tiered Friction Model

**Decision:** Implement three friction tiers (core/enhanced/quality) selectable at runtime rather than a single fixed model.

**Rationale:**
- Core tier provides stable baseline with minimal CPU
- Enhanced tier adds attack quality (elasto-plastic) for users who want it
- Quality tier adds subtle sustained tone evolution (thermal) for studio use
- Users can trade quality for CPU based on their system and use case
- Mirrors professional plugin design (FabFilter, iZotope offer quality modes)

**Alternatives considered:**
1. **Single model (thermal only):** Why rejected: ~5x CPU of core tier, many users don't need it
2. **Single model (core only):** Why rejected: Limits expressiveness, attack transients lack "bite"
3. **Automatic tier selection:** Why rejected: Unpredictable CPU usage, user should control

**Tradeoffs accepted:**
- More code to implement and test (3 friction models vs 1)
- UI needs quality selector control
- Acceptable because: models are additive (enhanced = core + bristle state, quality = enhanced + thermal)

### Decision 2: Morphable Body Resonator via Biquad Bank

**Decision:** Use parallel biquad bank with coefficient interpolation rather than convolution-based body.

**Rationale:**
- Convolution is more accurate but NOT morphable (fixed IR per body type)
- Biquad bank allows continuous morphing between body types (key differentiator)
- Lower CPU than convolution for equivalent perceptual quality
- Body morphing is identified as the #1 market differentiator (no competitor offers this)

**Alternatives considered:**
1. **Convolution with IR crossfade:** Why rejected: Crossfading IRs produces artifacts, not true morphing
2. **Modal synthesis:** Why rejected: Similar to biquad bank but less established in JUCE
3. **Hybrid (biquad + short convolution):** Considered for future enhancement (high-freq detail via short IR)

**Tradeoffs accepted:**
- Less accurate than measured IR for any single instrument
- 8 biquads approximates body, doesn't capture all modes
- Acceptable because: morph capability outweighs per-instrument accuracy

### Decision 3: juce::Synthesiser Pattern for Voice Management

**Decision:** Use `juce::Synthesiser` + custom `SynthesiserVoice` for voice allocation, same pattern as O-Lyrica.

**Rationale:**
- Proven pattern in codebase (O-Lyrica, O-Prism, O-Bells, OrganicHats)
- Built-in MIDI handling, voice stealing, note management
- Per-voice rendering via `renderNextBlock()`
- APVTS pointer per voice (pattern from O-Lyrica)
- MPE support via `juce::Synthesiser`'s built-in MPE handling

**Alternatives considered:**
1. **Custom voice manager:** Why rejected: Reinvents wheel, O-Lyrica pattern is proven
2. **Single monophonic voice:** Why rejected: Brief specifies 1-4 strings with optional double stops

### Decision 4: 2x Oversampling (Not 4x or None)

**Decision:** Use 2x internal oversampling for the friction junction / waveguide loop.

**Rationale:**
- The nonlinear friction junction generates aliasing at native sample rates
- 2x provides adequate aliasing reduction for the hyperbolic/elasto-plastic models
- Cost: ~2.2x CPU (acceptable)
- 4x would be ~4.4x CPU (too expensive for multi-string)
- No oversampling: audible aliasing artifacts especially at high frequencies

**Alternatives considered:**
1. **No oversampling:** Why rejected: Audible aliasing in friction junction, especially at high pitches
2. **4x oversampling:** Why rejected: CPU cost too high for 4 active strings
3. **Oversampling only for friction, not waveguide:** Possible optimization for later (complex to separate)

### Decision 5: Allpass (Thiran) Interpolation for Delay Lines

**Decision:** Use Thiran allpass interpolation for fractional delay instead of linear or Lagrange.

**Rationale:**
- Thiran provides flat magnitude response (no spectral coloring from interpolation)
- Critical for bowed strings where harmonics extend to high frequencies
- Linear interpolation acts as lowpass filter, dulling high harmonics
- Lagrange3rd acceptable but Thiran is native in `juce::dsp::DelayLine`

**Alternatives considered:**
1. **Linear interpolation:** Why rejected: Acts as lowpass, dulls harmonics, audible in high-pitched strings
2. **Lagrange3rd:** Acceptable quality, slightly more CPU than Thiran for equivalent accuracy

## Special Considerations

### Thread Safety
- All parameter reads use atomic `getRawParameterValue()->load()`
- Body resonator coefficients: double-buffer with atomic pointer swap (message thread calculates, audio thread reads)
- Friction tier selection: `std::atomic<int>` (0/1/2)
- Tuning table: atomic pointer swap (same pattern as O-Prism TuningEngine)
- Bristle displacement (z) and temperature (T_contact) are per-voice state -- no cross-thread access
- Voice allocation via juce::Synthesiser handles locking internally

### Performance
- Estimated CPU per active string (core tier): ~2% single core at 44.1 kHz
- Estimated CPU per active string (quality tier): ~5% single core at 44.1 kHz
- Estimated CPU for body resonator (8 biquads): ~0.5%
- Estimated CPU per sympathetic string: ~0.1-0.3%
- Total estimated (2 strings core + body + 4 sympathetic): ~6%
- Total estimated (4 strings quality + body + 12 sympathetic): ~25%
- Hot paths: friction junction inner loop (runs at 2x rate), waveguide read/write
- Optimization: SIMD for parallel biquad processing (body resonator), gating for sympathetic strings

### Denormal Protection
- Use `juce::ScopedNoDenormals` in `processBlock()`
- Delay lines can produce denormals during decay -- JUCE DelayLine handles internally
- Bristle displacement z: clamp to prevent tiny values near zero
- Temperature T_contact: clamp to [T_ambient, 200] -- no denormal risk
- Body resonator biquads: JUCE IIR::Filter handles denormals internally

### Sample Rate Handling
- All delay line sizes recalculated in `prepareToPlay()`
- Internal sample rate = hostSampleRate * 2 (oversampling)
- Maximum delay size: `internalSampleRate / 20.0` (C0 at ~16 Hz)
- Body resonator coefficients recalculated at native sample rate
- Bridge filter coefficients recalculated at internal sample rate (inside oversampled loop)
- Sympathetic strings: delay sizes at native sample rate (not oversampled)

### Latency
- Oversampling latency: `oversampling.getLatencyInSamples()` (typically ~8 samples for 2x with halfband)
- Waveguide latency: 0 algorithmic (causal system)
- Total reported: oversampling latency only
- Report via `setLatencySamples()` in `prepareToPlay()` (NOT virtual override -- juce8-critical-patterns.md)
