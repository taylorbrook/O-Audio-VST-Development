## Core Components

### 1. Reed Model (Exciter)

- **JUCE Class:** Custom implementation -- no JUCE class for reed excitation
- **Purpose:** Full mass-spring-damper reed model with Guillemain confined jet parameter (Psi) for single-to-double reed morphing
- **Parameters Affected:** BREATH_PRESSURE, EMBOUCHURE, REED_HARDNESS, REED_OPENING, REED_MASS, REED_DAMPING, DOUBLE_REED, ATTACK_CHIFF
- **Configuration:**
  - Reed displacement ODE: `mu_r * d2x/dt2 + g_eff * dx/dt + k_eff * x = (p_mouth - p_bore) * A_reed`
  - Embouchure modifies effective parameters:
    - `g_eff = g_r + g_lip` (total damping)
    - `k_eff = k_r + k_lip` (total stiffness)
    - `H_eff = H - x_lip` (reduced rest opening from lip force)
  - Reed closure: `x = max(x, -(H_eff + 0.001))` -- reed cannot pass through mouthpiece
  - REED_HARDNESS (0-1) maps to k_r range: soft cane to stiff synthetic
  - REED_MASS (0-1) maps to mu_r: near-zero (static reed behavior) to heavy (prominent reed resonance)
  - REED_DAMPING (0-1) maps to g_r: low (ringy reed) to high (muted, bore-driven)
  - REED_OPENING (0-1) maps to H: small (easy onset, bright) to large (hard onset, soft)
  - ATTACK_CHIFF (0-1) controls pressure overshoot envelope at note onset (0-30% overshoot, ~20-50ms)
  - Discretization: symplectic Euler for energy preservation
  - Cost: ~25 ops per sample (one 2nd-order ODE)

### 2. Nonlinear Junction (Reed-Bore Coupling)

- **JUCE Class:** Custom implementation -- core nonlinear DSP
- **Purpose:** Compute volume flow through reed channel using Bernoulli equation with Guillemain confinement
- **Parameters Affected:** BREATH_PRESSURE, DOUBLE_REED, EMBOUCHURE
- **Configuration:**
  - **Primary model:** Polynomial approximation of reed reflection function
    - Volume flow: `u(t) = sign(dp) * alpha * S_i(t) * sqrt(2 * |dp| / (rho * (1 + Psi * alpha^2 * S_i^2 / S_r^2)))`
    - S_i(t) = w * max(x(t) + H_eff, 0) -- instantaneous reed channel opening
    - alpha = vena contracta ratio (~0.6-0.8)
    - Psi = DOUBLE_REED parameter (0 = single reed, >0 = double reed character)
    - Polynomial fit (cubic) for fast evaluation: ~4 multiplies + 3 adds
  - **Alternative (high quality):** Newton-Raphson iteration for full dynamic reed
    - 2-3 iterations typical, previous sample as initial guess
    - ~30 ops per sample
    - Activated for 4x oversampling mono mode
  - Psi value mapping for instrument character:
    - 0: Pure single-reed (clarinet, saxophone)
    - 0.1-0.3: Mild double-reed (duduk, piri)
    - 0.3-0.6: Strong double-reed (oboe, bassoon)
    - 0.6+: Extreme confinement (zurna, shehnai -- piercing)
  - Output: reflection coefficient applied to incoming bore wave, outgoing wave injected into bore
  - Stability: clamp reed displacement, enforce minimum bore loss, energy-preserving discretization

### 3. Bore Waveguide (Resonator)

- **JUCE Class:** `juce::dsp::DelayLine<float, juce::dsp::DelayLineInterpolationTypes::Thiran>` (allpass interpolation for fractional delay)
- **Module:** `juce_dsp`
- **Purpose:** Model wave propagation in the bore via bidirectional delay lines with parameterized taper
- **Parameters Affected:** BORE_CHARACTER, BORE_LENGTH, BORE_DIAMETER, BORE_PROFILE, REVERSE_BORE, INFINITE_SUSTAIN
- **Configuration:**
  - Two delay lines per bore: forward (reed-to-bell) and backward (bell-to-reed)
  - Delay length determines pitch: `N = internalSampleRate / f0 - filter_delay_compensation`
  - Thiran allpass interpolation for sub-sample pitch accuracy (critical for tuning)
  - Maximum delay size: `internalSampleRate / 20.0` (lowest note ~20Hz)
  - **Bore taper implementation (Strategy B initial, upgrade to C):**
    - Strategy B (default): Cylindrical waveguide + conical correction filter
      - Correction filter boosts even harmonics proportional to bore_taper
      - Low CPU, good timbral accuracy
    - Strategy C (upgrade path): True conical waveguide sections
      - Spherical wave scaling: `p_plus_out = (r_in / r_out) * delay.read()`
      - Higher accuracy for conical bore instruments
  - BORE_CHARACTER (0-1) controls taper: 0=cylindrical, 1=full cone
  - REVERSE_BORE (0-1) extends into negative taper (hichiriki-like -- narrows at bottom)
  - BORE_LENGTH (0-1) scales effective tube length (register density)
  - BORE_DIAMETER (0-1) controls viscothermal loss filter and impedance
  - INFINITE_SUSTAIN (0-1) reduces bore loop loss toward zero (reduces damping)
  - BORE_PROFILE choice: Simple (single taper) vs Multi-segment (throat/body/bell sections)

### 4. Viscothermal Loss Filter

- **JUCE Class:** `juce::dsp::IIR::Filter<float>` with `juce::dsp::IIR::Coefficients<float>`
- **Module:** `juce_dsp`
- **Purpose:** Model frequency-dependent energy loss from thermal conduction and viscous friction in bore walls
- **Parameters Affected:** BORE_DIAMETER
- **Configuration:**
  - One-pole lowpass approximation per delay line loop
  - Loss proportional to `sqrt(f)` and inversely proportional to bore diameter
  - Narrow bores (oboe, clarinet) = more loss = quieter, more intimate
  - Wide bores (bass clarinet, baritone sax) = less loss = louder, more projected
  - Coefficients recalculated on BORE_DIAMETER change (not per-sample)
  - Combined with bore loop gain to ensure total loop gain < 1.0 (stability)

### 5. Bell Radiation Filter

- **JUCE Class:** `juce::dsp::IIR::Filter<float>` with `juce::dsp::IIR::Coefficients<float>`
- **Module:** `juce_dsp`
- **Purpose:** Frequency-dependent reflection at bell end (lowpass) and radiation to output
- **Parameters Affected:** BELL_SIZE
- **Configuration:**
  - First-order allpass reflection filter: `H_r(z) = -(a + z^-1) / (1 + a*z^-1)`
  - `a` coefficient controlled by BELL_SIZE: a ~ -0.99 (small bell) to -0.9 (large bell)
  - Radiated sound = incident wave + reflected wave (complementary filter)
  - Small bell = more internal resonance, darker external sound, less projection
  - Large bell = brighter radiation, more projected, more high-frequency output
  - Special case: BELL_SIZE=0 for instruments with no bell (duduk, piri) -- near-total reflection
  - Coefficients recalculated on BELL_SIZE change

### 6. Tone Hole Lattice

- **JUCE Class:** Custom implementation (three-port scattering junctions)
- **Purpose:** Model 2-4 virtual tone holes for spectral character, overblowing, and legato transitions
- **Parameters Affected:** TONE_HOLE_CUTOFF, REGISTER_HOLE
- **Configuration:**
  - 2-4 tone holes as Keefe three-port scattering junctions
  - Each hole has continuous `opening` parameter (0.0-1.0) for legato and half-holing
  - Scattering coefficient interpolated between open and closed states
  - Radiated sound from open holes contributes to output
  - TONE_HOLE_CUTOFF (200-8000 Hz) sets spectral envelope from open holes:
    - Oboe/Clarinet: ~1500 Hz
    - Saxophone: ~800-1200 Hz
    - Bassoon: ~600 Hz
    - Duduk: ~2000 Hz (fewer/smaller holes)
  - REGISTER_HOLE (0-1): opens register vent near reed end
    - Cylindrical bore: forces 3rd harmonic (overblows at 12th)
    - Conical bore: forces 2nd harmonic (overblows at octave)
    - Behavior auto-adapts based on BORE_CHARACTER setting
  - Cost: ~5-10 multiplies per tone hole per sample (~20-40 total)

### 7. Breath Noise Generator

- **JUCE Class:** Custom implementation using `juce::Random` for noise source + `juce::dsp::IIR::Filter<float>` for shaping
- **Module:** `juce_dsp`
- **Purpose:** Air turbulence noise adding breathiness, attack chiff, and realistic texture
- **Parameters Affected:** AIR_NOISE, BREATH_PRESSURE
- **Configuration:**
  - White noise source filtered to breath noise spectrum (bandpass ~1-8 kHz)
  - Amplitude modulated by volume flow velocity (faster air = more turbulence)
  - AIR_NOISE (0-1) controls overall breath-to-tone ratio
  - At note onset: short noise burst for attack chiff (controlled by ATTACK_CHIFF)
  - At soft playing: noise becomes proportionally louder (subtone characteristic)
  - Mixed into excitation signal before reed-bore junction (NOT in waveguide loop)
  - Level: typically 5-20% of main signal depending on AIR_NOISE setting

### 8. Mouthpiece Volume (Helmholtz Resonance)

- **JUCE Class:** Custom implementation (single compliance element)
- **Purpose:** Model air volume in mouthpiece between reed and bore entrance
- **Parameters Affected:** MOUTHPIECE_VOL
- **Configuration:**
  - Compliance: `C_mp = volume / (rho * c^2)`
  - Pressure update: `p_mp += (u_reed - u_bore) / (C_mp * sampleRate)`
  - Slightly lowers playing frequency (pitch correction)
  - Creates secondary resonance for upper harmonic coloring
  - In conical instruments: compensates for truncated cone tip
  - MOUTHPIECE_VOL (0-1) scales volume from small (bright, minimal effect) to large (warmer, more correction)
  - Cost: ~5 ops per sample

### 9. Vibrato System

- **JUCE Class:** Custom LFO implementation (sine oscillator)
- **Purpose:** Multi-source vibrato modulation
- **Parameters Affected:** VIBRATO_DEPTH, VIBRATO_RATE, VIBRATO_SOURCE
- **Configuration:**
  - LFO: `vibrato = sin(2 * PI * rate * t) * depth`
  - Three modulation targets (VIBRATO_SOURCE choice):
    - 0 = Lip vibrato: modulates embouchure (H_eff, k_eff) -- jaw vibrato, most common
    - 1 = Breath vibrato: modulates mouth pressure -- diaphragm vibrato
    - 2 = Throat vibrato: modulates bore impedance -- classical oboe style
  - VIBRATO_RATE (1-10 Hz) controls LFO frequency
  - VIBRATO_DEPTH (0-1) controls modulation depth
  - Maps to MPE Y-axis or CC77/CC76
  - Cost: ~3 ops per sample (sine LFO)

### 10. Growl/Vocal Coupling

- **JUCE Class:** Custom implementation (secondary oscillator)
- **Purpose:** Model vocal fold coupling for growl and multiphonic effects
- **Parameters Affected:** GROWL_AMOUNT
- **Configuration:**
  - Secondary sine oscillator at vocal frequency
  - Vocal frequency defaults to ~120 Hz (male fundamental) but auto-tracks relative to played pitch
  - Coupling modulates mouth pressure: `p_growl = p_mouth * (1 + coupling * vocal_osc * 0.3)`
  - GROWL_AMOUNT (0-1) controls coupling strength
  - At low coupling: subtle amplitude modulation (beating)
  - At high coupling: distinct sum/difference tones (multiphonics)
  - Maps to CC80
  - Cost: ~5 ops per sample

### 11. Flutter Tongue

- **JUCE Class:** Custom implementation (low-frequency oscillator)
- **Purpose:** ~25 Hz pressure modulation simulating tongue flutter
- **Parameters Affected:** FLUTTER_TONGUE
- **Configuration:**
  - Square-ish LFO at ~25 Hz modulating breath pressure
  - FLUTTER_TONGUE (0-1) controls modulation depth
  - Depth range: 0-40% pressure modulation
  - Filtered to avoid aliasing (smoothed square wave)
  - Cost: ~3 ops per sample

### 12. Subtone Mode

- **JUCE Class:** Custom implementation (parameter modifier)
- **Purpose:** Saxophone subtone technique -- reed never fully closes
- **Parameters Affected:** SUBTONE
- **Configuration:**
  - Increases lip damping: `g_lip_subtone = g_lip * (1 + subtone * 5.0)`
  - Reduces effective mouth pressure: `p_mouth_subtone = p_mouth * (1 - subtone * 0.3)`
  - Increases breath noise: `noise_subtone = noise * (1 + subtone * 3.0)`
  - Result: reed oscillates without beating, soft airy tone
  - SUBTONE (0-1) blends from normal to full subtone
  - Cost: ~3 ops per sample (parameter modification only)

### 13. Dual Bore System

- **JUCE Class:** Second `juce::dsp::DelayLine<float, juce::dsp::DelayLineInterpolationTypes::Thiran>` pair
- **Module:** `juce_dsp`
- **Purpose:** Second parallel waveguide bore for arghul/launeddas-style drone
- **Parameters Affected:** DUAL_BORE, DRONE_PITCH, FEEDBACK_PATH
- **Configuration:**
  - When DUAL_BORE enabled: second complete bore waveguide instantiated
  - DRONE_PITCH (-24 to +24 semitones) offsets second bore pitch from primary
  - Second bore shares the same reed excitation (simplified -- single reed drives both bores)
  - Second bore output mixed with primary bore output
  - FEEDBACK_PATH (0-1) controls cross-modulation between the two bores
  - When DUAL_BORE off: second bore completely bypassed (no CPU cost)
  - Cost when active: approximately doubles bore DSP cost

### 14. 2x/4x Internal Oversampling

- **JUCE Class:** `juce::dsp::Oversampling<float>`
- **Module:** `juce_dsp`
- **Purpose:** Reduce aliasing from nonlinear reed-bore coupling
- **Parameters Affected:** OVERSAMPLING (choice)
- **Configuration:**
  - 2x oversampling default (polyphase halfband filter)
  - 4x oversampling for monophonic high-quality mode
  - Process reed model + junction + bore waveguide at oversampled rate
  - Downsample output with built-in anti-aliasing
  - Latency reported via `setLatencySamples()` in `prepareToPlay()`
  - Reed nonlinearity is relatively mild -- 2x is sufficient for polyphonic use
  - 4x reserved for mono mode (CPU budget allows it)
  - NOTE: oversampling latency is acceptable and reported to host (waveguide itself is zero-latency)

### 15. Instrument Morph System

- **JUCE Class:** Custom implementation (macro parameter interpolation)
- **Purpose:** Crossfade full parameter sets between instrument presets
- **Parameters Affected:** INSTRUMENT_PRESET
- **Configuration:**
  - INSTRUMENT_PRESET (choice 0-20) selects target instrument configuration
  - When changing preset: smooth interpolation of ALL reed/bore/bell parameters over ~100ms
  - Preset data: stored as static arrays of parameter target values
  - Interpolation: linear lerp per parameter, coefficient recalculation after interpolation
  - Presets define: bore_taper, bore_length, bore_diameter, psi, reed_hardness, reed_opening, bell_size, tone_hole_cutoff, etc.
  - Does NOT change MIDI mapping or expression controls (those remain user-configured)
  - Cost: negligible (parameter interpolation, not audio-rate)

### 16. Microtonal Tuning System

- **JUCE Class:** Shared module at `modules/tuning/scala-tuning-engine`
- **Module:** Custom (pre-existing shared module)
- **Purpose:** Support Scala/TUN import, MTS-ESP, and standard 12TET tuning
- **Parameters Affected:** REFERENCE_PITCH, TUNING_SYSTEM
- **Configuration:**
  - TUNING_SYSTEM choice: 0 = Scala/TUN file, 1 = MTS-ESP, 2 = 12TET (default)
  - REFERENCE_PITCH: 220-880 Hz (default 440 Hz)
  - TuningEngine pointer passed to each voice (same pattern as O-Prism / O-Lyrica)
  - Scala file loading on message thread, tuning table passed to audio thread atomically
  - Frequency lookup: `f0 = tuningEngine.getFrequency(noteNumber)` in voice noteOn

## Processing Chain

```
MIDI/MPE Input
     |
     v
[Voice Allocation] -- Mono mode: single voice with legato/retrigger
     |                 Poly mode: up to MAX_VOICES independent voices
     |
     v (per voice)
[Breath Pressure Envelope] <-- BREATH_PRESSURE, velocity, CC2/MPE Pressure
     |
     +-- [Breath Noise Generator] <-- AIR_NOISE
     |         |
     |         v
     |   (mixed into excitation)
     |
     +-- [Vibrato LFO] <-- VIBRATO_DEPTH, VIBRATO_RATE, VIBRATO_SOURCE
     |         |
     |         v
     |   (modulates lip/breath/throat)
     |
     +-- [Growl Oscillator] <-- GROWL_AMOUNT
     |         |
     |         v
     |   (modulates mouth pressure)
     |
     +-- [Flutter Tongue LFO] <-- FLUTTER_TONGUE
     |         |
     |         v
     |   (modulates mouth pressure)
     |
     v
[Reed Model (Mass-Spring-Damper)] <-- REED_HARDNESS, REED_MASS, REED_DAMPING,
     |                                 REED_OPENING, EMBOUCHURE, SUBTONE
     |
     |   +------ [2x/4x Oversampling Upsample] ------+
     |   |                                             |
     v   v                                             |
[Nonlinear Junction (Bernoulli + Psi)] <-- DOUBLE_REED |
     |      Reed reflection + volume flow               |
     |      Coupled to bore waveguide                   |
     |                                                  |
     +--> [Mouthpiece Volume] <-- MOUTHPIECE_VOL       |
     |         |                                        |
     v         v                                        |
[Bore Waveguide] <-- BORE_CHARACTER, BORE_LENGTH,      |
     |                BORE_DIAMETER, BORE_PROFILE,      |
     |                REVERSE_BORE, INFINITE_SUSTAIN    |
     |                                                  |
     +--> [Viscothermal Loss Filter] <-- BORE_DIAMETER  |
     |                                                  |
     +--> [Tone Hole Lattice] <-- TONE_HOLE_CUTOFF     |
     |         |                                        |
     |         +--> [Register Hole] <-- REGISTER_HOLE   |
     |                                                  |
     +--> [Bell Radiation Filter] <-- BELL_SIZE         |
     |                                                  |
     |   +------ [2x/4x Oversampling Downsample] ------+
     |
     +--?--> [Dual Bore Waveguide] <-- DUAL_BORE, DRONE_PITCH, FEEDBACK_PATH
     |              (optional second bore, mixed with primary)
     |
     v
[Output Level] <-- OUTPUT_GAIN
     |
     v
Output (Mono -> stereo via slight decorrelation for poly, direct mono for mono mode)
```

**Routing notes:**
- Reed model, nonlinear junction, and bore waveguide operate at oversampled rate (2x default, 4x mono)
- Tone hole lattice is inside the bore waveguide loop (between delay line segments)
- Bell radiation filter is at the output end of the bore waveguide
- Viscothermal loss is inside the bore loop (each delay line pass)
- Mouthpiece volume is between the reed junction and the bore entrance
- Breath noise is mixed into excitation BEFORE the nonlinear junction
- Vibrato, growl, flutter modulate parameters feeding into the reed model
- Dual bore (when active) runs in parallel, output mixed with primary bore
- Feedback path (FEEDBACK_PATH) creates cross-modulation between dual bores
- Instrument morph system controls ALL reed/bore/bell parameters simultaneously
- Subtone modifies reed parameters (not a separate processing stage)
- INFINITE_SUSTAIN modifies bore loop loss (inside waveguide loop)
- Mono mode: single voice, legato transitions via smooth tone hole opening
- Poly mode: independent voice instances, each with full reed+bore chain

## System Architecture

### MIDI Routing

**Input handling:** MPE-aware (per-note expression) with legacy MIDI CC fallback and breath controller integration

**Note mapping:**
- MIDI note number determines pitch (f0 = tuningEngine.getFrequency(noteNumber))
- Velocity maps to tongue articulation force (attack overshoot intensity)
- Channel handling: MPE mode (per-note channel) or legacy omni mode

**MPE Dimensions:**

| MPE Dimension | Target Parameter | Range |
|---------------|-----------------|-------|
| Note velocity | Attack chiff intensity | 0-127 -> 0-100% overshoot |
| Pressure (Z) | Breath pressure | 0-127 -> 0.0-1.0 |
| Slide (Y / CC74) | Embouchure / brightness | 0-127 -> 0.0-1.0 |
| Pitch bend (X) | Pitch bend / vibrato | +/- 48 semitones |

**Legacy CC Mapping:**

| CC | Target | Description |
|----|--------|-------------|
| CC1 | Embouchure | Mod wheel -> lip force |
| CC2 | Breath pressure | Breath controller -> p_mouth |
| CC11 | Expression | Dynamics (when no breath controller) |
| CC74 | Embouchure (MPE Y) | Brightness |
| CC76 | Vibrato rate | |
| CC77 | Vibrato depth | |
| CC80 | Growl amount | Vocal coupling |

**Breath controller integration (critical):**
- CC2 maps directly to mouth pressure with configurable curve (linear/exponential/S-curve)
- When no breath controller detected: velocity sets initial attack, sustain level for held notes, CC11 for dynamics
- Compatible with: TEControl, Akai EWI, Roland Aerophone, Sylphyo, Warbl

**Mono mode specifics:**
- Single voice, legato transitions: smooth delay line interpolation between pitches
- Retrigger on non-legato notes: attack chiff + fresh reed onset
- Last-note priority for overlapping notes
- Portamento: smooth pitch interpolation via delay line length ramping

**JUCE classes:**
- `juce::MPESynthesiser` -- MPE-aware voice allocation
- `juce::MPESynthesiserVoice` -- per-voice processing with 6 pure virtual methods
- `juce::MidiBuffer` -- MIDI event iteration in processBlock
- `juce::MidiMessage` -- individual message parsing
- `enableLegacyMode()` on MPESynthesiserBase for standard MIDI fallback

### State Persistence

**What state is saved:**
- APVTS parameters: All 35 automatable parameters (automatic via APVTS)
- Custom state:
  - Scala/TUN file path (if tuning system = Scala)
  - Breath controller curve selection (linear/exponential/S-curve)
  - Last used instrument preset index

**Serialization format:**
- APVTS parameters: Automatic via `AudioProcessorValueTreeState`
- Custom state: `juce::ValueTree` with XML serialization

**JUCE classes:**
- `juce::AudioProcessorValueTreeState` -- parameter persistence (automatic)
- `juce::ValueTree` -- custom state tree
- `juce::File` -- Scala/TUN file path storage

**Save/restore methods:**
- `getStateInformation(MemoryBlock& destData)` -- serialize APVTS + custom ValueTree
- `setStateInformation(const void* data, int sizeInBytes)` -- deserialize and restore

**Restore behavior:**
- Missing Scala file: fall back to 12TET, show warning in UI
- Invalid state data: use defaults (all parameters at default values)
- Version migration: future-proofed via ValueTree versioning

## Algorithm Details

### Reed Model (Mass-Spring-Damper)

**Algorithm:** Second-order ODE for reed tip displacement, discretized via symplectic Euler

**Implementation notes:**
- `force = (p_mouth - p_bore) * A_reed`
- `x_ddot = (force - g_eff * x_dot - k_eff * x) / mu_r`
- `x_dot += x_ddot / sampleRate` (velocity update first -- symplectic Euler)
- `x += x_dot / sampleRate` (position update second)
- `x = max(x, -(H_eff + 0.001))` (closure limit)
- When REED_MASS approaches zero, mu_r -> epsilon (small positive), converging on static reed
- Cost: ~25 ops/sample

### Bernoulli Flow with Guillemain Confinement

**Algorithm:** Modified Bernoulli equation with confinement loss parameter Psi

**Implementation notes:**
- `S_i = w * max(x + H_eff, 0)` (instantaneous opening area)
- `dp = p_mouth - p_bore` (pressure difference)
- `u = sign(dp) * alpha * S_i * sqrt(2 * |dp| / (rho * (1 + Psi * alpha^2 * S_i^2 / S_r^2)))`
- For polynomial approximation: fit cubic to u(dp) curve for current reed state
- For Newton-Raphson: iterate `f(x) = 0` with Jacobian, 2-3 iterations, previous sample as guess
- sqrt approximation: use fast inverse sqrt for performance
- The `1 + Psi * ...` denominator is what makes double reeds sound different -- it creates additional energy loss that enriches upper harmonics and affects attack

### Conical Bore Correction (Strategy B)

**Algorithm:** Cylindrical waveguide with spectral correction filter for conical behavior

**Implementation notes:**
- Base cylindrical waveguide (two fractional delay lines)
- Correction filter derived from ratio of conical to cylindrical impedance
- Filter progressively boosts even harmonics as BORE_CHARACTER increases
- At BORE_CHARACTER=0: filter is flat (pure cylindrical, odd harmonics dominate)
- At BORE_CHARACTER=1: filter fully corrects to conical spectrum (all harmonics)
- Implementation: biquad shelving filter with gain proportional to bore_taper
- Coefficients recalculated when BORE_CHARACTER changes

### Tone Hole Scattering (Keefe Model)

**Algorithm:** Three-port scattering junction per tone hole

**Implementation notes:**
- Per hole: `p_junction = rho_scat * (p_plus_left + p_minus_right)`
- `p_minus_left = p_junction - p_plus_left`
- `p_plus_right = p_junction - p_minus_right`
- `rho_scat = lerp(closed_scatter, open_scatter, hole_opening)`
- `p_radiated = (1 - rho_scat) * (p_plus_left + p_minus_right)` (from open holes)
- Register hole: special tone hole near reed with small opening for overblow mode
- Cost: ~5-10 multiplies per hole per sample

## Integration Points

### Feature Dependencies

- Reed model -> Nonlinear junction: Reed displacement determines channel opening for flow calculation
- Nonlinear junction -> Bore waveguide: Volume flow from junction drives bore, bore pressure feeds back to junction
- Bore waveguide -> Tone hole lattice: Tone holes are embedded within bore (between delay line segments)
- Bore waveguide -> Bell radiation: Bell filter at output end of bore
- Bore waveguide -> Viscothermal loss: Loss filter inside bore loop
- Mouthpiece volume -> Junction/Bore: Between junction output and bore entrance
- Breath noise -> Junction: Mixed into excitation before junction
- Vibrato/Growl/Flutter -> Reed model: Modulate reed input parameters
- Dual bore -> Primary bore: Shares reed excitation, outputs mixed
- Instrument morph -> All parameters: Macro that crossfades target values
- Tuning system -> Voice pitch: Determines delay line length via frequency

### Parameter Interactions

- BREATH_PRESSURE + REED_OPENING: Together determine operating regime (subtone vs beating vs overblown)
- BORE_CHARACTER + REGISTER_HOLE: Bore type determines overblow interval (12th vs octave)
- DOUBLE_REED (Psi) + BORE_CHARACTER: Together define instrument family identity
- INFINITE_SUSTAIN + BORE_CHARACTER: Removing loss from cylindrical vs conical bore produces different sustain character
- EMBOUCHURE + REED_HARDNESS: Both affect brightness; high embouchure + soft reed vs low embouchure + hard reed reach similar brightness via different mechanisms
- SUBTONE + REED_OPENING + BREATH_PRESSURE: Subtone requires specific pressure/opening ratio to prevent full reed closure
- DUAL_BORE + FEEDBACK_PATH: Feedback can create instability if both bores have low loss -- FEEDBACK_PATH auto-limits based on INFINITE_SUSTAIN

### Processing Order Requirements

**Sequential processing order (REQUIRED per sample at oversampled rate):**

1. **Read MIDI/expression inputs:** Update breath pressure, embouchure, pitch from latest MIDI/MPE data
2. **Apply modulations:** Vibrato -> target parameter, Growl -> p_mouth, Flutter -> p_mouth
3. **Mix breath noise:** Add turbulence noise scaled by flow to excitation pressure
4. **Compute reed displacement:** Solve reed ODE using current p_mouth and p_bore (from previous sample)
5. **Compute volume flow:** Bernoulli + Psi through current reed channel opening
6. **Update mouthpiece volume:** Helmholtz compliance pressure update
7. **Inject into bore:** New outgoing wave enters bore delay line
8. **Process bore waveguide:** Advance delay lines, apply viscothermal loss
9. **Process tone holes:** Scattering junctions within bore (modify traveling waves)
10. **Process bell reflection:** Frequency-dependent reflection at bell end
11. **Extract output:** Radiated sound = transmitted wave at bell + tone hole radiation
12. **Feed back to reed:** Returning wave from bore becomes p_bore for next sample

**Why order matters:**
- Reed and bore are coupled (implicit): bore pressure feeds back to reed, reed output feeds bore
- Tone holes must be inside bore loop (they modify traveling waves between delay segments)
- Bell reflection determines what returns to bore vs what radiates
- Mouthpiece volume sits between junction and bore entrance (order-sensitive)
- Dual bore (if active): processed in parallel with primary bore, outputs mixed at step 11

### Thread Boundaries

**Audio thread:**
- All DSP processing (reed, junction, bore, tone holes, bell, modulation)
- Parameter reads via `APVTS::getRawParameterValue()->load()` (atomic)
- Sample-by-sample processing in processBlock()
- Voice allocation via juce::MPESynthesiser (handles locking internally)
- MIDI message processing in processBlock()

**Message thread:**
- Parameter updates from UI via APVTS (atomic writes)
- Preset loading/saving
- Instrument morph target selection
- Scala/TUN file loading
- UI repaints

**Background thread:**
- Scala/TUN file parsing (via TuningEngine)
- Tuning table passed to audio thread atomically (pointer swap)

**Communication:**
- APVTS parameters: atomic reads (audio thread) / atomic writes (message thread)
- Tuning table: atomic pointer swap from message thread to audio thread
- Instrument preset target: atomic int (preset index) + parameter interpolation on audio thread
- Breath controller curve: atomic int (curve type selection)

## Implementation Risks

### Reed-Bore Coupling (Nonlinear Junction)

**Complexity:** HIGH

**Risk Level:** MEDIUM

**Risk factors:**
1. Implicit coupling between reed and bore creates potential for instability
2. Full dynamic reed model with mass requires careful discretization
3. Guillemain Psi parameter changes the nonlinearity shape -- must verify stability across full range
4. sqrt() in Bernoulli flow equation has numerical issues near zero pressure difference

**Alternative approaches:**
1. **Static reed (STK-style):** Memoryless reed table -- O(1), stable, but loses transient realism
2. **Polynomial approximation:** Fit cubic to reed reflection -- fast, avoids sqrt per sample

**Fallback architecture:**
- Start with static reed table (STK BlowHole/Saxofony proven approach)
- Add dynamic reed ODE only after static reed produces stable tone
- If Psi causes instability at extreme values, clamp effective range to 0-0.8

**Mitigation strategy:**
- Implement STK-style reed table first (Phase 3.1), validate basic tone
- Add dynamic reed ODE in Phase 3.2
- Add Psi confinement in Phase 3.2
- Use symplectic Euler for energy preservation
- Clamp reed displacement to physical range at all times

### Conical Bore Modeling

**Complexity:** MEDIUM-HIGH

**Risk Level:** MEDIUM

**Risk factors:**
1. Strategy B (correction filter) is an approximation -- may not capture all conical physics
2. Strategy C (true conical sections) has potential junction instabilities
3. Morphing between cylindrical and conical in real-time requires smooth coefficient interpolation

**Alternative approaches:**
1. **Strategy A (STK Saxofony):** Variable blow position along cylindrical bore -- crude but stable
2. **Strategy B (correction filter):** Good enough for most instruments, moderate CPU
3. **Strategy C (true conical):** Best accuracy, higher complexity

**Fallback architecture:**
- Primary: Strategy B (cylindrical + correction filter)
- Fallback: Strategy A (variable blow position) if correction filter produces artifacts
- Upgrade path: Strategy C for v2.0 if bore morphing accuracy needs improvement

**Mitigation strategy:**
- Implement cylindrical bore first (Phase 3.1) -- clarinet sounds good with pure cylindrical
- Add correction filter for conical approximation (Phase 3.2) -- validates saxophone/oboe
- Strategy C deferred to post-v1.0 unless accuracy demands it

### Tone Hole Lattice

**Complexity:** MEDIUM

**Risk Level:** LOW-MEDIUM

**Risk factors:**
1. Scattering junction mathematics require careful implementation
2. Tone hole placement affects tuning -- incorrect placement causes intonation issues
3. Gradual opening (legato) requires smooth interpolation of scattering coefficients

**Alternative approaches:**
1. **No tone holes:** Use only delay line length for pitch -- loses spectral character
2. **Spectral shaping filter:** Replace tone hole lattice with a lowpass that approximates cutoff effect

**Fallback architecture:**
- Primary: 4 virtual tone holes + register hole
- Fallback: single lowpass filter at tone_hole_cutoff frequency (no scattering, but correct spectral envelope)

### Dual Bore System

**Complexity:** MEDIUM

**Risk Level:** MEDIUM

**Risk factors:**
1. Doubles bore CPU cost when active
2. Cross-modulation via FEEDBACK_PATH can cause runaway if not gain-limited
3. Two bores sharing one reed excitation is physically simplified

**Alternative approaches:**
1. **Delay-based drone:** Simple pitched delay line (not a full bore model) for drone
2. **Detuned unison:** Second copy of primary bore with pitch offset (simpler than independent bore)

**Fallback architecture:**
- Primary: Full second bore waveguide
- Fallback: Simple delay line + lowpass for drone tone (much cheaper, less accurate)

### MPE + Breath Controller Integration

**Complexity:** MEDIUM

**Risk Level:** LOW

**Risk factors:**
1. MPE zone management requires correct enableLegacyMode() usage
2. Breath controller (CC2) must coexist with MPE pressure dimension
3. When no breath controller: velocity-to-sustain mapping needs careful design

**Fallback architecture:**
- Start with standard juce::Synthesiser + basic MIDI (Phase 3.1)
- Upgrade to juce::MPESynthesiser with MPE support (Phase 3.5)
- Breath controller mapping is parameter routing, not DSP risk

### Overall Project Risk

**Overall complexity:** HIGH
- Nonlinear reed-bore coupling (HIGH) + conical bore modeling (MEDIUM-HIGH) + tone hole physics (MEDIUM)
- 35 parameters, 16 DSP components, extensive acoustic research backing

**Highest risk component:** Reed-Bore Nonlinear Junction
- Represents ~40% of project risk
- Most algorithmically complex (implicit coupling, nonlinear ODE)
- Custom implementation required (no JUCE class)
- Must be stable across full Psi range (0-1.0) and all bore types

**Recommended approach:**
1. Phase 3.1: Static reed + cylindrical bore (lowest risk, proven approach)
2. Phase 3.2: Dynamic reed + Psi + conical correction (medium risk, core differentiator)
3. Phase 3.3: Tone holes + register hole + expression (medium risk)
4. Phase 3.4: Extended techniques + impossible physics (lower risk, additive features)
5. Phase 3.5: Oversampling + tuning + MPE + optimization (integration risk)

## Architecture Decisions

### Voice Architecture: MPESynthesiser vs Synthesiser

**Decision:** Use `juce::MPESynthesiser` with `enableLegacyMode()` for standard MIDI fallback

**Rationale:**
- Reed instruments are inherently expressive -- per-note pressure, slide, and pitch bend are natural mappings
- MPE Pressure -> Breath and MPE Slide -> Embouchure create the most natural playing experience
- enableLegacyMode() provides standard MIDI compatibility when MPE is not available
- Same pattern proven in O-Formant and O-Lyrica

**Alternatives considered:**
1. **juce::Synthesiser:** Simpler, but loses per-note expression. Would require separate CC routing.
2. **Custom voice allocation:** Maximum control but unnecessary complexity.

**Tradeoffs accepted:**
- MPESynthesiserVoice has 6 pure virtual methods (more boilerplate than SynthesiserVoice)
- enableLegacyMode() is on MPESynthesiserBase, not MPESynthesiser directly

### Bore Implementation: Strategy B (Correction Filter)

**Decision:** Start with cylindrical waveguide + conical correction filter (Strategy B)

**Rationale:**
- Strategy B provides good timbral accuracy at moderate CPU cost
- Allows bore morphing via filter coefficient interpolation (smooth real-time control)
- Cylindrical waveguide is well-understood and stable
- Strategy C (true conical) is the upgrade path, not the starting point

**Alternatives considered:**
1. **Strategy A (STK Saxofony):** Too crude -- variable blow position doesn't capture true conical physics
2. **Strategy C (true conical):** Best accuracy but junction instabilities at taper transitions, higher CPU

**Tradeoffs accepted:**
- Strategy B is an approximation -- won't capture all conical dynamics (especially bell-bore transitions)
- Real-time morphing via filter interpolation may produce slight artifacts during fast taper changes
- Acceptable because: initial release targets "good enough" conical, upgrade to C for accuracy-critical users

### Reed Nonlinearity: Polynomial Approximation Default

**Decision:** Use polynomial approximation (cubic fit) for default, Newton-Raphson for high-quality mode

**Rationale:**
- Polynomial: 4 multiplies + 3 adds per sample -- very fast
- Newton-Raphson: ~30 ops per sample -- reserved for mono/4x mode
- Polynomial handles 95% of the timbral range adequately
- NR only needed for extreme reed dynamics (very high mass, very low damping)

**Alternatives considered:**
1. **Table lookup (STK):** Fastest but inflexible -- can't morph Psi smoothly
2. **Full NR always:** Best accuracy but too expensive for polyphonic mode

**Tradeoffs accepted:**
- Polynomial has small error vs true nonlinearity at extreme parameter values
- Acceptable because: 4x oversampling mode enables NR for users who need precision

### Mono-First Design

**Decision:** Monophonic mode is primary, polyphonic is optional

**Rationale:**
- Reed instruments are fundamentally monophonic -- one reed, one bore, one player
- Mono mode allows higher quality: 4x oversampling, NR solver, more tone holes
- Poly mode is for sound design / layering, not realism
- Mono mode enables legato transitions (smooth delay line interpolation) which is the most expressive feature

**Alternatives considered:**
1. **Poly-first:** Would limit quality per voice, not authentic for reed instruments
2. **Mono-only:** Too restrictive for sound designers

**Tradeoffs accepted:**
- Polyphonic mode uses 2x oversampling and polynomial approximation (lower quality per voice)
- Acceptable because: users choosing poly mode want texture/layering, not solo instrument realism

## Special Considerations

### Thread Safety
- All parameter reads use atomic `getRawParameterValue()->load()`
- Reed ODE state (x, x_dot) is per-voice -- no cross-thread access
- Bore delay line state is per-voice -- no sharing
- Tuning table: atomic pointer swap from message thread
- Instrument preset target: atomic int, interpolation on audio thread
- Voice allocation via juce::MPESynthesiser handles locking internally

### Performance
- Per-voice cost at 44.1 kHz with 2x oversampling (~88.2 kHz internal):
  - Reed dynamics: ~25 ops/sample
  - Bernoulli flow + sqrt: ~15 ops/sample
  - Reed nonlinearity (polynomial): ~4 ops/sample
  - Bore delay lines: ~6 ops/sample
  - Viscothermal loss: ~3 ops/sample
  - Bell reflection: ~3 ops/sample
  - Tone holes (x4): ~20 ops/sample
  - Breath noise: ~5 ops/sample
  - Vibrato LFO: ~3 ops/sample
  - Mouthpiece volume: ~5 ops/sample
  - **Total: ~89 ops/internal sample = ~178 ops/output sample (2x OS)**
- Practical polyphony: 16-32 voices at 2x OS
- Mono mode (4x OS): ~356 ops/output sample (~0.4% CPU single core)
- Dual bore: approximately doubles bore section cost when active

### Denormal Protection
- Use `juce::ScopedNoDenormals` in processBlock()
- Clamp reed displacement x and velocity x_dot to prevent tiny values
- juce::dsp::DelayLine and juce::dsp::IIR::Filter handle denormals internally
- Add epsilon to sqrt argument: `sqrt(max(|dp|, 1e-10))` to avoid denormals

### Sample Rate Handling
- All delay line lengths recalculated in `prepareToPlay()` for new sample rate
- Oversampling internal rate = sampleRate * oversamplingFactor
- Filter coefficients recalculated on sample rate change
- Reed ODE integration step = 1.0 / internalSampleRate
- Maximum delay length sized for lowest note at maximum expected rate (192 kHz * 4x OS)

### Latency
- Waveguide: 0 algorithmic latency (causal system)
- Oversampling: ~8 samples (2x halfband filter) or ~16 samples (4x)
- Reported via `setLatencySamples()` in `prepareToPlay()`
- NOTE: getLatencySamples() is NOT virtual in JUCE 8 -- use setLatencySamples() only
