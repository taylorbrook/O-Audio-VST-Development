2. UNDER 8-WAY CPU LOAD — REPRODUCED IMMEDIATELY

  10 runs   ->  1 firing   (CN, run 9: "1 allocation(s) ... 8/8 meters registered")

3. ATTRIBUTION — a temporary diagnostic recording the allocating thread
------------------------------------------------------------------------
  note() was instrumented to compare std::this_thread::get_id() against the thread that
  armed the counter, and the AO verdict was made to print the foreign tally.

  40 runs under 8-way CPU load:

     4 of 40 FIRED    ->  "1 allocation(s) ... [DIAG foreign-thread 1]"     <-- all four
    36 of 40 clean    ->  "0 allocation(s) ... [DIAG foreign-thread 0]"

  4 of 4 attributed to a thread OTHER than the one calling processBlock. No exceptions.

  CAUSE: rtcheck::armed is a PROCESS-WIDE flag, so the replaced operator new family counted
  any thread's allocation inside the window — the JUCE message thread and the macOS runtime
  threads a console app keeps alive included. Contention does not make processBlock
  allocate; it widens the window in which some other thread's allocation lands inside it.


4. THE FIX (tests/render-harness/main.cpp — the only tree change made at verify)
---------------------------------------------------------------------------------
  - note() counts only allocations on the ARMING thread
  - foreign allocations are tallied separately and STILL REPORTED beside the verdict
  - every arm site routes through one rtcheck::arm(), so the unattributed form cannot be
    reintroduced by writing armed.store(true) directly

  BEFORE:  4 of 40 loaded runs FAILED
  AFTER:   0 of 40 loaded runs failed; the one foreign allocation observed printed as

     [PASS] CN no-allocation-with-metering 0 allocation(s) across 65 processBlock calls
            incl. an 8192-sample over-size block, with the eight meters live; 8/8 meters
            registered the render [+1 foreign-thread, NOT counted — see rtcheck]

  That exact run would have FAILED before the fix.
